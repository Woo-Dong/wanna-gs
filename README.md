# 원하GS · WANNA GS

자연어 상품 요청 → 점포별 수요 → 경영주 묶음 검토/보수적 자동발주 → 모의 자동 결제 → 입고·48시간 픽업을 시연하는 랄프톤 프로토타입.

이 문서 묶음은 최초 구현의 현재 기준이다. 별도의 문서 릴리스 번호를 붙이지 않고 Git 이력과 결정 기록으로 변경을 추적한다.

이 저장소에는 설계 문서, 에이전트 작업 지침, 사전점검 도구가 있다. 앱·CI·DB·배포는 아직 구현하지 않았다. 실제 문서 검증·Git 게시 상태와 남은 준비는 [진행 기록](docs/PROGRESS.md)에서 확인한다. GitHub와 Vercel 등 환경을 준비한 뒤 `/goal`로 개발을 시작한다.

## 이 goal의 목적과 차별점

`/goal`을 실행하면 에이전트가 자료 조사부터 구현, 테스트, Vercel 배포까지 진행한다. 사용자가 정한 핵심 요구는 유지하고, 미정인 세부 정책은 검토와 기록을 거쳐 결정한다. 완료 여부는 실제 테스트와 배포 결과로 판단한다.

| 차별점 | 실행 방식 | 남겨야 할 증거 |
|---|---|---|
| 실행 시점의 새로운 조사 | 당시 트렌드·고객/경영주 니즈·기능별 UX/기술/검증 자료를 직접 확인. 대화의 특정 상품 예시에 범위를 고정하지 않음 | 출처·날짜·한계 → 설계 결정 → 데이터·시나리오·테스트 연결 |
| 현실적인 데이터와 평가를 함께 구축 | 약 200개 다양한 상품, 실제 점포/좌표, 합성 사용자와 모의 거래를 준비. 정상·모호·예외 상황에서 발화 생성 | 사실/합성 구분, seed 버전·무결성, 평가셋 분할 |
| 핵심 요구를 보존하는 자율 결정 | 기존 유효 결정 확인 → 정책 초안 → 서로 다른 두 에이전트 검토 → 채택 → 구현/회귀 검증 | ADR·대체/의존 관계·기각 이유·변경 영향 |
| 역할별 개발과 독립 검증 | 고객/경영주 UX·FE·BE, DBA, 조사, 자연어 실험/평가, QA, 통합 담당 분리 | 작업 계약·파일 소유권·공유 버전 확인·별도 검증자 |
| 작은 기능부터 단계적으로 통합 | 각 기능 구현과 단위 검증 후 실제 DB·인접 기능·브라우저로 연결 범위를 넓힘 | G0~G6 결과와 해당 코드/데이터 revision |
| 자연어 품질 자체를 개선 목표로 포함 | 기준선 → 실패 분석 → 프롬프트/검색/데이터 구조 변경 → 독립 평가 → 최선 버전 채택 | 전후 지표·범주별 회귀·기각 후보·중단 이유 |
| GitHub에서 단계별 개발 이력 유지 | 검증한 변경을 commit/push·작업 PR·CI·통합 branch로 누적하고 제출 후보를 검증 | 원격 SHA·PR·checks·배포 source의 연결 |
| 에이전트 운영 방식도 점검 | 인계 누락·역할 충돌·불필요한 반복을 독립 감사하고 제한된 개선 시험 수행 | 운영 변경의 가설·효과·복구 판단 |
| 장시간 실행·실패 후 재개 | 유효 체크포인트와 실패 원인을 남기고 마지막 확인된 상태에서 이어감 | PROGRESS 포인터·실패 보고서·원격 상태 대조 |

완성도와 실제 검증을 우선한다. 단순 작업에는 가벼운 모델을, 중요한 결정·복잡한 구현/검토에는 적합한 강한 모델을 선택할 수 있다. 실제 가용 모델·동시 실행 슬롯·계정 한도를 따르며 역할 수만큼 에이전트를 한꺼번에 생성하지 않는다.

## 반드시 유지할 서비스 범위

고객은 자연어로 상품을 찾고 상품·수량·한 점포·가격을 확인한 뒤 자동 구매에 동의해 요청한다. 경영주가 수요를 모아 승인하거나, 미리 승인한 보수적 규칙으로 자동발주한다. 물량이 확보되면 접수 순서로 배정하고 모의 자동 결제와 예약을 처리한다.

입고 후 픽업 가능 알림을 생성한다. 수령 마감은 알림 생성 시각으로부터 정확히 48시간이며, 마감 정각부터 수령할 수 없다.

경영주는 건별 확인을 늘리지 않도록 묶음 요약·자연어 지시로 관리한다. 미확보 요청 관리와 미식별 요청 보존/경영주 조회도 포함한다. 발주 승인·공급 확보·결제·예약·입고는 각각 관리한다. 자동발주는 활성 발주에 연결되지 않은 유효 미확보 수요만 대상으로 삼는다. 실행 시 최신 수량·예산·발주 조건을 한 트랜잭션에서 다시 검증한다. LLM은 해석과 제안을 맡고 권한·동의·금액·수량·기한은 서버가 검증한다.

본부 화면, 사진·링크 입력, 레시피·복수 상품 묶음, 실제 GS 연동·실제 청구는 제외한다. 본부 가치는 설명만 남기고 Vector RAG는 개선 근거가 있을 때의 선택 실험으로 둔다. 기술 기준선은 Next.js/TypeScript FE·BE, Neon PostgreSQL, Vercel AI Gateway다. Gemini API 직접 호출을 예비 경로로 준비하고 양쪽 접근을 사전점검한다.

## 시작 전 준비

1. [GitHub 저장소](https://github.com/Woo-Dong/wanna-gs)를 원하는 위치에 clone하거나 기존 clone/worktree를 연다. Git 작성자·인증, push/PR/merge·Actions 권한과 실제 브랜치 보호·승인 경로를 확인한다.
2. Codex 환경에서 프로젝트·Git 메타데이터 쓰기, 패키지 설치, 네트워크, 브라우저·서브 에이전트 권한을 준비한다. 설정 파일 이름뿐 아니라 P00의 실제 작업 결과를 확인한다. 새 장비의 신뢰/실행 키 위치와 선택적 설정 예시는 [18번](docs/18-environment-preflight.md)의 안내를 따른다.
3. Vercel에 로그인하고 이 GitHub 저장소를 프로젝트에 연결한다. 플랜의 행사 이용 조건, Production 브랜치, Preview/Production 환경과 배포 권한을 확인한다. 자동 테스트용 보호 우회와 심사자용 공유 링크/공개 접근을 나누어 준비하고 로그인하지 않은 브라우저에서도 확인한다.
4. Neon 계정은 생성 완료로 보고받았다. [Neon 후속 연결 가이드](docs/28-neon-setup-guide.md)에 따라 제공 프로젝트의 접근 권한과 브랜치를 확인하고 테스트·Preview·제출 데이터를 분리한다. 연결 정보는 서버 비밀 저장소에 넣는다. 계정 생성만으로 DB 연결 성공을 판정하지 않는다.
5. Gateway의 무료 모델·잔액·인증을 확인한다. Gemini 예비 경로용 프로젝트와 키는 사용자가 만들고 서버 비밀 저장소에 주입한다. 무료 등급과 호출 한도를 확인하며 카드 등록·유료 전환을 자동으로 진행하지 않는다. 계정이 카드·약관·본인 확인을 요구하면 그 조건과 비용을 먼저 확인한다.
6. Node·패키지 관리자·Git·Python 3와 테스트 브라우저를 준비한다. 로컬/CI/Preview/Production별 필요한 인증을 확인하고 비밀값을 저장소나 채팅에 넣지 않는다.
7. 아래 inspect와 live preflight를 실행해 부족한 설정을 확인한 뒤 goal을 시작한다. 실제 계정·권한·한도 차단은 준비 단계에서 해결한다.

`approval_policy="never"`는 승인 질문을 생략하는 설정이고 `sandbox_mode="danger-full-access"`는 샌드박스 범위를 바꾸는 설정이다. 어느 쪽도 외부 계정 인증·조직 규칙·사용량 제한을 해결하지 않는다. 이 프로젝트는 두 값을 필수 설정으로 강제하거나 config에 자동 저장하지 않는다. 실제 적용 권한과 실패 경로를 [P00 안내](docs/18-environment-preflight.md)로 확인한다.

### 작업 위치 확인

새로 받는 경우:

```bash
git clone https://github.com/Woo-Dong/wanna-gs.git
cd wanna-gs
git rev-parse --show-toplevel
```

기존 clone 또는 worktree에서는 마지막 명령으로 현재 루트를 확인한다. 이후 명령은 이 루트에서 실행한다. 폴더 이름이나 사용자 홈 경로는 고정하지 않는다. 아직 Git이 없는 문서 폴더라면 `pwd`와 `AGENTS.md`·`card.md`·`docs/GOAL.md`를 대조하고, 기존 저장소를 새로 초기화하지 않는다. 다른 장비에서 받은 프로젝트에는 로컬 인증·비밀값·Vercel 연결 설정을 별도로 준비한다.

## 모델 키와 무료 한도

Gateway를 기본으로 쓰고, 사용자가 발급한 Gemini 키를 서버의 `GEMINI_API_KEY`에 넣어 예비 경로를 준비한다. 키는 채팅이나 저장소에 올리지 않는다. `GEMINI_MODEL_ID`는 실행 당시 사용 가능한 저가 모델 중 한국어·구조화 출력 검증을 통과한 것으로 정한다.

테스트 중과 배포 직전에 잔량을 확인한다. 남은 필수 평가·배포 검증·데모에 부족하면 Gemini 직접 호출로 전환하고, 선택한 모델로 자연어 평가와 고객/경영주 E2E를 다시 검증한다. 키를 넣는 것만으로 무료 이용이 보장되지는 않으므로 Google 프로젝트의 무료 등급과 호출 한도도 확인한다. 유료 전환·자동 충전은 별도 승인 없이 하지 않는다. 설정과 전환 절차는 [모델 사용량과 Gemini 전환](docs/25-model-budget-and-fallback.md)을 따른다.

## 1. 전용 스킬로 연결 점검

Codex에서 먼저 읽기 전용 점검:

```text
$wanna-gs-preflight 이 프로젝트를 inspect 모드로 점검하고 GitHub/Vercel 인증 상태와 부족한 설정을 알려줘.
```

이어서 실제 시험:

```text
$wanna-gs-preflight live 모드로 임시 GitHub 브랜치·PR·CI·Vercel Preview·격리 DB·실제 모델·브라우저·서브 에이전트 연동을 시험하고 정리해줘. goal 준비 상태와 미검증 릴리스 조건을 보고해줘.
```

스킬이 목록에 없으면 `.agents/skills/wanna-gs-preflight/SKILL.md`를 읽고 실행하도록 요청한다. live 모드는 지정 repo/project의 임시 리소스를 사용한다. 기존 기본·통합 branch, Production 배포·설정·데이터는 변경하지 않는다.

CLI에서 로컬 검사기만 실행할 수도 있다:

```bash
python3 .agents/skills/wanna-gs-preflight/scripts/inspect_environment.py --project . --check-auth
```

이 검사기의 PARTIAL은 실제 외부 기본 동작 검사가 아직 남았다는 뜻이다. 로컬 관찰만으로 READY를 반환하지 않는다. 스킬이 실제 시험 증거를 모아 READY/PARTIAL/BLOCKED를 판정한다. READY는 목표 시작 범위이며 Production 실행 검증은 별도다.

## 2. 한 번의 goal로 개발

[GOAL.md](docs/GOAL.md)에 전체 실행 문장이 있다. 짧게 시작하려면:

```text
/goal docs/GOAL.md 계약에 따라 원하GS를 구현·검증하고, 단계별 commit/push·PR·CI·자율 정책 검토를 거쳐 Vercel 제출 URL에서 최종 검증까지 완료하라.
```

목표 안에서 영역별 구현→단위 검사→독립 검증→통합 검사→commit/push→PR/CI→통합 branch 누적→최종 정책 감사→제출 branch 병합·배포가 이어진다. 미지정 데모 정책은 기존 정의와 가치를 지키며 두 서브 에이전트 검토 후 채택한다. 작은 정책마다 사람의 답변을 기다리지 않는다.

| 자연어 품질 개선 | 기준선 측정, 실패별 후보 실험, 독립 평가·회귀 검사, 최선 버전 선택 | 사전 출시 최소 기준 충족 및 개선 결과/중단 사유 기록 |
| 제출 전 전체 검증 | 전체 적용 인수 기준·자연어 최종 평가·두 역할 UX·정책 빈틈·운영 감사 | 최신 제출 기반과 결합한 정확한 후보의 G5 통과 |
| 실제 배포·제출 검증 | 검증된 릴리스 PR 병합, Vercel 배포, 실제 제출 URL에서 모델·DB·브라우저 확인 | 해당 deployment/source/schema/seed/model에 대한 G6 통과 |
| 인계·완료 판정 | URL·실행/시연/복구 안내·결정/실험/검증·Git/배포 이력 정리 | 아래 완료 체크리스트 모두 충족 |

초기 조사는 계획 전에 직접 수행해 질문·근거 사례·설계/테스트 매핑과 한계를 독립 검토하고, 본격 데이터 조사는 계획을 구체화한 뒤 수행한다. 각 적용 기능 G0에서도 현재 질문을 답하는 조사 요약을 확인하며 유효한 근거는 재사용하고 필요한 부분만 갱신한다. 평가 정답·최종 holdout은 앱 테이블·별칭·공개 번들에 넣지 않는다. 스키마와 seed importer는 DB 삽입보다 먼저 만든다. 테스트·CI·게이트 실행기 역시 초기 구축에서 구현하며, 첫 구축 PR은 그 단계에서 실행할 수 있는 검사로 검증한다. 완제품 테스트는 해당 기능을 구현한 뒤 적용한다.

## 실행 중 지켜야 할 운영 규칙

최신 사용자 정의와 [핵심 요구](docs/CORE_REQUIREMENTS.md)가 기준이다. 작업 시작·새 결정·통합 시 [유효 결정 인덱스](docs/DECISION_INDEX.md)를 읽고 관련 계약·데이터·정책 버전을 확인한다. 변경은 의존 작업에 전달하고 관련 검증 결과를 stale로 처리한다. 사용자 고정 정의를 투표로 바꾸거나 기각된 접근을 이유 없이 반복하지 않는다. 개발 정책 위임은 앱 고객/경영주의 확인·동의·승인을 대신하지 않는다.

구현자 자체 검사와 독립 검증을 구분한다. 고객 QA와 경영주 QA는 서로 다른 agent ID로 배정하고 각각 대상 기능 구현자와도 분리해 실제 브라우저에서 UX를 확인한다. 슬롯이 적으면 순차 실행한다. 공통 스키마·마이그레이션·lockfile·계약에는 작성자를 한 명 두고, 독립 가능한 작업만 병렬화한다. 운영 감사자는 또 다른 관리자/감사자를 재귀 생성하지 않는다.

기능마다 정상·경계·실패를 검사하고 거래에는 중복·경합·세션 격리·시간 경계를 포함한다. 테스트 0개, skip, stale, 불안정한 결과나 fixture 성공을 필수 live 통과로 표시하지 않는다. 화면 캡처만으로 거래 성공을 판단하지 않고 DB/event/UI 상태를 대조한다. 정책·코드·모델·프롬프트·seed가 바뀌면 영향을 받는 검사부터 상위 통합까지 재검증한다.

작업 브랜치 → 통합 브랜치 → 제출 브랜치로 진행한다. 검증 후 작은 논리 단위로 commit/push하고 PR·독립 리뷰·CI를 연결한다. 새 통합 검사 항목의 기본 이름은 `gate`이며 기존 필수 검사 설정과 호환되어야 한다. 작업→통합 squash는 허용 방식 안에서 사용하고, 통합→main은 이력을 보존하는 merge/FF를 우선한다. 초기/중간 Preview를 유지하되 최종 Production은 G5 이후, 완료는 배포 후 G6까지 요구한다. 같은 계정의 에이전트 리뷰를 GitHub의 별도 인간 승인으로 계산하지 않는다.

실패는 재현·분류·원인 가설·수정·관련 회귀 검증 순서로 처리한다. timeout이면 기존 작업 ID/멱등 키의 상태를 먼저 확인해 중복 발주·결제·배포를 방지한다. 실패한 변경은 병합하지 않으며 앱 복구와 DB 복구를 따로 검토한다. 근거 없는 동일 재시도를 제한하고 필요하면 독립 진단을 배정한다.

## 자연어 실험의 채택·중단 기준

[21번 평가 기준](docs/21-ux-and-natural-language-quality.md)과 [23번 실험 루프](docs/23-nl-experiment-loop.md)를 따른다. 실제 사용 상황을 평가 범주로 나누고, 검색 누락·오인식·과도한 거절·잘못된 실행을 측정해 개선한다.

- 평가 규모 기본안은 고객 300개 이상·경영주 120개 이상이다. 같은 니즈·의도·상품/상태 조합의 표현·오타·번역·말투 변형을 scenario/paraphrase family와 `split_group_id`로 묶어 한 split에만 두고 개발/검증/최종 평가셋으로 분리한다. 출처 사실과 에이전트가 창작한 발화를 구분한다.
- 최종 평가셋(holdout)은 독립 평가자가 관리하고 프롬프트 예시·상품 별칭·개발 테스트에 유출하지 않는다. 노출 후 튜닝했다면 새 독립 평가셋과 변경 이력을 준비한다.
- 기본 시도 한도는 고객/경영주 각각 후보 6개, 전체 12개이며 같은 역할에서 연속 3개 후보가 의미 있는 개선에 실패하면 추가 최적화를 멈춘다. 규모·출시 최소 기준·개선폭·반복수·호출량·한도는 결과를 보기 전에 ADR로 채택하거나 조정한다.
- 출시 최소 기준을 통과한 최선 버전이 있으면 추가 개선을 포기하고 실패 범주·시도·한계를 기록한 뒤 배포 작업을 계속할 수 있다. 최소 기준 미달이나 허구 SKU·동의·권한·수량 오류를 실험 중단으로 면제할 수 없다.
- 무료 잔량·호출 제한을 기준으로 실험량을 계산하고 최종 평가/G6 호출분을 확보한다. 429·한도 소진·미실행을 정확도 개선으로 계산하지 않으며, 결과를 보고 합격선을 낮추지 않는다.

## 추가로 유의할 사항과 재개

| 유의점 | 적용 원칙 |
|---|---|
| 자동 진행의 전제 | 계정 가입·인증·약관·조직 권한 등 사람이 필요한 준비는 goal 전에 식별. 실제 적용 파일/네트워크/Git/브라우저 권한까지 검사 |
| 개발 환경과 앱 모델 구분 | Workspace 로그인만으로 앱 API가 준비됐다고 보지 않음. local/CI/Preview/Production의 모델 인증·잔량 각각 확인 |
| 실제 자료와 데모 구분 | 실제 점포 위치를 써도 가격·재고·공급·거래는 모의. 과거 기사로 현재 인기나 특정 점포 재고를 보장하지 않음 |
| 준비 성공과 최종 성공 구분 | preflight READY는 시작 준비 증거. 실제 보호 branch 병합·Production·최종 품질은 후속 검증 필요 |
| 승인 설정과 권한 구분 | 질문을 생략해도 권한이 생기지 않음. sandbox·조직 정책·브랜치 보호를 해제해 완주시키지 않음 |
| 품질 우선의 경계 | 많은 시간/토큰 사용 허용은 새 유료 구매·자동 충전·사용량 한도 무시의 허용이 아님 |
| 운영 중단 | 유효 체크포인트마다 task/branch/PR/게이트/배포/다음 행동 기록. 갑작스런 한도 정지 직전 기록을 보장하지 않음 |
| 재개 | PROGRESS와 실제 원격 Git·CI·deployment·DB를 대조해 마지막 유효 단계부터 계속. 실제 goal 상태/재개 방법은 제공 도구 계약을 따름 |
| 외부 차단 | 가능한 독립 작업은 계속하되 차단된 필수 작업을 완료로 표시하지 않음. 필요한 외부 조치·실패 근거·재개 위치를 남김 |
| 외부 리뷰 | 제안을 근거와 기존 요구에 대조해 채택/수정/미채택 기록. 보고서에만 있는 승인을 사용자 확정으로 승격하지 않음 |

이미 위임된 지정 repo의 Git 작업·검증된 병합·연결된 Vercel 배포·허용된 DB/테스트는 매 단계 재확인하지 않는다. 새로운 유료 구매, 외부 repo 변경, 사용자 데이터 파괴, 제외 기능 추가까지 위임된 것은 아니다.

## 최종 완료 체크리스트

합의한 프로토타입 범위와 사전에 정한 품질 기준으로 완료를 판단한다. 현재 아래 항목은 모두 미검증 상태다. 상용 운영 정책과 평가하지 않은 입력은 검증 범위에 포함되지 않는다.

- [ ] 핵심 요구와 적용 인수 기준이 구현·테스트에 연결되고 관련 G0~G6가 통과했다.
- [ ] 실행 당시 조사 기록에서 약 200개 상품·검증된 실제 점포/위치·합성 사용자·시나리오·평가셋으로 이어지는 근거와 버전이 있다.
- [ ] 고객 요청부터 경영주 발주·공급 확보·모의 자동 결제·입고·48시간 수령까지 정상/필수 예외 흐름이 검증됐다.
- [ ] 중복 실행·초과 배정/발주·동의/권한 위반·타 세션 간섭과 reset·시간 경계를 검사했다.
- [ ] 자연어 기준선·후보·최선 버전의 비교, 독립 최종 평가, 개선 달성 또는 정당한 중단 사유를 기록했고 출시 최소 기준을 충족했다.
- [ ] 구현자와 분리된 서로 다른 고객/경영주 QA의 브라우저 검사 및 최종 정책·운영 감사에서 중대한 미해결 문제가 없다.
- [ ] 실제 제출 Vercel URL에서 실제 모델·DB·브라우저 동작과 심사자 접근 경로를 확인했다.
- [ ] Gateway와 Gemini 예비 경로를 시험하고, 최종 선택 모델의 품질·전환 검증·잔량·남은 데모 예산을 기록했다.
- [ ] 원격 commit/PR/CI·릴리스 source SHA·deployment ID·schema/seed/model/config가 검증한 버전과 일치한다.
- [ ] 실행·시연·초기화·복구 안내, 유효 결정/기각 이력, 알려진 한계와 후속 개선을 정리했다.
- [ ] 필수 미실행·실패·외부 차단을 숨기거나 과거/fixture 결과로 대체한 항목이 없다.

최종 보고에는 제출 URL, 구현 범위, 실제 테스트/자연어 평가 결과, 주요 자율 결정과 개선 한계, Git/배포 증거, 실행·복구 방법을 포함한다. 모든 필수 조건을 확인한 뒤에만 goal을 완료 처리한다.

## 최근 실행 계획 검토

전체 자료 수집과 기반 개발은 [ADR-001](docs/decisions/ADR-001-minimal-seed-development.md)의 최소 seed 방식으로 병행한다. 실제 점포 검증·전체 평가·최종 G5/G6는 유지한다. fixture 중간 결과는 Preview에서 확인하며, 중간 Production을 별도 완료 기준으로 허용하는 안은 아직 채택하지 않았다. [외부 제안 검토](docs/reviews/2026-09-21-execution-proposals.md)에 이유와 대안을 정리했다.

## 기능의 원래 목적을 유지하는 장치

[card.md](card.md)는 새 작업·인계·오류 수정·컨텍스트 재개 때 읽는 짧은 작업 기준이다. 고객과 경영주의 원래 정상 흐름을 적고 [핵심 요구](docs/CORE_REQUIREMENTS.md)와 유효 결정에 연결했다. 작업 계약에는 사용자 결과와 유지할 정상 사례, 실패 보고서에는 수정 전후 영향, 독립 검증에는 정상·실패·인접 기능 증거를 기록한다.

오류가 사라졌어도 정상 요청을 전부 거절하거나 필수 기능을 없앴다면 완료할 수 없다. 기존 recovery·verify 스킬에 이 판정을 연결했으며 GATE-BOOTSTRAP에서 필수 항목과 증거 누락을 검사하도록 구현한다. 현재는 문서·스킬 지침이며 앱 테스트나 CI가 이미 강제하는 상태는 아니다.

## 화면 디자인과 이름 읽는 법

**원하GS는 ‘원하지쓰’라고 읽는다.** 첫 화면에서 이름과 발음 안내를 함께 보여주며 이후 헤더·소개에서도 다시 확인할 수 있게 한다. `~GS` 카피는 제목에 쓰고, 요청·발주·결제·픽업 상태와 행동 버튼은 명확한 한국어로 표시한다.

[디자인 가이드](docs/26-design-and-brand-guide.md)에 사용자 참고 이미지, 공식 우리동네GS 화면에서 참고할 요소, 시안·블루 색상 토큰, 고객/경영주 화면 구성, 발음·접근성·상태별 검증 기준을 정리했다. [카피 가이드](docs/12-demo-and-copy.md)의 `담아두GS`는 예약 확정, `여기 있GS`는 픽업 가능 상태에 연결한다. 화면 구현 담당과 독립 UX QA는 D-35·CORE-24·AC-30을 작업 계약에 포함한다.

## 서비스가 지켜야 할 가치

고객의 자연어를 DB의 상품코드로 연결하고, 찾지 못한 니즈도 정제해 남긴다. 대체 상품은 차이를 알리고 다시 확인받는다. 경영주는 모인 수요와 필요한 예외를 보고 사전 승인한 정책 안에서 자동발주한다. 이 과정의 기록은 향후 본부가 미충족 수요를 이해할 자료가 될 수 있다.

[27번 가치·검증 규칙](docs/27-service-values-and-guardrails.md)은 잘못된 SKU 대체, 반복 승인 알림, 과잉/중복 발주, 오류가 섞인 니즈 통계를 차단한다. 고객의 조작·질문과 경영주의 승인·작업 시간을 기준선과 비교하며 기능 성공과 편의성을 함께 확인한다. 인근 수요·다른 상품 발주 제안은 선택 부가 기능이고 본부 화면은 만들지 않는다.

[최종 홍보 시안](docs/assets/wanna-gs-promo-mascot.png)은 시안·블루와 ‘원하지쓰’ 안내, 고객/경영주 입력 예시, 무무씨 참고 캐릭터를 담았다. 생성 컨셉이며 실제 앱 실행 화면은 아니다. [생성 프롬프트와 기록](docs/assets/promo-generation-notes.md), [디자인 가이드](docs/26-design-and-brand-guide.md)를 함께 참고한다.

## 시안을 구현에 활용하고 팀원 제안을 검토하는 방법

[26번의 이미지 활용 루프](docs/26-design-and-brand-guide.md)에 따라 최종 시안을 공통 디자인 참고로 사용한다. 화면별 컴포넌트/상태에 연결해 구현한 뒤 실제 브라우저 화면과 비교한다. 홍보용 고정 숫자·생략된 절차를 코드 규칙으로 복사하거나 매 반복 이미지를 재생성하지 않는다.

새 팀원 자료는 [경영주 비교 검토](docs/reviews/2026-09-21-merchant-handoff-review.md)에 정리했다. MOQ 현황·이력·자동 설정 영향 확인 등 후보와 픽업 제외·회차 상한·재발주 제한 등의 충돌을 구분했다. **사용자가 선택하기 전까지 제품 명세·DB·goal 필수 기능에 병합하지 않는다.**

후속 사용자 결정 D-41/42는 반영했다. 모집 목표를 넘는 요청도 받고, 발주·구매 동의·픽업 기한을 혼동해 자동 구매나 입고 전 수령 만료가 발생하지 않도록 한다. 나머지 경영주 기능은 비교 검토의 최신 권고를 보고 선택하며 아직 일괄 병합하지 않았다.
