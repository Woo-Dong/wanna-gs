# Independent NL evaluation

Owner: nl-evaluator (`/root/method_auditor`). Context APP-v3, ADR-003. These tools never call a model. `python3 -m unittest discover -s evals/tests -v` checks the scorer, not application quality.

- taxonomy.json fixes 300 customer +120 merchant cases (dev252, validation84, private holdout84).
- case.schema.json documents cases. scorer.py also validates critical execution fields and rejects pending catalog bindings.
- adapter.py normalizes N01 customer/merchant responses. It does not infer a completed customer consent or grant execution authority.
- dev.jsonl / validation.jsonl will contain source-bound public cases. The private holdout is evaluator-only under the ignored `artifacts/private/run-20260921/holdout/` directory. Do not inspect, import, bundle, copy into aliases/prompts, or print those files.
- All observed errors and provider attempts remain in the denominator/accounting. Product domain checks and FE confirmation are separate G1~G6 evidence; a passing NL metric cannot substitute for them.

The customer API adapter separates primary exact/confirm IDs and explicitly labelled alternatives. Scoring requires the correct primary SKU, no wrong primary assertion, no unknown SKU and a confirmation-oriented response. The UI's actual confirmation behavior requires independent browser QA. The merchant normalized command is `{intent: modify|restore, scope: current_proposal|policy, constraints: {...}}`. All nonempty explicit constraints must match exactly; null, empty arrays and false schema defaults are removed by the adapter. A clarify action requires a nonempty question and never executes.

A runner observation includes case_id, role, mode=fixture|live, run_fingerprint, transport, schema_valid, normalized response, and attempts with provider_called/status/latency_ms/usage. run_fingerprint must bind source SHA, model/prompt/search/catalog/schema/config versions. `domain_violations` may attach real downstream violations; absence is not proof that domain gates passed. The report always says `product_gates=not_assessed`.

```sh
python3 evals/scorer.py --cases evals/validation.jsonl --observations PATH_TO_RESPONSES --catalog PATH_TO_CATALOG --expected-hash DATASET_CANONICAL_HASH --mode live --run-fingerprint CONFIG_FINGERPRINT --run-id UNIQUE_RUN_ID --coverage evals/validation-coverage.json
```

Default reports show aggregate counts and hashes only. `--private-details` includes case results and must be sent only to evaluator private artifacts when scoring holdout. Baseline uses dev+validation only. Final frozen best is evaluated on protected holdout once. Earlier failed results are never replaced by later successes.

Scorer self-tests use three explicitly fictional IDs in isolated fixtures. Those IDs are not catalog data and cannot be passed as production evaluation binding. Live model calls and product evaluation remain not_run until N01 and the actual catalog contract are ready.

Each completed model turn must have a successful provider attempt with `status: ok`; timeout-only observations cannot count as live evidence. Use `prior_observations` (transport/schema_valid/response/attempts and optional checked case_id/role) for earlier user turns, not raw prior response placeholders. `expected_prior` holds the evaluator oracle for each earlier turn and must never enter the model prompt. Keep the actual assistant responses in conversation history.

`nl_minimum_pass` describes the supplied subset only. `stage_ready` requires live evidence and exact frozen coverage (hash, count and per-role/split/category counts). CLI exits successfully only for `stage_ready`; `repeat_ready` additionally needs two distinct run IDs with an identical run fingerprint and frozen dataset. The catalog fingerprint uses SHA256 of JSON.stringify(Product[]) in catalog order; dataset fingerprints use canonical sorted keys. Never substitute one for the other.

The manifest is frozen before first model baseline; current 248-SKU binding is catalog-248-v1. Public scenarios are synthetic expansions grounded in the stated source IDs; they are not observed customer quotes. Same SKU-derived phrasing is confined to a single split. Private generation seed and generator remain with the evaluator. Do not reconstruct protected cases from metadata.

## HTTP evaluation runner (E02)

`scripts/run_nl_eval.py` is a transport runner; it never puts `expected`, `expected_prior`, `label`, research metadata or scorer output into a model request. Only the current user turn, actual previous assistant responses and allowlisted business state go to `/api/product-assistant` or `/api/merchant-assistant`. Each user turn costs a separate possible provider attempt. Static scripted assistant turns are rejected.

**Default is plan-only. No HTTP request occurs without `--execute`.** Actual model evaluation remains unrun until I01 and explicit stage dispatch. Self-tests use local fake HTTP servers and temporary budget files, including tests of the `live` protocol; those are not provider evidence.

```sh
python3 -m unittest discover -s tests/eval-runner -v
python3 scripts/run_nl_eval.py --config artifacts/private/run-20260921/baseline-config.json --state-fixtures artifacts/private/run-20260921/merchant-states.json --output artifacts/private/run-20260921/baseline
# Add --execute only for the separately authorized actual stage.
# Add --resume to the same arguments/output after an ordinary clean interruption.
```

Configuration fields are `mode`, exact `origin` (no query/path/credentials), model snapshot ID, `prompt_version`, prompt file SHA256 as `prompt_hash`, `catalog_version`, `catalog_hash`, `source_sha`, API contract identifier as `api_version`, `source_files` mapping repository paths to SHA256, and `mandatory_reserve` mapping future stage names to reserved outbound attempts. Source files must include every path in the runner’s `REQUIRED_SOURCES`: runner, adapter/scorer, taxonomy/manifest/validation coverage and cases, all server modules, both API routes, assistant contract, seed catalog and package/lock files. Add any additional candidate dependencies too. The full config plus state-fixture hash form `run_fingerprint`; each execution gets a separate `run_id`. `mandatory_cost_reserve_usd` optionally overrides the default planning reserve of $0.01 per reserved future attempt. This is a conservative local estimate, not a provider hard cap.

Live configuration also requires `deployment_proof: {origin, source_sha, artifact, sha256}`. The immutable Vercel artifact must contain matching `url`, `gitSource.sha`, a `dpl_` ID and `readyState: READY`; its bytes must match `sha256`. Local validation can explicitly use `kind: local_exact_source` with an artifact containing matching origin/source_sha/source_files. Such local evidence does not establish the deployed build. Current API responses directly verify session/generation/actor/role epoch/request/conversation/input revision/catalog, mode, model, prompt version and catalog version. **The present API does not attest its source SHA or prompt hash:** source identity is bound through the separately verified deployment artifact. `require_remote_attestation: true` additionally requires matching response `sourceCommit`, `promptHash` and `apiVersion` when that API contract is implemented.

Merchant state fixtures are required explicitly: a mapping of case IDs and/or `default` to N01 business state (`storeId`, proposal IDs/versions, saved daily budget, current/previous constraints and actual group summaries). Export these from the agreed synthetic scenario/SQLite state at I01. Case business context may override only allowed fields; proposalRevision/currentRevision map explicitly to the API version fields. The runner never invents group demand, procurement costs or saved budget from an oracle. E01's synthetic scenario context is evaluation input, not proof that a corresponding browser transaction exists.

`--bypass-file` reads a private `{secret: ...}` record or the single secret key in Vercel's `protectionBypass` map. The header is attached only to the configured exact origin. Redirects are blocked, including redirects to another origin. The secret never enters the URL, request JSON, output, checkpoint, trace or log. A non-HTTPS origin is accepted only on loopback, and fixture transport is loopback-only.

The shared default ledger is `artifacts/private/run-20260921/nl-budget.json`. It starts with **20 prior-call reserve, actual prior calls unknown**, and $1 prior-cost planning reserve (20 × $0.05); neither is claimed as observed usage. It separately counts known provider calls, unresolved possible calls, observed cost, and reserved/unknown cost. Every possible outbound attempt is durably charged before sending. Explicit `providerCalled:false` releases that attempt's call reserve; uncertain transport consumes a conservative slot. The ledger prevents this executor from exceeding 2,400 accounted calls including required future reserves or the $15 estimated soft stop. Calls made outside this runner must also be recorded by the coordinator; the ledger is not an account-wide provider limit.

Full baseline is 336 cases / 368 user turns / at most 1,104 attempts. Baseline config must reserve at least best validation276 + holdout276 + UX144 and a positive explicit G5/G6 reserve; actual additional UI turns can require more. The current stage's remaining turns also reserve three attempts each. Rate/timeout/transient errors use at most three attempts total per turn, including before resume. Auth/quota/model/configuration errors stop the run immediately. Failed responses, unknown usage and unsuccessful earlier turns remain in the observations. Unexpected provider mode still charges the observed live call, even when a fixture run expected otherwise.

`checkpoint.json`, `observations.jsonl`, `progress.json`, and `summary.json` are atomic, permission0600 files. The content-free progress/summary can be shared; content-bearing checkpoint/observations for holdout remain evaluator-only. A completed case is never called again on resume. Received successes and retry counts are journaled before continuation. If a process dies with an unresolved `pending` request, resume stops with `UNCERTAIN_PENDING_ATTEMPT_DO_NOT_REPLAY`; HTTP cannot promise exactly-once provider execution without evidence of that response. Do not erase the pending record to force a retry. A changed config, source, dataset or state fixture also blocks resume.

Holdout needs `--evaluator-holdout --frozen-best PATH`, live mode, private output under `artifacts/private`, and a frozen-best record matching model/source/prompt/catalog with two distinct validation run IDs. Include `validation_reports: [{path,sha256}, {path,sha256}]` for two actual live `stage_ready:true` reports on the same dataset/config; `validation_both_stage_ready` and `approved` must be true. Also supply `validation_binding: {config: {path,sha256}, state_fixtures: {path,sha256}}` for the actual validation inputs. The runner recomputes the reports’ fingerprint from those artifacts, requires the frozen public validation dataset, and matches every candidate identity field (including model and all source hashes) to the holdout candidate. Two reports from another candidate cannot authorize holdout. The shared ledger allows one run per protected dataset, with safe resume of that same run. This is a local evaluator workflow/access contract, not an OS identity or cryptographic authorization system. Never run holdout for tuning, and never copy its body into developer prompts.

A runner summary's `complete` means every input case has an observation, including failures. `quality_pass` remains `not_scored` and product gates remain `not_assessed`. Run the independent scorer with the same frozen coverage, run ID and fingerprint to obtain metrics; failed/missing cases remain in the denominator. Passing the HTTP runner does not establish browser consent, SQL transaction safety, UX or G5/G6.
