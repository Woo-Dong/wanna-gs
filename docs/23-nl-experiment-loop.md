# 자연어 이해·매핑 품질의 실험 루프

최초 구현 기준. 자연어 이해·검색·매핑 품질도 goal의 완료 기준에 포함한다. 개발용 nl-experiment 담당이 고객·경영주 에이전트의 개선안을 실험하고, 검증한 변경을 버전으로 관리해 배포한다. 앱 실행 중에는 코드나 DB 스키마를 수정하지 않는다.

## 역할과 준비

- 실험자: 실패 분석·가설·프롬프트/검색/데이터 구조 후보를 만든다.
- 독립 평가자: 21번 coverage/정답·분할·최종 holdout과 채점·회귀를 관리한다. 자기 후보를 승인하지 않는다.
- DBA/domain/UX 담당: 스키마·업무 의미·사용자 흐름 변화의 영향을 검토한다.
- 조정자: 실험 예산·비교·채택/보류/중단과 PR를 관리한다. 중요한 판단은 적합한 강한 모델을 우선한다.

기준선 전 각 런타임 역할에 대해 출시 최소 기준, 개선 목표, 회귀 금지 조건, 비교 데이터·반복수·의미 있는 개선 기준·호출 한도·시도 한도를 ADR과 [실험 기록](templates/nl-experiment.md)에 고정한다. 결과를 보고 합격선을 내려 성공으로 만들지 않는다.

## 실험 가능한 변경

1. 프롬프트의 역할/행동 지침, few-shot, 확인 질문, 스키마 설명.
2. query 정규화, 별칭/맛/용량/브랜드 필드, 검색 후보 수·정렬·정확/속성 결합.
3. 상품 데이터 구조·표현의 정규화, 출처 이력을 지키는 속성 보강·명백한 데이터 오류 정정.
4. 도구 입력/결과 요약·structured output 검증·확신 부족 시 후보/질문 분기.
5. 실제 계정에서 사용할 수 있는 앱 모델 비교. 개발용 Codex 모델 변경과 혼동하지 않는다.
6. 접근·비용·개선 근거가 있을 때의 선택 임베딩/Vector RAG.

거래/권한/동의·48시간 불변식 변경, 허구 SKU 생성, holdout 정답을 별칭에 복사, 예산 초과 유료 모델 구매는 후보가 될 수 없다. 스키마 변경이 필요하면 DBA 소유권·마이그레이션·기존 데이터 호환/복구·전체 영향 검사까지 포함한다. ‘프롬프트만 바꿨다’고 거래 결과 검증을 생략하지 않는다.

## 반복 흐름

1. 기준선: 현재 검증된 기준선의 catalog/search, 고객/경영주 intent/fields, 대화 적절성, 오류/지연·사용량을 같은 데이터/모드에서 측정한다.
2. 실패 분해: 검색 누락 / 후보는 있지만 오분류 / 모호함 미확인 / 대화 맥락 손실 / 스키마 위반 / 도구 오류 / 사실·데이터 결함으로 분류한다. 모델 문제와 업무 코드 버그를 구분한다.
3. 가설: 구체적인 실패 집합과 예상 개선을 정한다. 한 후보는 가능한 한 한 요인만 바꾸며 복합 변경은 이유와 ablation 계획을 기록한다.
4. 격리 후보: 작업 branch/config 버전에 변경하고 현재 최선 버전 버전을 보존한다. 모든 실험을 즉시 서비스 기본값으로 적용하지 않는다.
5. 빠른 선별: 변경 범주의 dev 표본·고정 regression·서버 불변식을 검증한다. 여기서 실패한 후보는 비싼 전체 live 평가로 보내지 않는다.
6. 후보 비교: 유효 후보를 같은 validation 사례·모델 설정·반복수로 비교한다. paired 결과·범주별 분모·잘못된 확정/과도한 거절·지연/비용을 보고한다. 무작위 모델 변동을 개선으로 단정하지 않는다.
7. 독립 채택: 중대한 회귀가 없고 사전 기준을 만족한 후보만 평가자와 관련 역할이 검토한다. 버전/ADR/실험 근거를 PR에 연결하고 관련 G1~G4/eval을 통과한 뒤 최선 버전으로 승격한다.
8. 최종 확인: 선정된 후보에 독립 holdout과 두 UX 브라우저 시나리오를 실행한다. 후속 튜닝에 노출된 holdout은 21번의 교체 규칙을 따른다.
9. 배포 확인: 실제 제출 모델/config/검색/데이터가 선정 버전인지 확인하고 G6에서 대표 live 입력을 재검증한다.

실패 후보도 버전·가설·결과·기각 근거를 남긴다. 비교 가능한 기준선이 없는 ‘좋아 보인다’는 판단만으로 개선 완료를 선언하지 않는다. 새 테스트/데이터가 버그를 드러냈다면 과거 결과와 새 기준 결과를 따로 보존한다.

## 시도 한도와 개선 포기 정책

다음은 실행용 기본안이며 시작 시 ADR로 채택/조정한다. 명시적인 goal token_budget은 아니다.

- 고객/경영주 각각 기준선 이후 최대 6개 후보, 전체 최대 12개 후보. 하나의 후보 재실행을 무제한으로 허용하지 않는다.
- 같은 역할에서 연속 3개 후보가 사전 개선 기준을 충족하지 못하면 추가 최적화를 조기 중단한다.
- 반복수·표본·API 호출량은 실제 잔량에 맞춰 사전 계획한다. quota/권한 장애는 품질 실패와 구분한다. 한도에 도달한 뒤 task 이름을 바꿔 같은 실험을 다시 시작하지 않는다.
- 더 나은 새 가설이 있어도 이번 목표의 한도를 자동 연장하지 않는다. 다음 과제로 기록한다. 사용자 새 지시가 있으면 별도 범위를 정한다.

중단 결과:

| 상황 | 처리 |
|---|---|
| 개선 목표 달성·필수 기준 통과 | 후보 채택, 최종 회귀/holdout/UX/배포 검증 |
| 한도/정체, 기존 최선 버전은 출시 최소 기준 충족 | 추가 개선 포기, 최선 버전 유지, 알려진 실패 범주·시도·한계·다음 가설 기록. 다른 기능 완성과 배포 계속 |
| 후보 악화·새 회귀 | 후보 기각, 이전 최선 버전 복귀, 필요한 회귀 확인 |
| 허구 SKU/동의/권한/수량 등 필수 오류 | 실험 포기로 면제 불가. 버그 복구/보수적인 정상 실패 경로/원인 수정 후 필수 기준 재검증 |
| 모든 버전이 출시 최소 기준 미달 | 추가 선택 최적화는 중단할 수 있으나 제품 goal 완료 불가. 필수 결함/미달 결과를 정확히 보고하고 가능한 구현·복구 계속 |
| 모델 접근/무료 잔량 없음 | external-blocked 또는 not_run, fixture를 live 품질 증거로 바꾸지 않음 |

시도 한도에 도달하면 추가 자연어 최적화를 종료하고 나머지 개발을 계속한다. 품질은 사전에 정한 평가 범위와 출시 최소 기준으로 판단한다. 최종 보고서는 achieved / plateau / budget-stop / rejected-regression / external-blocked를 구별하며 수치와 증거를 연결한다.

## 기록과 회귀 방지

실험 ID, 가설·실패 case ID, parent/baseline/candidate/best 버전, context/CORE/ADR, 데이터 split hash, 프롬프트·model·schema/seed/search 설정, 실행 명령·run ID·정답 판정, 범주별 전후 결과·분모·latency/usage, 채택/기각/중단, PR/rollback을 남긴다. 새 실험은 이전 실패/기각 원인을 먼저 읽고 같은 접근을 근거 없이 반복하지 않는다.

후보용 상세 로그는 산출물로, 결론과 manifest는 repo 문서로 관리한다. holdout 내용이 실험자 프롬프트나 일반 공개 작업 계약으로 새지 않게 한다. 실험 지침/도구는 [wanna-gs-nl-experiment](../.agents/skills/wanna-gs-nl-experiment/SKILL.md)에 있다. 실험 실행기와 평가셋은 아직 구현하지 않았으며 성능도 측정 전이다.

## 참고

[OpenAI evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)는 목표·데이터·지표·비교·지속 검증을 정의하는 참고이며, 위 한도/역할/채택 규칙은 원하GS 자체 설계다(2026-09-20 확인). 기존 앱 모델 호출과 로컬 eval 실행기로 구성할 수 있고 별도 유료 Evals 계정을 필수로 하지 않는다.

## 초기 데이터와 재조사 연결

[24번](24-market-research-and-scenario-design.md)의 goal 실행 당시 조사를 기준선 전에 수행한다. 과거 대화에서 언급된 특정 유행 상품이나 극단 사례만 반복한 평가셋을 만들지 않는다. 실제 니즈에서 도출한 일반/모호/예외 상황을 균형 있게 구성하고 research/scenario/case ID를 유지한다. 실패가 자료·상품 속성·사용 상황의 오해에서 비롯되면 해당 범위를 새로 조사한 뒤 데이터 수정 후보를 만든다. 새 사실 확인과 성능 비교를 구분하고, 평가셋을 바꾸면 이전 점수와 그대로 비교하지 않는다. 조사 범위 확대만으로 실험 시도 한도를 초기화하지 않는다.

## Gateway 잔량과 Gemini 전환

[25번](25-model-budget-and-fallback.md)에 따라 평가 묶음 전후 잔량을 확인하고 최종 검증·데모 예산을 남긴다. Gateway가 부족하면 Gemini 직접 호출을 사용한다. 모델이 바뀌면 이전 기준선 점수와 섞지 않고 같은 검증 데이터·조건에서 새 결과를 기록한다. 전환을 위한 품질 비교도 기존 후보 한도에 포함하며 중단 횟수를 초기화하지 않는다. 이미 검증한 후보로의 단순 전환은 새 최적화 후보로 세지 않되 영향받는 회귀 검사와 G5/G6는 수행한다. 최종 평가셋은 기존 보호·교체 규칙을 따른다.

## 서비스 가치와 편의성 회귀

D-37·CORE-25·AC-31과 [27번 VAL-01~08](27-service-values-and-guardrails.md)을 적용한다. 정확 검색·대체 후보·미충족 분류를 각각 평가하고 상품 추천 개선으로 기존 정상 경로 실패를 상쇄하지 않는다. 고객의 질문/필수 조작/완료 시간과 경영주의 승인/화면 이동/중복 알림·자동발주 정상 성공을 같은 업무량에서 비교한다. 기준선 전에 수치 문턱·허용폭을 ADR로 정하고 결과에 맞춰 낮추지 않는다.

동의 없는 대체·가짜 SKU·수요 오염·초과/중복 발주·권한 침해는 허용 0건이다. API 오류를 미식별 데이터로 넣거나 모든 요청을 보류하는 결과도 실패로 잡는다. 추가 최적화 종료는 필수 기준 면제가 아니며 보호 holdout의 공개 예시 오염을 검사한다.
