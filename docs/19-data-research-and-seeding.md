# 약 200개 상품·실제 점포 기반 데모 데이터

최초 구현 기준. 시장 조사, 약 200개 상품·점포 데이터, DB는 아직 준비하지 않았다. goal 초기에 실제 사용자 필요·상품 탐색/재고 확인 어려움·시장/트렌드 근거를 먼저 조사하고, 그 결과에서 상품 목록·시나리오·eval 자료를 함께 파생한다. 최소 스키마 준비 뒤 검증·삽입하고 기능 단위부터 최종 평가까지 공통 기반으로 사용한다.

## 조사에서 시작하는 데이터 원칙

초기 데이터는 카테고리 숫자를 먼저 채우는 방식으로 만들지 않는다. [시장 조사·시나리오 설계](24-market-research-and-scenario-design.md)의 조사 사례에 실제로 보고된 필요와 탐색/재고 어려움, 상품 사실, 시점이 있는 시장·트렌드 근거를 기록한 뒤 상품 후보와 실패/성공 시나리오를 도출한다. 확인된 사실과 설계용 합성 확장은 다음처럼 분리한다.

- 출처마다 URL·발행일·확인일·근거 범위·원문/2차 보도 여부를 남긴다. 상품명·구성·출시 같은 `product_evidence`와 품절·관심·유행 같은 `trend_evidence`는 각각 별도 신뢰도로 판정한다.
- 보도된 행동을 요약할 수는 있지만 출처에 없는 고객·경영주, 인용문, 구매 이력이나 점포 관계를 만들지 않는다. 새 발화와 여정은 `synthetic_expansion`으로 표시하며 실제 인터뷰 인용으로 표현하지 않는다.
- `research_case_id → catalog_candidate_id/scenario_id → eval_case_id`를 연결하되 조사 사례, 실행 시나리오, 평가 case는 서로 다른 산출물로 유지한다. 하나의 기사 문장을 그대로 seed·few-shot·holdout에 복사하지 않는다.
- 넓은 시장 인기, 전국 재고, 특정 점포 취급을 제한된 기사나 발표 한 건에서 추론하지 않는다. 근거가 부족하면 `unverified` 또는 `synthetic_scenario`로 둔다.
- 상품 목록와 대표 시나리오를 기능 개발 전에 버전 고정한다. eval은 같은 위험 분류와 출처·변경 이력을 사용하되 dev/validation/final holdout의 정확한 발화는 분리한다.

이 초기 공통 조사 뒤에도 각 기능의 G0에서 해당 사용자 흐름과 공식 기술 근거를 적시에 확인한다. 실패가 오래된 상품/트렌드/기술 가정을 가리킬 때 관련 조사 사례만 갱신하고 출처·변경 이력으로 영향받는 데이터·테스트를 다시 검증한다. 조사 범위와 준비 상태·중단 기준은 24번을 따른다.

## 데이터 구성

목표는 약 200개 독립 SKU다. 같은 상품의 맛·용량 차이는 실제 구분되는 후보일 때만 별도 SKU로 만들고 단순 복제로 개수를 채우지 않는다. 초기 배분안은 아래와 같으며 데이터 담당이 출처·식별 난이도를 검토해 ADR로 조정할 수 있다.

| 카테고리 | 목표 SKU |
|---|---:|
| 도시락·김밥·주먹밥 | 25 |
| 샌드위치·버거·빵 | 25 |
| 컵라면·면류 | 25 |
| 스낵·과자·초콜릿 | 30 |
| 디저트·아이스크림 | 25 |
| 음료·생수·차 | 30 |
| 커피·우유·요거트 | 20 |
| 간편조리·냉동식·생활 소품 | 20 |
| 합계 | 200 |

숫자와 카테고리는 구현 기본안이며 사용자 확정 상한이 아니다. 주류·담배·의약품 등 별도 성인/법적 구매 흐름을 필요로 하는 품목을 이번 데모를 복잡하게 만드는 기본 데이터로 추가하지 않는다.

- 널리 알려진 상품명 또는 현실적인 합성 상품명을 사용한다. 실제 출처가 없는 것은 합성으로 표시한다.
- 최근 관심/신상품은 목표 20~30개를 데이터셋의 일부로 포함한다. goal 실행 시 최근 자료를 다시 찾아 날짜와 근거를 남긴다. 신상품 발표가 곧 인기/판매량 증거는 아니다.
- 비슷한 이름·맛·용량·브랜드, 줄임말, 복수 후보, 취급 안 함·공급 제한·종료 등 식별/발주를 시험할 분포를 만든다.
- 점포는 한 지역의 8~12곳을 기본으로 조사한다. 지역은 에이전트가 시연에 적합한 밀집 지역을 정하고 기록한다. 실제 GS25 점포명·주소·위치를 가능한 공개 근거로 확인한다.
- 고객은 이름·성별·나이·직업·실제 구매 이력이 없는 약 20개의 합성 테스트 계정(`DEMO-CUSTOMER-*`)으로 둔다. 고객은 요청마다 한 점포를 고르며 특정 실제 점포의 실제 고객이라고 표현하지 않는다.
- 경영주 역할은 조사·채택한 8~12개 점포마다 합성 계정 하나(`DEMO-MERCHANT-<store_id>`)를 1:1로 매핑한다. 해당 계정은 자기 점포 범위만 조회·변경한다. 실제 점포와 실제 점주 관계를 뜻하지 않으며 본부 역할을 추가하지 않는다.
- 200 SKU가 모든 점포에 있다는 밀집 행렬을 만들지 않는다. 초기 기본안은 전체 점포×SKU 조합의 약 20~35%만 결정적으로 활성화하고, 핵심 정상 시연 상품은 둘 이상의 점포, 희소/트렌드 상품은 1~3개 점포에만 두는 것이다. 비율은 PLAN-READY ADR로 조정할 수 있다. 이 availability·가격·재고·공급 조건은 전부 simulated이며 실제 점포 취급 주장에 쓰지 않는다.

## 사실과 모의 값 분리

| 필드 | 기준 |
|---|---|
| product_id/store_id/actor_id | `DEMO-*` namespace의 고정 내부 ID. 실제 GS 상품코드/POS ID라고 주장하지 않음 |
| 상품명·브랜드·용량 | reference_verified 또는 synthetic, 출처/확인일 |
| trend_tag | 발표/판매/관심 근거 종류와 기간. 근거 부족은 synthetic_scenario 또는 unverified |
| 판매가·매입가·재고·발주 조건·공급일 | 기본 simulated, 실제 가격/취급/입고 보증 아님 |
| 점포명·주소 | 공개 원문 출처·확인일, 최신 운영 여부를 확인하지 못했다면 별도 표시 |
| latitude/longitude | WGS84, 순서/범위·주소 정합성 검증, coordinate_source/accuracy 기록 |
| 고객·경영주 | synthetic test account only, 실제 사람의 프로필·인용·구매 이력이나 실제 점포와의 관계를 만들지 않음 |

권장 출처 이력: `source_url`, `source_type`, `published_at`, `checked_at`, `evidence_scope`, `product_confidence`, `trend_confidence`, `field_origin`, `license_or_usage_note`, `research_version`, `catalog_version`, `scenario_version`, `eval_version`. 출처 시각은 가져온 시각과 발표/사건 시각을 구분한다. 실제 점포 위치를 쓴다고 그 점포에 모의 상품 재고가 있다는 뜻이 아니다. 화면에는 ‘점포 위치 참고 / 상품·재고·결제는 데모’를 표시한다.

## 연구·생성·DB 삽입 순서

1. 사용자 필요·검색/재고 어려움·상품군·트렌드 주장·지도 대상 지역의 조사 질문과 source 기준을 계획한다. 평가 담당이 누락 범주와 확증 편향을 독립 검토한다.
2. 공식 GS25 상품/점포 안내, GS리테일 보도자료, 제조사 상품정보를 우선하고 신뢰할 수 있는 기사·조사로 사용자 어려움과 시점이 있는 관심 신호를 보완한다. 최근 인기 주장은 상품 존재와 별도로 확인한다.
3. source record와 조사 사례를 작성하고 `product_confidence`와 `trend_confidence`를 분리 판정한다. 필요한 소량만 수집·정규화하며 보호된 내부 API나 무분별한 크롤링을 필수로 만들지 않는다.
4. 조사 사례에서 상품 목록 candidate, 성공·모호·미식별·품절/공급 제한 시나리오, 고객/경영주 eval family를 파생한다. 파생 발화는 `synthetic_expansion`으로 표시하고 출처의 실제 발화로 표현하지 않는다.
5. `data/research.*`, `catalog.*`, `stores.*`, `actors.*`, `availability.*`, `scenarios.*`, `eval-manifest.*`, `provenance.*` 같은 버전 관리 파일을 생성한다. 이름은 구현자가 정하며 현재 존재하지 않는다.
6. 생성 담당과 다른 data reviewer가 출처 사실·중복·정답 후보·좌표·희소 availability와 시나리오를 확인한다. nl-evaluator는 의미/패러프레이즈 family 단위 split을 만들고 최종 holdout을 독립적으로 구성·보호한다. 생성자 스스로 붙인 real/popular 라벨을 증거로 인정하지 않는다.
7. DBA가 마이그레이션과 재현 가능한 seed importer를 구현한다. 실제 테스트 DB에 dry-run/rollback과 반복 seed 안전성을 검증한 뒤 데모 세션에 삽입한다.
8. 약 200개 목록, 8~12개 점포와 역할 매핑, 희소 availability, 고객/경영주 세션이 조회되는 최소 화면/API를 검증한다. 기능 단위·통합·UX·최종 eval은 사용한 `research/catalog/scenario/eval` 버전과 case ID를 기록한다.

최소 스키마/seed CLI/검사 코드는 이 데이터 삽입에 앞서 필요하다. ‘모든 코드를 쓰기 전에 DB 삽입’ 순환을 만들지 않는다. 조사/생성과 skeleton 설계는 독립적으로 병렬 진행할 수 있다.

## seed 품질과 재현성

- SKU ID/정규화 이름+용량 중복·카테고리 다양성·필수 필드·양의 가격·FK·세션 소유권 검사.
- 상품 마스터는 공유 읽기 전용, 가변 가격/공급/정책·거래는 세션별 격리.
- 시나리오 생성은 domain factory를 사용해 가능한 상태를 만든다. 불가능한 상태는 negative fixture에만 격리한다.
- 수요/진행 발주/확보/배정/모의 결제/예약/입고/수령/잔량 수량과 시각의 불변식 검사.
- source 파일 checksum·research/catalog/scenario/eval/seed 버전·정책 버전·clock·생성 설정으로 재현. 같은 seed 재실행이 이중 요청/발주를 만들면 실패.
- 핵심 성공 데모, 공급 부족·예산 미달·미식별·결제 실패·48시간 경계 시나리오를 preset으로 제공.
- 같은 의미·의도·상품/상태 조합의 패러프레이즈 family는 한 split에만 둔다. 최종 평가 발화는 카탈로그 별칭, 프롬프트 예시, dev regression에 그대로 역주입하지 않는다. 공개 상품 마스터와 독립적으로 큐레이션한 보호 holdout 질의·정답을 구분한다.

## 실제 위치와 지도

실제 점포명·주소·좌표를 확인해 정적 seed로 저장하고 지도 marker/점포 목록에서 동일 ID로 선택하게 하는 것이 기본안이다. 자동 최근접 추천에 사용할 고객 위치는 가상 시연 위치를 기본으로 두며 실제 GPS 권한을 필수로 만들지 않는다. 직선거리는 도보 시간으로 표시하지 않는다.

공개 좌표/주소 자료를 우선 사용한다. 좌표가 없으면 허용된 geocoding을 준비 단계에서 소량 수행·캐시하거나 다른 검증 가능한 점포를 선택한다. 확인되지 않은 좌표를 실제값으로 꾸미지 않는다. 외부 접근이 전혀 없어 요구한 실제 점포 근거를 확보하지 못하면 그 데이터 항목은 미검증이며 전체 데이터 요구 완료라고 하지 않는다. 나머지 합성 데이터/기능 작업은 계속한다.

새 유료 지도 계정을 기본 의존성으로 추가하지 않는다. 지도 renderer/provider는 preflight에서 접근·표기·사용 조건을 확인해 선택한다. 지도 타일/SDK가 실패하면 점포 목록으로 핵심 요청을 계속하고 오류를 명시하되 지도 검증 자체를 성공으로 바꾸지 않는다. 반복 CI는 지도 제3자 응답을 fixture로 격리하고 앱 marker/선택/오류 동작을 검사하며 실제 지도 연결은 허용 범위의 소수 기본 동작 검사로 따로 기록한다.

## 자료 조사 출발점과 한계

2026-09-20 확인: [GS25 브랜드](https://www.gsretail.com/brand/gs25)와 [GS리테일 보도자료 진입점](https://www.gsretail.com/gsretail/ko/media/news-report)은 조사 후보이다. 이 시점의 텍스트 도구에서는 동적 페이지 내용이 충분히 추출되지 않았으므로 실제 상품 200개/점포 좌표를 확보한 출처로 취급하지 않는다. goal 실행 시 브라우저 등으로 개별 근거를 확인한다.

공개 지도도 무제한 무료 리소스가 아니다. [OSM tile 정책](https://operations.osmfoundation.org/policies/tiles/)은 bulk/prefetch 사용을 제한하므로 CI가 지도 전역을 반복 순회하게 하지 않는다. [Nominatim 정책](https://operations.osmfoundation.org/policies/nominatim/)은 낮은 호출량·식별 가능한 요청·캐시 등을 요구한다. 사용하는 provider의 당시 조건을 확인하고 따라야 한다. 이 문서는 특정 provider 사용 확정이 아니다.

## 최소 seed

[ADR-001](decisions/ADR-001-minimal-seed-development.md)에 따라 자료 계약을 먼저 정하고 전체 수집과 기반 개발을 나눈다. D04A는 위험 범주에 필요한 최소 상품·점포·역할·상태를 같은 스키마와 공통 importer로 만든다. 임시 위치는 합성으로 표시한다. 최소 seed는 실제 DB 무결성·반복 삽입·격리와 독립 검토를 통과해야 한다.

전체 상품·검증 점포·평가 자료는 D04B/D05에서 완성한다. 원본 출처와 holdout 분리 요구는 유지한다. 전체 seed 전환 후 검색·점포·권한·reset·브라우저 검사의 영향을 확인하고 N01/Q01/Q02/G5를 새 버전에서 실행한다. 초기 seed 성공을 전체 데이터 완료로 보고하지 않는다.
