# 위임된 자율 정책 결정과 최종 빈틈 감사

상태: 최초 구현 기준. 사용자는 해커톤 세부 정책을 매번 묻지 말고 기존 정의와 서비스 철학 안에서 에이전트가 결정·기록·복수 검토·검증하도록 위임했다. 미정이라는 이유만으로 사람 답변을 기다리지 않는다. 이전 문서의 ‘U: 사용자 판단/의논/승인 대기’는 이 범위에서 아래 절차로 대체한다.

## 목적과 판단 순서

원하GS의 가치는 원하는 상품을 찾기 어려운 고객의 수요를 보이게 하고, 경영주의 업무를 늘리지 않으면서 근거 있는 보수적 발주와 신뢰할 수 있는 픽업으로 연결하는 것이다. 해커톤에서는 이 닫힌 흐름과 설명 가능한 예외를 재현하는 데 집중한다.

의사결정 우선순위:

1. 최신 사용자 명시 결정과 범위/금지사항.
2. 수량·동의·권한·시간·데모 격리 불변식과 필수 인수 기준.
3. 고객이 예상 가능한 동작, 경영주의 적은 개입, 보수적인 발주.
4. 데모에서 재현·설명·테스트하기 쉬운 최소 정책.
5. 향후 변경 가능성과 구현 비용. 실제 운영 수준 기능을 지금 추가할 이유로 쓰지 않는다.

선택한 최소 정책을 일관되게 구현한다. 예외가 발생하면 실제 상태와 실패 원인을 그대로 보고한다.

결정 전에 [DECISION_INDEX](DECISION_INDEX.md)에서 현재 유효 정책과 `effective_scope`, `depends_on`, `supersedes`, `conflicts_with`를 확인한다. 인덱스에 없는 과거 결정을 없다고 단정하지 않고 원문/코드/config를 대조한다. 채택 뒤에는 decision→Context Manifest→schema/seed/scenario/eval/prompt/config→task/PR/test의 출처·변경 이력을 기록한다. 작업 branch 범위의 결정을 통합 전 전역 정책으로 표시하지 않는다.

## 자율 결정 가능한 범위

기간·횟수·수량 상한, 부분 배정/대기열 세부 규칙, 대기 동의 만료, 취소 허용 단계, 결제 실패의 모의 재시도/배정 해제, 매입가 예산 기간, 묶음 실패 처리, 데모 위치/역할/세션·표현·시연 데이터·평가 문턱 등 미지정 사항을 결정할 수 있다. O/R 항목의 위험을 검토하고 위임 범위에서 결정한다.

예를 들어 O-03은 ‘대기 요청의 동의 유효기간’을 정하고 만료 경계를 구현할 수 있다. 그러나 이미 확정된 ‘픽업 가능 알림 생성부터 정확히 48시간’을 더 짧게 바꾸는 것은 이 위임에 포함되지 않는다. 숫자는 실제 GS 정책으로 주장하지 않고 버전이 있는 데모 설정으로 둔다.

비즈니스 정책의 원본은 결정 기록과 서버 설정에 둔다. FE·BE·seed·모델 프롬프트에 서로 다른 숫자를 하드코딩하지 않는다. 주말·신선도·환불 같은 실제 운영 복잡성이 필요하지 않으면 지원 범위를 명시적으로 단순화하고 범위 밖 입력을 안정적으로 거절한다.

## 실행 시점 조사와 현실적인 시나리오

계획 문서의 과거 조사만으로 현재 사실을 고정하지 않는다. goal 시작 때 시장/사용자 필요·최근 관심 상품·공개 점포 근거를 담당 agent가 직접 조사하고, 각 기능 G0 전에는 그 기능의 고객/경영주 필요, UX·오류 복구, 기술 통합과 테스트 방식에 필요한 최신 공식 자료를 확인한다. 조사 결과로 선택지와 반례를 보완하고, 프로젝트 요구에 맞는 정책을 결정한다.

- 주장마다 출처 URL, 발행/사건/확인 시각, 사실/추론/가설, 영향을 받는 설계·데이터·테스트를 연결한다.
- 실제 관측 표현은 `evidence_backed`, 평가 다양성을 위해 만든 표현은 `synthetic_utterance`로 구분한다. 합성 발화를 실제 고객/경영주 조사 결과라고 쓰지 않는다.
- `민음사 빵`은 24번에 과거 출처 확인이 있는 예시이며 goal 실행 당시의 최신성·seed 채택은 미검증인 후보 하나다. goal 실행 당시 직접 확인하며, 근거가 없으면 실제/인기 SKU나 전체 카탈로그의 고정 축으로 만들지 않고 미식별·모호성 시나리오로 사용할 수 있다.
- 소수 사례의 이름을 바꿔 200개 이상 상품이나 평가셋을 채우지 않는다. 조사된 필요·카테고리·식별 난이도·오류/회복 분포에서 다양한 시나리오 묶음를 도출한다.
- 스키마 확정 전에 조사 claim/시나리오/eval 요구를 설계하고, schema/migration 뒤 재현 가능한 seed와 정답 데이터를 생성한다. 같은 family의 패러프레이즈는 dev/validation/holdout 사이에 흩뜨리지 않는다.
- 외부 근거가 stale이거나 통합 실패가 조사 전제를 깨면 관련 조사와 결정만 갱신한다. 이미 답한 넓은 시장 질문을 무한 반복하거나 조사로 범위를 키우지 않는다.

## 유지해야 할 경계

- 프로토타입·합성/모의 데이터·실제 GS 연동 없음·실제 청구 없음.
- 고객 자연어 입력, 실제 존재 후보 확인, 한 점포 요청, 요청 시 자동 구매 동의.
- 경영주 승인 또는 사전 승인된 보수적 자동발주 정책, 요청 초과 자동발주 금지.
- 동일 점포·상품 안에서 요청 접수 순서 유지. LLM은 해석·제안하고 수량·금액·권한·상태의 최종 검증은 서버 코드가 담당.
- 공급 확보와 입고를 구분, 실제 입고 전 픽업 가능 표시 금지, 정확히 48시간.
- 본부 화면/기능·사진·링크 입력·레시피 등 제외 범위 유지.
- Vercel 제출, live 모델과 fixture의 정직한 구분, 필수 테스트와 상태 불변식 유지.

개발 과정의 인간 결정 생략은 앱 사용자의 동의를 대체하지 않는다. 고객 SKU 확인·자동 구매 동의·경영주의 발주 정책 활성/승인을 에이전트가 몰래 생략하거나 동의한 것으로 만들지 않는다. 앱 대화에서 상품을 구분하기 위한 고객 질문도 여전히 필요할 수 있다.

## 경량 결정 프로토콜

정책 공백을 발견하면 제품 구현자가 즉시 다음을 수행한다. 관련 없는 작업은 병렬로 계속한다.

1. 발견/분류: O/R/CORE/테스트 실패와 연결하고 `DECISION_INDEX` 및 실제 config에서 이미 정해진 규칙인지 확인한다. 외부 접근 장애, stale 조사, 제품 미정을 구분한다.
2. 근거: 해당 결정에 필요한 실행 시점 조사와 기존 사용자/기술 증거를 모으고 claim→설계/데이터/테스트 매핑을 만든다. 관련 없는 광범위한 조사는 생략한다.
3. 초안: 합리적인 선택지 1~3개를 비교하고 가장 단순한 권장안을 낸다. 기간/상한에는 시작·종료·경계값·예외를 적는다. 필요한 규모는 짧은 한 문단+표면 계약이면 충분하다.
4. 기록: `docs/decisions/ADR-<번호>-<주제>.md`에 [결정 양식](templates/decision-record.md)으로 `proposed`를 남기고 `DECISION_INDEX`에 ID·상태·effective scope·의존/충돌·담당을 등록한다. 영향이 같은 사소한 설정은 한 ADR에 묶는다.
5. 복수 독립 검토: 제안자 외 서로 다른 서브 에이전트 두 명이 검토한다. 한 명은 고객/경영주 가치·사용자 정의·범위, 다른 한 명은 상태/수량/중복·복구·테스트 가능성을 본다. 가능한 한 상대 결론을 보기 전에 검토 의견을 작성한다. 슬롯이 적으면 순차 배정한다.
6. 결정: 조정자가 증거와 두 검토를 확인하고 불변식 충돌이 없으며 중대한 반례가 해결되면 `adopted`로 채택한다. `authority: user-delegated`로 표시하며 사용자 직접 확정이라고 쓰지 않는다. 단순 다수결로 불변식을 무시하지 않는다.
7. 반영/검증: 관련 결정 원장·업무/상태/API·설정·UI 안내·schema/seed/scenario/eval/prompt·테스트 기대값을 같은 작업에서 갱신한다. Context Manifest와 영향 소비자에게 새 버전을 알리고, 적어도 정상·경계·실패와 영향받는 통합을 확인해 `verified`와 PR/test 출처·변경 이력을 기록한다.
8. 변경 관리: 재검증에서 모순이 나오면 새 버전/후속 ADR로 수정하고 이전 결정을 `superseded`로 남긴다. 영향받는 증거를 무효화하고 해당 부모 게이트를 다시 실행한다. 기각 대안과 실패 반례를 지우지 않는다.

기술적 오타·명확한 버그 수정까지 정책 위원회에 보내지 않는다. 기존 정책 의미를 바꾸지 않는 수정은 14/15번 개발·복구 루프로 처리한다. 기능별 G0의 제한된 실행 시점 조사는 수행하되, 그 근거는 프로젝트의 사용자 정의나 실제 GS 운영 사실을 대신하지 않는다. 같은 근거로 이미 답한 사소한 설정마다 새 검색을 반복하지 않는다.

## 이견과 반복 한도

통상 초안 검토와 보완 검토 2회 안에 결정한다. 검토자가 단순 취향 차이로 이견이면 조정자가 불변식을 모두 만족하는 더 단순하고 보수적인 안을 선택하고 소수 의견을 남긴다. 중대한 반례가 해결되지 않으면 상태/지원 범위를 축소해 유효한 대안을 검증한다. 이미 확정된 필수 기능 자체를 삭제하는 방식은 허용하지 않는다.

여러 에이전트의 찬성 수가 코드 실행 결과를 대체하지 않는다. 평가셋 실패를 보고 합격선을 낮추거나 기대값을 현재 버그에 맞추는 것은 정책 결정이 아니다. 품질 문턱은 평가 결과를 보기 전에 합리적 데모 목표로 고정하며, 재설정이 필요하면 원래 기준 결과와 근거·독립 검토를 보존한다. 사용자 확정 기준은 바꾸지 않는다.

진행 가능한 대안이 전혀 없이 사용자 확정 요구끼리 충돌하거나, 실제 인증·조직 권한·유료 한도·파괴적 데이터 작업이 막는 경우만 외부 결정/행동 필요 항목으로 올린다. 그 경우에도 시도/근거/다음 조건을 남기고 독립 작업을 계속한다. 이는 매번 정책 승인을 구하는 절차가 아니다. 목표 상태는 실제 도구 계약을 따른다.

## 통합할 때마다 빈틈 찾기

각 G3/G4 통합과 G5 최종 감사에서 단위 기능의 정상 결과보다 경계 사이 누락을 본다.

| 검사 축 | 대표 질문 |
|---|---|
| 시간 | 기산점·정각·기한 초과·늦은 응답·시계 이동·동의 만료와 수령 기한 충돌은? |
| 수량 | 부분/전량·FIFO·공급 잔량·취소·결제 실패 후 수량 보존과 중복발주 방지는? |
| 권한/동의 | 가격·점포·수량 변화 때 동의가 유효한가? 다른 역할/세션이 변경할 수 있나? |
| 상태/재시도 | timeout은 실패인가 결과 미확인인가? 이벤트 역전·중복·부분 성공에서 재개 가능한가? |
| 경영주 경험 | 예외마다 새 건별 승인을 요구하지 않는가? 제안과 실제 실행을 구분하는가? |
| 데모 범위 | 지원하지 않는 현실 정책은 명시했는가? 기능 추가로 핵심 시연을 늦추지 않는가? |

공백을 발견하면 ADR→두 검토→채택→구현/테스트를 같은 목표 안에서 진행한다. 단순 모델 의견은 후보 반례이며, 구체적인 입력과 기대값으로 재현할 수 있을 때 수정 작업으로 승격한다.

## 최종 감사와 끝내는 조건

‘구현 후 최종 통합 감사’도 goal의 일부다. 코드 작성이 끝났다고 먼저 goal 완료로 바꾸고 테스트를 나중 작업으로 미루지 않는다.

- 제품 원칙 검토자와 실패/통합 검토자가 독립적으로 13번 목록, 적용 ADR, 실제 G4/G5 결과를 살펴 누락된 사용자 행동과 경계 반례를 제시한다.
- 각 항목은 `채택+검증`, `범위 내 단순화+검증`, `현재 제외+이유`, `외부 확인 완료/실제 차단`으로 처분한다. 56개가 모두 새 기능 56개를 뜻하지 않는다.
- 필수 정상/실패 흐름과 불변식에 영향을 주는 발견은 해결하고 영향 테스트 및 검토를 다시 한다. 범위 밖 개선 제안은 후속 과제로 남긴다.
- 두 검토자의 중대한 미해결 반례가 없고, 필수 정책이 추적되고, 적용 G5/G6가 실제 통과하면 완료한다. ‘완벽할 때까지’ 무한 연구하거나 추가 기능을 계속 늘리지 않는다.

## 원장과 효력

02번은 사용자 확정과 주요 위임 결정의 원장, [DECISION_INDEX](DECISION_INDEX.md)는 현재 유효 상태·효력 범위·대체/충돌·출처·변경 이력을 찾는 운영 인덱스, 개별 ADR은 세부 정책의 권위 있는 기록, 설정/코드는 실행, 테스트는 검증이다. 인덱스 빈 행이나 proposed ADR은 채택 증거가 아니다. O/R 권장안은 출발점이며 이번 문서 갱신만으로 모두 채택된 것은 아니다. 실행 목표가 필요한 정책을 골라 위 절차로 결정한다. 최신 사용자가 해당 내용을 바꾸면 사용자 지시를 우선하고 ADR·인덱스·Context Manifest·구현·테스트를 갱신한다.

관련 정책은 수량/FIFO, 동의/취소, 자동발주, 시연/세션처럼 영향이 같은 묶음별 ADR로 검토할 수 있다. 묶음 안의 개별 O/R 기대값과 두 독립 관점을 생략하지 않으며 정확히 4개 문서로 제한하지 않는다.

## 목적 보존과 정책 변경 구분

[card.md](../card.md)는 관련 CORE·원장·유효 ADR을 찾고 수정 전후 사용자 결과를 확인하는 작업 안내다. 새로운 정책 권위가 아니며 충돌하면 최신 사용자 지시와 원장을 기준으로 관련 요약을 고친다. 세부 정책 변경은 기존 ADR 절차로 처리한다. 단순 코드 수정·경로 정리·문체 수정마다 두 정책 검토를 새로 요구하지 않는다. 테스트 기대값을 바꾸려면 독립 검증자가 원장·ADR의 기대 동작과 대조한다.
