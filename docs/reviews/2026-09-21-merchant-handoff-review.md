# 경영주 팀원 자료 비교 검토

현재 실행 기준: D-44의 한 탭 브라우저 SQLite와 D-45의 OpenAI API 직접 호출이다. 아래 과거 Neon/PostgreSQL·Gateway/Gemini·서버 거래/종료 후 실행 제안은 현행 설정이나 필수 검증이 아니다. 제품 후보의 미채택 상태는 그대로 유지한다.

검토일: 2026-09-21. **상태: D-41/42 두 기준 반영, 나머지 기능은 사용자 판단 대기.** 사용자 요청에 따라 자료를 읽고 반영 후보를 정리했다. 아래 ‘추천’은 채택 결정이 아니다. 팀원 원본 10개는 수정하지 않았으며 코드·SQL·실행 로그는 전달받지 않았다.

## 결론

경영주가 수요를 빠르게 파악하고 과거 처리 결과를 확인하는 아이디어는 현재 철학과 잘 맞는다. 특히 MOQ 진행 표시, 현재 설정과 과거 발주 방식의 구분, 변화 없는 설정 저장의 이력 중복 방지, 빈 목록/오류 구분이 유용하다.

다만 원본은 **한 점포·상품의 한 묶음 모집 회차 → 한 발주 결과 → 입고 안내**를 중심으로 한다. 현재 프로젝트는 **고객의 자연어·동의 → 계속 쌓이는 요청 → 여러 상품 묶음/정책 발주 → 공급 배정·모의 결제 → 입고·48시간 수령**이다. 화면 아이디어는 고를 수 있지만 스키마·상태·제외 범위를 통째로 옮기면 안 된다.

가장 큰 충돌은 픽업/48시간 제외, 모집 한 묶음을 넘는 신청 거절, 거절 결과까지 회차당 한 건으로 고정하는 발주, 예산/동의/세션 정보가 없는 자동발주 계약이다. 이 부분은 사용자 결정과 현 명세를 바꾸지 않고는 적용할 수 없다.

## 그대로 병합하면 생기는 충돌

### 1. 모집 목표를 고객 신청 상한으로 삼음

STEP-1은 목표 초과 신청을 거절한다. 예를 들어 MOQ 6개일 때 유효 수요 13개가 있어도 첫 6개에 도달한 뒤 신청을 막는 구조다. 현재 서비스는 수요를 보존하면서 발주 단위·예산에 맞게 공급해야 한다. 다음 회차가 아직 구현되지 않은 상태라면 수요와 고객 편의가 함께 손실된다.

M-01을 고르면 `현재 유효 수요 / 최소 발주 기준 / 추가 필요량 / 이번 발주 가능량 / 잔여 수요`를 구분하는 표시가 적절하다. MOQ와 주문 배수는 같은 값이라고 가정하지 않는다. 진행률 100%를 표시해도 실제 수요를 그 값으로 잘라 저장하지 않는다. 단위나 조건이 바뀌면 현재 실행 조건으로 다시 검사하고 과거 스냅샷은 설명/감사에 사용한다. 정확한 발주 수량은 BR-09/12/13·O-12를 따른다.

### 2. 모집 기한·발주 기한·고객 동의 기한의 결합

STEP-2는 모집 기한을 발주 기한으로 함께 쓴다. STEP-5는 다음 기한·대기 신청 만료가 미정이다. 현재 프로젝트에서 구매 의사 유효기간 O-03, 발주 가능 조건, 픽업 알림부터 48시간은 각각 다르다. 하나의 deadline으로 세 의미를 덮으면 이미 동의가 끝난 자동 구매나 입고 전 수령 만료가 발생할 수 있다. 회차 도입 시 각 기한의 시작·종료·재동의·취소·FIFO 영향까지 별도 결정해야 한다.

### 3. 픽업·48시간·모의 결제 삭제

STEP-6/7은 수령 가능 안내까지만 남기고 수령 확인·기한·중복 수령 방지를 제외한다. 이는 D-07~09와 03/04/09/GOAL의 필수 흐름을 축소한다. **그대로 채택 비추천.** STEP-6의 중복 입고·수량 검증 아이디어만 가져오더라도 공급 확보→배정→모의 결제→예약→입고·픽업→48시간 수령을 유지해야 한다. 선결제 없이 발주한다는 STEP-3의 방향 자체는 현 정의와 충돌하지 않는다.

### 4. 공급 가능 boolean과 무예산 자동발주

SCHEMA는 `supply_available=true` 기본값과 `auto_order` 토글을 둔다. 현재는 공급 가능 **수량**·제한 사유·unknown/조회 오류, 유효 동의·예산·정책 버전·활성 발주 연결까지 확인해야 한다. 공급 정보 부재를 가능으로 처리하거나 토글만으로 주문을 만들면 보수적 자동발주 요구를 위반한다. 예산·조건 확인 없는 자동발주를 완성 기능으로 병합하지 않는다.

### 5. 회차당 발주 결과 1개와 영구 거절

`purchase_orders.round_id UNIQUE`는 accepted와 rejected 모두에 적용되고 원본은 실패 회차 재발주를 제외한다. 현재 미확보 관리 에이전트에는 조건 변화 후 재검토·수요 복귀가 필요하다. 같은 요청 재시도는 같은 결과를 반환하되, 조건/정책이 바뀐 **새 시도**를 어떻게 구분할지는 별도 계약이다. 결과 행 하나가 과거 거절을 영구 잠금으로 만들지 않게 성공 주문·시도 이력·멱등 키를 구분할 필요가 있다. 이 설계는 아직 채택하지 않았다.

### 6. 재신청이 최초 신청 순번을 복원할 위험

SCHEMA는 동일 고객/회차 행을 다시 active로 만들고 최초 created_at을 남긴다. 이를 FIFO 기준으로 사용하면 취소 후 재신청자가 새 고객보다 앞설 수 있다. 현 O-02/O-04와 서버 sequence 규칙에 맞춰 재신청·수량 증가·취소 후 복귀의 순번과 새 동의를 결정해야 한다. created_at 하나로 현재 구매 의사와 순번을 모두 표현하지 않는다.

### 7. 고객 요청 저장과 자동발주의 오류 결합

STEP-3은 저장 오류 시 신청·발주 또는 설정·이력이 함께 rollback된다고 적는다. DB 원자성은 유용하지만 자동발주 실패가 정상 고객 요청까지 사라지게 하면 니즈를 보존하는 목적을 해친다. 공급 제한이라는 업무 결과, 일시적인 실행 실패, 요청 자체 저장 실패를 나눠야 한다. 고객 요청 성공·발주 보류를 허용할지와 이벤트 재처리 계약은 현 R-02/R-08/R-10과 맞춰 결정할 후보이며, 현재 문서에 일괄 rollback을 새 규칙으로 넣지 않았다.

### 8. 한 상품씩 누르는 UI와 전체 묶음 업무

STEP-2/3의 상품별 승인·토글은 상세 설정에는 유용하지만 기본 업무가 되면 승인 수가 상품 수만큼 늘어난다. D-12/37의 묶음 요약·자연어 수정·예외 위주 처리를 유지해야 한다. 상품별 화면을 추가할 경우 기본 수요 보드에서 일괄 처리하고 필요할 때만 상세로 이동하는 안을 권한다. 부가 기능 채택 후에도 27번의 경영주 조작/시간 비교가 필요하다.

## 실적 조회를 선택한다면 먼저 정할 것

STEP-9의 회차 생성 기간 기준 집계는 이벤트 발생 기간 집계와 다르다. 기간 밖 입고도 포함될 수 있고 조회 시점 취소로 과거 기간 값이 바뀔 수 있다. 화면에 기준을 설명하고 같은 조건의 상세와 합계가 맞아야 한다. 회차 모델을 쓰지 않는 현재 구조에서는 어떤 요청/발주 집합을 기준으로 연결할지 다시 정해야 한다.

과거 목표 달성률에는 목표 달성 시각·사건 이력이 필요하다. SCHEMA의 status/updated_at만으로 정확한 과거 상태를 복원할 수 있다고 가정하지 않는다. 발주 실패율은 시도 수와 최종 발주 결과 수 중 분모를 선택해야 하며 조회 0건/미수집/오류도 구분해야 한다. 픽업 기능이 있는 이 프로젝트에서는 ‘수령 가능 안내’를 판매나 수령 완료로 세지 않고 실제 상태와 분리한다. 본부 화면을 추가할 이유로 사용하지 않는다.

## 권장 선택 묶음과 병합 순서

**가장 작은 후보 묶음:** M-01 수요 카드, M-02 처리/정책 이력, M-03/04 과거 방식·변경 이력 정확성, M-05 자동 전환 영향 확인, M-11 입고 반례. 기존 흐름을 유지하면서 경영주가 이해하기 쉽게 만드는 데 집중한다. 전부 미채택이며 사용자 판단을 기다린다.

사용자가 항목을 선택한 뒤에만 다음을 수행한다.

1. 선택한 M-ID·원문·유지/수정/제외 범위를 02/DECISION_INDEX에 연결한다. 현재 문서를 이미 병합한 것으로 표시하지 않는다.
2. 회차·기한·토글 우선순위·재신청/재시도 등 세부 정책은 관련 O/R 및 기존 요구와 대조하고 필요한 ADR·복수 검토를 거친다.

4. 취소 경합, 단위 변경, 자동/수동 동시 실행, 예산 경쟁, 실패 재검토, 정책 변경과 과거 이력, 부분/중복 입고의 기대값을 고정한다.

### 수량과 기한 예시

MOQ 6개·주문 배수 6개인 상품에 각각 1개씩 13명이 유효하게 요청했다면 **13개를 모두 접수**한다. 공급 가능량 12개·예산 충분·기존 발주 연결 없음 등 조건을 만족하면 12개 발주, 1개 미발주로 남길 수 있다. 이미 6개가 발주에 연결됐다면 전체 13개를 다시 발주하지 않고 미연결 7개만 검사한다. 접수 화면에는 확보 보장을 하지 않는다. MOQ와 주문 배수는 일반적으로 별도 값이다.
