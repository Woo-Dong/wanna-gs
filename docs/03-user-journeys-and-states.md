# 사용자 흐름과 상태

상태 이름은 구현 초안이다. 제품 규칙의 확정 여부는 [결정 기록](02-decisions-and-open-questions.md)을 따른다.

## 고객 정상 흐름

1. 자연어로 상품을 표현한다.
2. 에이전트가 실제 카탈로그 후보를 검색한다. 필요하면 구분 질문을 한다.
3. 고객이 상품 카드를 확인한다.
4. 수량·점포·가격·자동 구매·48시간 수령 조건을 확인한다.
5. 요청이 저장되고 접수 순서가 정해진다.
6. 경영주의 직접 승인 또는 사전 승인 규칙에 따른 모의 발주가 진행된다.
7. 공급 시뮬레이터가 확보 수량을 확정한다. 발주 수량과 확보 수량은 다를 수 있다.
8. 서버가 접수 순서대로 배정하고 동의 조건을 검증한다.
9. 모의 자동 결제에 성공하면 예약 확정 알림을 만든다.
10. 모의 입고 시 픽업 가능 알림과 48시간 마감 시각을 함께 만든다.
11. 기한 안에 수령 완료를 처리한다.

## 경영주 정상 흐름

1. ‘오늘 발주 정리’에서 최신 수요와 미확보 이유를 확인한다.
2. 에이전트가 `알아서 처리했GS / 이것만 봐주GS / 조금 더 기다리GS`로 묶는다.
3. 조건 충족 항목은 승인된 자동발주 규칙에 따라 처리한다.
4. 예외 묶음에는 ‘샌드위치 빼고 5만 원 안에서’처럼 말한다.
5. 구조화한 변경 조건, 정확한 금액·수량·보류 이유를 확인하고 일괄 승인한다.
6. 공급·입고를 시뮬레이션해 고객 상태 전환을 확인한다.

‘이번만’은 현재 제안에 적용한다. ‘앞으로도’는 지속 규칙 변경 초안이며 적용 조건을 별도로 확인한다.

## 요청·발주·예약별 상태

고객 요청, 점포 발주, 고객 예약은 서로 다른 생명주기를 가진다. 아래 상태를 구분해 보존하고 고객 타임라인은 이들을 조합해 표시한다.

### 고객 요청

| 상태 | 의미 | 전환 근거 |
|---|---|---|
| `pending` | 식별·동의를 마친 미확보 요청 | 고객 제출 |
| `review_required` | 조건 변경·공급 종료 등 별도 판단 필요 | 확인된 사유 |
| `allocated` | 물량을 특정 고객에게 확보해 둠 | 배정 트랜잭션 |
| `reserved` | 모의 결제 성공 후 예약 연결 | 결제 결과 |
| `cancelled` | 허용 범위의 명시적 취소 | 취소 규칙, O-04 |

단순 발주 제한·최소 수량 미달은 요청 자체를 종료하지 않는다. 요청 상태와 함께 `pending_reason`을 둔다. 미식별은 이 대기열에 넣지 않고 별도 기록한다.

### 점포 발주

| 상태 | 의미 |
|---|---|
| `draft` | 에이전트/규칙이 만든 제안 |
| `approved` | 경영주 또는 승인된 정책이 실행을 허용 |
| `submitted` | 모의 발주 제출 |
| `supply_confirmed` | 모의 공급 확정, 확보 수량 기록 |
| `received` | 모의 입고 완료 |
| `blocked` | 조건 변경 등으로 실행 불가 |

공급·입고는 라인별 수량으로 관리한다. 고객 요청이 다른 발주에 중복 포함되지 않도록 연결 수량을 기록한다.

### 예약·모의 결제

| 상태 | 의미 |
|---|---|
| `payment_pending` | 배정 후 모의 결제 중 |
| `payment_failed` | 실패 시뮬레이션 또는 검증 실패 |
| `confirmed` | 모의 결제 성공, 입고 대기 |
| `pickup_ready` | 실제 시뮬레이션상 수령 가능 |
| `collected` | 수령 완료 |
| `pickup_expired` | 48시간 경과, 후속 처리 규칙은 O-07 |

## 수령 시간의 정확한 의미

- `pickup_available_at`: 픽업 가능 상태와 앱 내 알림이 DB에 생성된 시각.
- `pickup_deadline_at`: 위 시각 + 48시간.
- 알림을 고객이 열어본 시각으로 재설정하지 않는다.
- 같은 입고 이벤트를 재처리해도 마감이 연장되지 않는다.
- `now >= pickup_deadline_at`이면 수령 가능하지 않다. 경계 포함 여부는 이 명세를 구현 기본안으로 삼는다.
- DB 시각은 UTC `timestamptz`, 표시 기본은 Asia/Seoul이다.
- 만료 레코드 정리 작업이 늦더라도 수령 API는 시각을 직접 확인해 기한을 강제한다.

## 예외 흐름

| 예외 | 고객 처리 | 경영주 처리 |
|---|---|---|
| 상품 식별 실패 | 원문 보존, 예약 아님 안내 | 미식별 목록 |
| 발주 제한 | 확인된 사유만 표시 | 보류·재검토 |
| 최소 수량 미달 | 집계 중 표시 | 자동발주 제외 |
| 일부 공급 | 확정된 부분 배정·FIFO 정책에 따라 처리 | 잔여 대기, O-01 미정 |
| 동의 가격 변경 | 자동 결제 중단 | 조건 변경 검토 |
| 결제 실패 | 예약 확정으로 표시하지 않음 | 재시도/배정 해제 O-06 |
| 수령 기한 초과 | 마감 시각·기한 초과 표시 | 미수령 목록, 환불 등은 미정 |

## 화면 목록

- 고객: 자연어 요청, 후보 확인, 수량·점포·동의, 내 요청 타임라인, 모의 결제 완료, 픽업 예약 상세.
- 경영주: 수요 보드, 묶음 검토·대화 수정, 자동발주 설정, 미확보 사유, 미식별 요청, 모의 입고·수령.
- 데모 도구: 세션 생성/연결, 시나리오 불러오기, 초기화, 공급 조건 변경, 시간 이동.
- 본부 화면은 없다.

## 구현 전 상태 계약 보완

위 상태표에는 아직 정의하지 않은 전이가 있다. [검토 목록](13-review-checklist.md)의 R-02~R-06/R-14를 해결하면서 다음을 완성한다.

- 공급 0·부족 확정·추가 공급 대기·영구 실패에서 발주 연결 해제와 수요 복귀.
- `review_required`의 재동의·취소·대기열 유효성 및 복귀 API.
- 주문 헤더와 라인 상태 집계, 공급/입고 1회 제한 여부, 누적·증분 수량 의미.
- 요청·예약·수령/만료를 합친 사용자 표시 상태와 유효 미확보 수요 진리표.

정책 미정인 부분을 새 상태 이름만 추가해 해결했다고 판단하지 않는다. 각 전이에 주체·선행조건·수량/예산 영향·멱등성·알림·오류를 연결한다.

## 모집 목표·기한 재검토 반영

D-41에 따라 최소 발주 기준을 채운 뒤에도 요청 접수를 유지한다. 기준 충족은 발주 검토 조건이며 고객 예약 완료 상태가 아니다. 진행 중 발주에 연결된 수요와 새 미발주 수요를 구분한다.

D-42에 따라 모집/발주 마감과 동의 유효성, 수령 만료를 분리한다. 공급 확보 후 결제 시점에 유효 동의를 검증하고, 입고 대기 예약을 모집/발주 기한으로 `pickup_expired` 처리하지 않는다. O-03의 구체 기간·재동의 절차는 별도 결정하며 픽업 마감은 기존 알림 생성 +48시간을 유지한다.
