# /goal 단일 실행 계약

상태: 최초 구현 기준. GitHub repo·인증·Vercel 등 사전 설정이 끝나고 이 저장소에 설계 문서와 프로젝트 지침이 있는 상태에서 시작한다. 세부 정책 결정·구현·검증·Git 운영·배포까지 한 목표로 진행한다. 이 파일을 편집하는 것만으로 목표가 시작되지는 않는다.

## 실행 전

[18번 환경 점검](18-environment-preflight.md)의 wanna-gs-preflight 스킬을 먼저 실행한다. 실제 검사 범위·차단·미검증 릴리스 권한을 확인한다. inspector만 실행한 상태는 실제 연동 성공이 아니다. 사전 설정/인증이 바뀌면 관련 검사를 다시 한다. 같은 환경의 유효한 검사를 이유 없이 모두 반복하지 않는다.

## 한 번 입력할 실행 문장

저장소를 clone한 위치 또는 연결된 worktree를 Codex 프로젝트로 연 뒤 입력한다. `git rev-parse --show-toplevel`로 루트를 확인하고 그곳의 `AGENTS.md`, `card.md`, `docs/GOAL.md`가 이 프로젝트 문서인지 대조한다. 절대 경로는 실행 환경에서 구하며 다른 clone의 경로를 재사용하지 않는다.

```text
/goal 이 저장소의 docs/GOAL.md 계약에 따라 원하GS 해커톤 프로토타입을 완성하라. GitHub repo와 Vercel 등 사전 설정 완료 및 preflight 결과를 확인하고 루트 AGENTS.md·card.md와 docs를 읽어 구현을 시작하라. 실행 당시의 시장·트렌드·고객/경영주 니즈와 기능별 기술·검증 근거를 조사 에이전트로 새로 확인하라. 과거 대화의 소수 예시를 고정 데이터로 삼지 말고 근거→설계→약 200개 상품·실제 점포 위치·합성 사용자→다양한 자연어 평가 시나리오를 추적 가능하게 만들라. 기존 사용자 정의와 서비스 가치를 지키는 세부 데모 정책은 사람에게 매번 묻지 말고 초안·기록·서로 다른 두 서브 에이전트 검토·채택·테스트로 결정하라. 영역별 구현과 자체 단위 검증, 별도 독립 검증, 실제 DB 영역 통합, 인접 기능 통합, 전체 브라우저·실제 모델 검증을 수행하라. 단계별 테스트가 통과할 때마다 지정 GitHub repo에 논리적 commit과 push를 하고 작업 브랜치·PR·CI·통합 브랜치를 운영하며 검증된 PR을 자율 병합하라. 자연어 이해·매핑 품질도 목표로 삼아 고정 baseline 대비 프롬프트·검색·데이터 구조를 변경·평가·독립 검토하는 제한된 실험을 진행하라. 23번 중단 조건에 도달하면 필수 기준을 통과한 최선 버전을 유지하고 개선 한계를 기록하되 필수 오류를 면제하지 말라. 최종 통합에서 시간·수량·동의·상태·재시도 정책의 빈틈을 다시 감사하고 같은 결정·수정·재검증 루프로 해결하라. G5와 최종 정책 감사를 통과하면 제출 브랜치로 병합해 연결된 Vercel에 배포하고 G6를 수행하라. 최종 URL·live 모델·DB·필수 정상/예외 흐름, 원격 commit/PR/CI·배포 증거, 정책 결정 이력과 실행/복구 안내가 갖춰진 경우에만 완료하라. 유료 구매·실제 GS/결제 연동·제외 기능 추가·보호 규칙 우회는 하지 말고 실제 권한·인증·비용 장벽만 근거와 다음 행동으로 보고하라. 작은 정책 미정이나 테스트 실패만으로 사람의 중간 결정을 기다리지 말고 해결을 계속하라.
```

목표와 계약 경로를 함께 전달한다. `/goal`에는 이 계약의 경로와 목표를 함께 적는다. 상태 조회·중단/재개는 현재 환경의 실제 동작을 따른다.

## 읽기와 범위

루트 AGENTS/card → CORE_REQUIREMENTS/README/02/DECISION_INDEX/PROGRESS → 16번 Git 운영/17번 자율 결정/14번 검증/15번 복구 → 해당 영역 명세·AC·13번 점검 항목 순으로 읽는다. 매 반복마다 전체 문서를 다시 읽지 않는다. 프로젝트 `.agents/skills/`의 verify/recovery/decide/preflight 스킬은 자동 발견되지 않으면 SKILL.md를 직접 읽는다. 글로벌 스킬 설치는 필수가 아니다.

고객 자연어 식별·상품 확인·수량/점포/가격/자동 구매 동의·요청 → 경영주 묶음 검토·자연어 수정·보수적 자동발주 → 공급 확보·선착순 배정·모의 자동 결제 → 입고·픽업 가능 알림 생성부터 정확히 48시간 수령을 연결한다. 출처가 있는 상품·실제 점포와 모의 거래 seed·미식별 기록/경영주 조회·세션 격리/reset도 포함한다. 본부 화면·사진/링크/레시피·실제 GS/청구는 제외하고 Vector RAG는 선택 실험이다.

Next.js FE/BE·Neon DB·Gateway 기본 호출과 Gemini 직접 호출 예비 경로가 기술 기준선이다. 같은 범위 안의 동등한 기술 조정은 증거와 변경 기록을 남긴다.

## 내부 진행 순서

1. 사전점검 증거·실제 repo/권한/설정·DB/모델을 대조한다. 기존 repo를 재사용하며 유효한 준비를 이유 없이 되풀이하지 않는다. 최소 고객/경영주 shell을 실제 Preview에서 확인한다.
2. [WORKPLAN](WORKPLAN.md)을 의존성·역할·소유권·핵심 요구·기대값·게이트·조사 과제로 구체화한다. 필요한 ADR과 context manifest를 준비하고 PLAN-READY를 검토한다. 10번의 M0-C(GATE-BOOTSTRAP)에서 실행기·CI·게이트를 만든다. 초기 구축에 완제품 검사를 요구하지 않는다.
3. [24번](24-market-research-and-scenario-design.md)에 따라 실행 시점 자료를 직접 조사한다. 시장/니즈뿐 아니라 각 기능의 UX·업무·연동·검증 근거를 필요한 범위에서 확인한다. 자료의 최신성과 채택 이유를 기록하고 과거 예시를 반복하는 것으로 대신하지 않는다.
4. [19번](19-data-research-and-seeding.md)의 약 200개 상품·실제 점포/좌표·합성 사용자를 만들고 최소 schema/검증된 seed importer를 거쳐 DB에 넣는다. 자연어·업무 시나리오와 분리된 평가셋도 함께 준비해 SEED-READY를 확인한다. ADR-001에 따라 최소 seed의 실제 DB·독립 검토와 P04를 마치면 F00을 먼저 시작할 수 있다. 전체 수집과 기능 개발을 병행하되 정식 QA·최종 자연어 기준선·G5는 전체 seed를 요구한다.
5. 역할별 기능 구현→단위→독립 검증→실제 DB→인접 기능→브라우저 순으로 확장하고 commit/push→PR→CI→통합한다. 각 G0에서 관련 연구·유효 정책·계약을 다시 확인한다. 변경 영향이 있는 근거만 추가 조사한다.
6. [23번](23-nl-experiment-loop.md)의 자연어 품질 실험을 수행한다. 실험자와 평가자를 분리하고 holdout을 보호하며 채택/기각/정체/한도 중단을 기록한다. 모델은 [20번](20-agent-roles-and-context.md)에 따라 실제 제공 모델에서 작업에 맞게 선택한다.
7. 고객/경영주 별도 UX QA, [22번](22-orchestration-audit.md)의 운영 감사, 정책 빈틈 감사와 G5를 통과하면 최신 제출 기반 릴리스 PR을 병합하고 실제 Vercel deployment에서 G6를 실행한다.
8. 최종 URL·원격/배포/DB/모델·조사/결정/실험 증거와 실행·시연·복구 안내를 남긴다. 필수 통과 기준 충족을 확인한 뒤 완료한다.

## 위임된 작업과 경계

지정 repo의 branch/worktree·commit/push·PR 작성/수정·통과한 PR 병합, 연결된 Vercel Preview/최종 제출 배포, 허용된 무료 환경의 DB migration/seed·테스트는 반복 확인 없이 수행한다. 실제 새로운 유료 구매·외부 repo 변경·조직 권한 획득·사용자 데이터 파괴·보호 규칙 우회는 포함하지 않는다.

GitHub Actions는 테스트를 실행하고 Codex 목표가 서브 에이전트를 조정한다. 같은 GitHub 계정의 서브 에이전트 리뷰를 별도 계정의 공식 approval로 위장하지 않는다. 스킬/문서가 있다고 CI가 구현된 것은 아니므로 첫 단계에서 만든다. 목표 예산은 사용자가 명시한 경우에만 지원 도구로 설정한다.

## 완료 조건

- 필수 정상/예외 기능·AC·위임 정책이 현재 코드와 실제 증거에 연결되고 적용 G0~G6 통과.
- 실제 제출 URL에서 모델·DB·브라우저·reset·48시간 경계 확인. fixture/live/미실행 명확히 구분.
- 두 관점의 최종 정책 감사에서 중대한 미해결 반례 없음. O/R를 채택+검증 또는 명시적 데모 단순화/제외로 처분.
- 원격 commit/PR/CI, merge/source SHA·deployment URL/ID, schema/seed/model/config 연결.
- 실행·시연·복구 안내·위임 결정 이력·제한과 재개 가능한 작업 이력.
- 약 200개 상품·검증된 실제 점포 위치·합성 사용자와 연구→시나리오→테스트 연결. goal 실행 시 조사 기록과 데이터/eval 버전.
- 고객/경영주 독립 UX QA, 현재 유효한 정책/context, 운영 감사·개선 기록.
- 자연어 baseline/후보/best-known 전후 지표, 독립 평가 및 중단 사유. 추가 개선 정체는 허용되지만 필수 출시 기준 미달을 완료로 바꾸지 않음.

필수 기능을 막는 외부 차단은 완료가 아니다. 코드 작성 후 최종 통합 감사도 목표 안의 남은 작업이다. 과거 SHA의 성공·Preview Ready·fixture-only로 완료를 대체하지 않는다. 모든 상용 정책의 구현이나 무한 기능 추가는 완료 조건이 아니다.

## 실패와 재개

15번 복구, 17번 자율 정책, 16번 Git/배포 상태 조회를 적용한다. 작은 정책 질문을 중단 이유로 삼지 않는다. 실제 요구 충돌·인증/권한/비용 차단은 시도·증거·가능한 독립 작업·필요 조건을 남긴다. 재개 시 PROGRESS와 실제 repo/PR/CI/deployment/DB를 대조하고 마지막 유효 게이트에서 이어간다. 한도 도달·실패 횟수를 목표 달성으로 바꾸지 않고 goal 수명주기는 현재 도구 계약을 따른다.

## 역할과 추가 스킬

20번의 역할별로 작업을 배정하되 실제 슬롯 수 안에서 독립 가능한 일만 병렬화한다. 조사에는 wanna-gs-research, 고객/경영주 UX에는 wanna-gs-ux-audit, 자연어 실험에는 wanna-gs-nl-experiment, 운영 방식 점검에는 wanna-gs-orchestration-audit를 사용한다. 자동 발견이 안 되면 해당 `.agents/skills/<이름>/SKILL.md`를 직접 읽는다. 중요한 결정은 적합한 강한 모델과 독립 검토로 보강하고 단순 작업은 가벼운 모델을 선택할 수 있다. 모든 역할을 항상 동시에 띄우거나 관리자 에이전트를 재귀 생성하지 않는다.

## 장시간 실행과 재개 포인터

매 유효 체크포인트에서 PROGRESS 최상단의 task·branch·PR·마지막 게이트·배포·다음 행동을 갱신한다. 사용량/예산 제한은 추가 메시지를 쓸 틈 없이 실행을 중단시킬 수 있으므로 마지막 순간 기록을 보장하지 않는다. 재개 때 실제 원격/배포 상태와 포인터를 대조한다. 내부 sqlite 경로/스키마를 공식 운영 API로 고정하지 않고 현재 제공 goal 상태 도구/UI를 사용한다. 지원되는 재개 방법은 그때의 도구/공식 문서에 따른다.

외부 차단은 증거와 필요한 조치를 기록하고 남은 독립 작업을 진행한다. 현재 도구의 blocked 전환 조건을 충족할 때만 그 상태를 설정한다. 문서가 사용량 한도를 해제하거나 실패 직후 goal 상태를 임의로 종료할 권한을 주지 않는다. 새 토큰 예산은 사용자가 명시한 경우에만 설정한다.

조사와 계획의 순서: PLAN-READY 전에는 각 영역의 문제·자료 접근·위험을 파악하는 초기 탐색과 연구 질문/출처 계획을 검토한다. M1에서는 그 계획으로 본격 조사·데이터 생성·독립 평가셋 구축을 마쳐 SEED-READY를 판정한다. 전 상품 수집을 PLAN-READY의 선행조건으로 만들거나 조사를 계획 이후에만 허용하는 순환은 없다. 각 기능 G0의 추가 조사는 해당 결정에 필요한 범위로 제한한다.

## 모델 잔량과 예비 경로

D-31·CORE-23·AC-29와 [25번](25-model-budget-and-fallback.md)을 실행 범위에 포함한다. 사용자가 주입한 Gemini 키로 직접 호출 경로를 준비하고 Gateway를 기본으로 쓴다. 테스트 중과 배포 직전에 남은 평가·데모 예산을 확인한다. 부족하면 검증한 Gemini 모델로 전환하고 변경된 설정의 품질·E2E·G5/G6를 확인한다. 두 경로 모두 무료 용량이 부족하면 외부 차단과 재개 조건을 기록한다. 유료 전환이나 자동 충전은 별도 승인 없이 수행하지 않는다.
