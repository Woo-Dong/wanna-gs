# 에이전트와 검색 설계

## 원칙

동일한 서버에서 고객·경영주 에이전트의 지시문, 허용 도구, 출력 스키마를 구분한다. LLM이 입력을 해석하고 행동을 제안하면 서버 코드가 거래 조건과 실행 권한을 검증한다.

## A. 고객 상품 식별 에이전트

### 입력

고객 발화, 현재 대화, 검색 가능한 상품 목록/검색 도구 결과. 위치·가격·재고는 필요한 경우 서버가 제공하며 모델의 일반 지식으로 채우지 않는다.

### 허용 도구 초안

- `search_products(query, attributes)`: 상품명·별칭·종류·맛·용량 등으로 후보 검색.
- `get_product(product_id)`: 실제 존재하는 상품의 상세 정보 확인.
- `get_store_product_options(product_id)`: 테스트 점포의 가격·취급 상태 확인.
- 선택 실험: `semantic_search_products(query)`.

대화 저장과 고객이 확인한 요청 생성은 검증된 서버 흐름에서 수행한다. 이 에이전트는 고객 동의나 물량 배정을 대신하지 않는다.

### 출력 계약 초안

```json
{
  "action": "show_candidates",
  "candidateIds": ["PRD-DEMO-001", "PRD-DEMO-002"],
  "question": null,
  "reason": "두 후보 모두 딸기와 크림을 포함하지만 상품 종류가 다릅니다."
}
```

`action`은 `show_candidates | ask_clarification | unidentified` 등 제한된 값으로 구성한다. 서버는 후보 ID의 존재·접근 범위를 검증한다. 자연어 이유나 모델의 자신감 숫자를 정답 증거로 삼지 않는다. 추가 질문 상한 2회는 O-11의 제안이다.

## B. 경영주 미확보 요청 관리 에이전트

### 할 일

1. 유효 미확보 요청과 기존 발주 연결을 읽는다.
2. 최신 공급 조건·예산·자동발주 정책을 조회한다.
3. 자동 처리 가능/검토 필요/대기 유지로 묶는다.
4. 경영주의 비정형 지시를 구조화된 변경안으로 만든다.
5. 근거와 요약을 제공한다. 조건 검사·실행은 서버 도구가 한다.

### 허용 도구 초안

- `get_pending_demand(store_id)`
- `get_supply_conditions(product_ids)`
- `get_order_policy(store_id)`
- `build_order_proposal(constraints)`
- `validate_order_proposal(proposal_id, version)`

실행 도구를 연결하는 경우에도 권한·정책 검사를 내부에 강제한다. 모델이 ‘승인됨’이라고 말하는 것만으로 승인을 생성하지 않는다. 자동 실행의 권한 근거는 DB의 활성 정책이다.

### 자연어 제약 예시

```json
{
  "scope": "current_proposal",
  "excludeCategories": ["샌드위치"],
  "budgetLimitKrw": 50000,
  "allowExtraQuantity": false
}
```

- ‘아까 뺀 것 다시’: 이전 변경 이력으로 대상을 확인한다.
- ‘너무 쓰지 말고’: 저장된 예산을 사용하거나 없으면 한 번 묻는다.
- ‘앞으로도 이렇게’: 지속 정책 변경 초안으로 전환해 확인한다.
- ‘잘 팔릴 것만’: 판매 예측 모델이 있는 것처럼 답하지 않고 유효 요청 등 사용할 기준을 표시한다.

## 최소 실행 구조

요청 기반의 짧고 제한된 도구 루프로 만든다. 도구 호출 횟수·전체 실행 시간·출력 길이를 설정으로 제한한다. 실패 시 현재 상태·다음 행동을 응답하고 거래 상태를 임의 변경하지 않는다. 끝없는 자기 재호출·상시 감시 프로세스는 이번 범위가 아니다.

## 기본 검색

상품 ID·정확한 상품명 → 별칭·정규화된 문자열·속성 검색 → 필요하면 LLM으로 후보 구분. 한국어의 띄어쓰기·오타·줄임말·종류 혼동을 평가 데이터에 포함한다. 문자열 검색이 놓치는 한국어 표현을 별도로 측정한다.

초기 데이터가 작으면 모델에 필요한 후보/필드만 전달한다. 카탈로그가 커지면 검색으로 후보를 좁힌다. 가격·재고·발주 제한처럼 변하는 정보는 항상 현재 DB에서 확인한다.

## 선택 실험: 하이브리드 Vector RAG

1. 상품 한 개의 이름·별칭·분류·설명을 하나의 검색 문서로 구성한다.
2. 임베딩 모델로 벡터를 생성해 PostgreSQL `pgvector`에 저장한다.
3. 고객 질문도 동일 모델·호환 설정으로 임베딩한다.
4. 벡터 후보와 키워드·속성 후보를 결합한다.
5. 명시된 브랜드·용량 등의 조건을 검증하고 LLM이 후보 설명·구분 질문을 만든다.
6. 고객이 최종 확인한다.

벡터 검색은 후보 회수이고, 회수된 근거로 LLM이 응답하는 부분이 RAG다. 가장 가까운 벡터를 반드시 정답으로 취급하지 않는다. ‘없는 상품’도 최근접 이웃은 존재할 수 있다.

### 임베딩 운영

- 상품 임베딩은 seed/상품 변경 시 생성한다. 질의 임베딩은 검색 시 필요하다.
- `model`, `dimensions`, `text_hash`, `generated_at`을 기록한다.
- 모델·차원 변경 시 재색인을 수행한다. 다른 모델 벡터를 섞어 검색하지 않는다.
- Vercel AI Gateway 임베딩 지원과 해당 모델의 무료 사용 가능 여부는 별도 확인한다.
- 단순 프롬프트로 임의 숫자를 생성해 임베딩으로 사용하지 않는다.
- 임베딩 경로가 없거나 개선이 없으면 기본 검색으로 출시한다.

## 평가와 모델 교체

실제 LLM과 고정 응답 모드를 구분하는 provider 인터페이스를 둔다. 실제 호출은 [25번](25-model-budget-and-fallback.md)의 Gateway·Gemini 어댑터로 연결한다. `live`는 실제 호출, `fixture`는 사전 정의된 재현용 응답이다. UI·실행 로그·보고서에 모드를 남기며 조용히 바꿔 실제 AI 성공으로 보고하지 않는다.

평가는 [검증 명세](09-verification-and-evals.md)의 정답 상품, 미식별, 모호한 입력, 경영주 명령 사례로 수행한다. 성능·비용을 측정하기 전 특정 모델의 한국어 품질을 보장하지 않는다.

## 개발용 에이전트와 평가 경계

이 문서의 두 에이전트는 제품 런타임이다. 기능을 만드는 서브 에이전트의 구현/검증/복구 책임은 [14번](14-agent-development-loop.md), [15번](15-failure-recovery.md)에 별도로 정의한다.

구현 전 R-32/R-33에서 모델/프롬프트 버전·지연 목표·실행 상한·정답/허용 행동·반복수·품질 문턱을 기록한다. 도구 결과와 사용자 입력의 지시문을 권한으로 신뢰하지 않는다. 검색 장애와 미등록 상품을 구분하고 이전 대화의 늦은 응답이 최신 결과를 덮지 않게 버전을 검사한다.

## 개발 중 자연어 품질 개선

앱 안의 고객/경영주 에이전트와 개발용 실험 에이전트를 구분한다. [23번](23-nl-experiment-loop.md)에 따라 기준선·실패 분해·프롬프트/검색/데이터 구조 후보·독립 평가·최선 버전 채택을 반복한다. [24번](24-market-research-and-scenario-design.md)의 실제 니즈 조사로 개발/평가 사례를 만들고 holdout은 분리한다. 런타임이 임의로 자기 코드·정책·스키마를 수정하지 않는다. 개선 정체 시 검증된 최선 버전을 보존하고 한계와 기각 실험을 기록한다.

## 식별·대체 추천·미충족 니즈 계약

[27번](27-service-values-and-guardrails.md)의 D-37을 고객/경영주 에이전트 모두 적용한다. 고객 출력에는 후보별 `candidate_kind`(정확/확인필요/대체), 검증한 SKU, 공통점/차이의 근거 필드, 충족 여부가 확인되지 않은 조건을 표현한다. 이름은 구현 초안이며 모델은 존재 SKU만 반환하고 서버가 검증한다. 대체 후보를 원상품 식별 정답으로 채점하지 않는다.

`unidentified`는 검색/모델 호출이 정상 완료됐지만 상품을 식별하지 못한 결과다. `lookup_error`는 운영 오류이며 니즈·확약 수량을 증가시키지 않는다. 점포 취급·재고·공급 가능 여부는 별도 확인하고 모르면 unknown이다. 적합한 대안이 없으면 추천을 만들지 않고 입력 보존·기록/재입력 경로를 제공한다. 좋은 후보가 있는 정상 요청까지 모두 거절하는 방식은 금지한다.

경영주 추천은 조회/제안과 실제 발주 도구를 분리한다. 인근 수요·대체재 참고 제안은 선택 부가 기능이며 자동발주 근거에 포함하지 않는다. 이번 묶음 수정·영구 정책 변경을 구분하고 전체 결과를 요약하고 실패/보류 상세를 묶어 설명한다. 고객 확인과 경영주 승인 권한은 개발 에이전트의 자율 결정 위임으로 대신할 수 없다.
