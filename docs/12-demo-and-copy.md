# 데모 구성·표현·향후 가치

## 핵심 데모 이야기

고객은 정확한 상품명을 몰라도 원하는 상품을 확인해 요청한다. 경영주는 이미 팔린 수량에 더해 아직 충족하지 못한 요청을 보고, 묶음 지시와 보수적인 자동발주로 대응한다. 확보된 물량은 요청 순서대로 예약되고 고객에게 수령 시각을 명확히 알려준다.

## 권장 시연 순서

1. 데모 세션을 초기화하고 고객/경영주 화면을 같은 세션으로 연다.
2. ‘그 딸기 들어간 빵 같은 거’로 검색하고 구분 질문·상품 확인을 보여준다.
3. 수량·점포·가격·자동 구매·48시간 조건에 동의해 요청한다.
4. 경영주 화면에서 기존 요청과 합산된 수요를 확인한다.
5. ‘샌드위치는 빼고 나머지는 요청만큼, 예산 안에서’ 등 수정 동작을 다른 준비된 묶음에서 보여준다.
6. 자동발주 조건 충족 품목은 처리되고 최소 수량 미달 품목은 보류되는 것을 확인한다.
7. 공급 확정 → FIFO 배정 → 모의 결제 완료 → 예약 확정을 보여준다.
8. 입고 → 픽업 가능 알림 → 48시간 마감 표시 → 모의 수령을 보여준다.
9. 별도 초기화 사례에서 미식별과 48시간 초과를 짧게 확인한다.

하나의 시연에서 서로 모순되는 명령으로 핵심 상품을 제외하지 않도록 fixture를 준비한다. 정상 흐름과 예외 흐름의 데이터를 분리한다.

## 브랜드 이름과 발음

국문 표기는 **원하GS**, 발음은 **원하지쓰**, 영문은 **WANNA GS**다. D-35에 따른 현재 기준이며 이전 발음 제안을 대체한다. 첫 화면에는 `원하GS` 바로 아래 `‘원하지쓰’라고 읽어요.`를 표시한다. 소개 첫 줄은 `원하GS(원하지쓰) · WANNA GS`로 쓴다.

말장난 속 `~GS`는 `~지쓰`로 읽도록 안내한다. 예: `없으면 말하GS` → `없으면 말하지쓰`, `여기 있GS` → `여기 있지쓰`. 이름을 처음 접할 때 발음이 보이게 하고, 이후 모든 문장에 반복해서 붙이지 않는다. 공식 고유명사 GS25·우리동네GS의 발음을 바꾸는 규칙은 아니다.

브랜드 배치·색상·화면 구성·접근성 구현은 [26번 디자인 가이드](26-design-and-brand-guide.md)를 따른다. 한글 발음 안내를 작은 이미지 글자·툴팁·숨겨진 접근성 속성에만 넣지 않는다.

## 카피 가이드

장난스러운 제목 아래에는 정확한 상태·행동·기한을 쓴다. 큰 카피는 첫 진입·접수·픽업 같은 주요 순간에 집중하고, 승인·금액·동의·오류 본문과 버튼은 평이한 한국어로 쓴다. 아래 제목은 구현 카피 시작안이며 상태 의미를 바꾸지 않는 범위에서 다듬을 수 있다. 확정된 브랜드 발음은 유지한다.

| 상황 | 제목 예시 | 정확한 설명·행동 |
|---|---|---|
| 입력 | 없으면 말하GS | 찾는 상품의 이름이나 특징을 알려주세요. 버튼: `상품 찾기` |
| 후보 확인 | 찾으시는 상품이 맞나요? | 상품명·맛·용량을 확인해주세요. 버튼: `이 상품 선택` / `다른 상품이에요` |
| 요청 접수 | 원하GS, 접수했GS | 선택한 점포에 요청을 남겼어요. 아직 물량 확보 전이에요. 버튼: `내 요청 보기` |
| 수요 집계 | 지금 {고객 수}명이 원하GS | 유효 고유 고객 수와 요청 상품 수량을 별도 표시. 예: 3명·5개 |
| 자동 구매 동의 | 물량이 확보되면 자동 구매해요 | 상품·점포·수량·가격·총액·동의 유효조건, 모의 결제, 픽업 알림부터 48시간을 명시. 버튼: `요청하기` |
| 발주 승인/공급 대기 | 점포에서 발주를 진행했어요 | 아직 공급 확보·예약 확정 전임을 알림. 실제 저장된 단계가 승인뿐이면 제출 완료라고 쓰지 않음 |
| 공급 확보/배정·결제 처리 중 | 물량을 확보했어요 | 배정·모의 결제 상태를 표시. 아직 결제 완료로 쓰지 않음 |
| 모의 결제 성공·예약 확정 | 담아두GS | 모의 결제와 예약이 완료됐어요. 입고 후 알려드릴게요. 실제 청구 없음, 아직 수령 전 |
| 모의 결제 실패 | 결제를 완료하지 못했어요 | 예약 확정 여부와 가능한 재시도/확인 행동을 실제 상태에 맞게 안내. 성공 카피 사용 금지 |
| 픽업 가능 | 여기 있GS | 수령 점포와 서버 계산 마감 날짜·시각(KST)을 표시. 픽업 알림 생성부터 48시간. 버튼: `픽업 정보 보기` |
| 공급 제한 | 지금은 못 구하GS | 모의 공급 정보의 확인된 사유·재검토 조건. 일시 제한/공급 종료/원인 미확인 구분 |
| 미식별 | 못 찾았지만, 남겨두GS | 미식별 기록은 구매 요청·예약이 아님. 기록 저장에 성공한 경우에만 ‘남겨두었어요’ 표시 |
| 기한 종료 | 수령 기한이 지났어요 | 마감 시각과 현재 상태 표시. 수령 불가, 미구현 환불·재판매 약속 없음 |
| 경영주 처리 결과 | 발주 처리 결과 | 성공/실패/보류 품목·수량·금액·적용 정책을 묶어 표시. 전부 성공한 것처럼 표현하지 않음 |
| 경영주 예외 검토 | 이것만 확인해주세요 | 자동 처리하지 않은 이유와 선택 가능한 행동 |

상태별 제목과 설명은 03/04번 및 유효 ADR에 연결한다. `담아두GS`는 모의 결제 성공·예약 확정, `여기 있GS`는 입고 및 픽업 알림이 생성된 수령 가능 상태에서만 사용한다. UI 카피가 서버 상태를 먼저 바꾸거나 성공을 예측하지 않는다.

`{고객 수}`는 현재 데모 세션·점포·상품의 유효 수요 집합에서 집계하며 `{요청 수량}`과 구분한다. 정확한 포함 상태는 업무 계약에 고정한다. 0명·1명·큰 수, 취소·중복 제출·새로고침을 확인하고 이미지의 3명을 고정하지 않는다. 기한은 절대 날짜·시각과 남은 시간을 함께 표시하며 재전송·화면 열람으로 연장하지 않는다. 서버 기준 `현재 시각 >= 마감`이면 수령을 허용하지 않는다.

`이런 거 찾았GS`는 신상품 발굴을 구현할 때의 후속 카피이며 이번 화면 기능으로 넣지 않는다. 사진·마이크·실제 바코드도 참고 이미지에 있다는 이유로 구현하지 않는다.

## 항상 구분할 표시

- 데모 데이터: 실제 GS 상품 취급·재고·공급 현황이 아님.
- 데모 결제: 실제 청구 없음.
- 실제 AI / 시나리오 모드: LLM 장애를 숨기지 않음.
- 예약 확정 / 픽업 가능: 별도 사건.
- 고객 수 / 요청 수량 / 발주 수량 / 확보 수량: 서로 다른 지표.

## 본부에 대한 향후 가치: 화면 구현 없음

미식별·미충족 요청이 운영 중 축적되면 상품명/검색 경험 개선, 신규 취급 검토, 지역별 수요 관찰에 활용할 수 있다. 이는 미래 가설이다. 이번 프로토타입이 본부 수요 지도·자동 상품 기획·정확한 판매 예측을 제공한다고 발표하지 않는다.

후속 확장: 사진·링크·레시피, 인근 점포 합산, 임박 재고 역매칭, 판매·수령 결과 기반 추천 개선. 사용자 검증과 실제 업무 연동이 선행돼야 한다.

## 제출 설명에 포함할 것

문제 가설, 구현한 사용자 흐름, 에이전트가 필요한 두 지점, 코드로 강제한 거래 규칙, 실제 모델/DB 실행 증거, 가상 데이터와 모의 결제의 범위, 비용·접근 제한, 본부 활용을 포함한 향후 가치.

## 시연에서 밝혀야 할 전제

모든 공급·결제·입고 데이터는 모의이며 모델 live/fixture 모드를 명확히 표시한다. 상태 설명은 모델의 제안과 실제 완료를 구분한다. 48시간 수령 기한과 구매 의사 유효기간은 별개다. 참고한 실제 점포와 구분해서 설정한 모의 영업시간·신선도 처리, 시연 viewport, 심사 접근 방식은 13번 R-15/R-30/R-37/R-39에서 최종 결정한다.

## 입력 도움과 서비스 가치 설명

고객은 `민음사 빵을 찾고 싶어`, 경영주는 `미확보 요청만 보여줘`처럼 말할 수 있음을 26번 예시로 보여준다. 소재는 goal 실행 당시 재조사하며 특정 시점의 인기를 영구히 주장하지 않는다.

소개 문구: **“원하는 말은 상품으로, 모인 수요는 사장님의 쉬운 판단으로.”** 찾지 못한 니즈도 정제해 남겨 미래 상품·지역 수요 분석의 근거가 될 수 있음을 설명한다. 정확 매핑과 대체 추천, 구매 확약과 관심 신호는 구분한다. `비슷하지만 다른 상품이에요. 맛과 용량을 확인해 주세요.`처럼 차이를 드러내고 재확인·동의 없이 바꾸지 않는다. 경영주는 `처리된 항목은 모아 보고, 필요한 예외만 확인하세요.`로 설명하되 실제 자동발주 조건/예외는 함께 표시한다.

[27번](27-service-values-and-guardrails.md)의 실패 사례도 시연한다. API 장애를 품절로 표시하지 않기, 대체 거절 후 원래 흐름 복귀, 중복 검토에도 승인/발주가 늘지 않기, 정책 해제 후 자동발주 중단을 확인한다. 인근 점포·대체 상품 발주 제안은 선택 부가 기능이며 구현 여부를 밝힌다. 본부 데이터 분석은 향후 가치이고 이번에 본부 화면을 구현했다는 뜻은 아니다.
