# 고객·경영주 UX와 자연어 품질 검증

최초 구현 기준. 제품 요구의 ‘바로 운영해도 좋을 품질’은 모의 서비스 범위에서 완결된 사용자 경험·오류 복구·정합성을 뜻한다. 실제 GS·청구·실물 배송/폐기 운영의 적합성을 인증한 것으로 보고하지 않는다.

## 고객과 경영주 독립 브라우저 QA

customer-qa와 merchant-qa는 서로 다른 agent ID이며 각 대상 기능 구현자와도 분리한다. 가용 슬롯이 적으면 순차 수행한다. [UX 감사 스킬](../.agents/skills/wanna-gs-ux-audit/SKILL.md)을 사용한다. 화면을 설계한 사람이 설계 의도를 확인한 것과 사용자가 처음 만난 화면을 탐색하는 검사는 별개다.

| 관점 | 실제 브라우저에서 확인할 내용 |
|---|---|
| 고객 모바일 | 의도 입력·추가 질문·후보 거절/정정·상품 확인·실제 점포 위치/목록 선택·동의·요청·상태·입고 알림·수령 기한 |
| 고객 예외 | 없는 상품·모호한 표현·모델/네트워크 실패·뒤로가기/새로고침·연타·늦은 응답·만료·지도 장애 |
| 경영주 데스크톱 | 상품별 묶음→고객별 요청 상세·미식별·근거·자연어 수정·이번만/지속 정책·예산/조건·수동/자동 실행 결과·입고/수령 |
| 경영주 예외 | stale 제안·조건 변경·부분 실패 정책·중복 승인·예산 재검증·공급 제한·실행 재개·미수령 |
| 역할 교차 | 같은 데모 세션의 요청/발주/예약/알림 일치, 다른 세션 격리, 역할 권한·점포 범위 |
| 공통 UX | 가독성·반응형·키보드 focus·입력 label·오류 후 다음 행동·빈/로딩/실패 상태·모의 표기 |

QA는 초기 Preview shell, 기능 통합 G4, 릴리스 Preview G5, 제출 G6에서 적용 범위를 달리 검사한다. 초기 fixture 화면은 live 기능 통과가 아니다. QA별 독립 profile/context에서 같은 seed를 사용하며 각자 한 탭에서 고객/경영주 역할을 전환한다. 서로 다른 profile 사이 DB 공유를 가정하지 않는다. 각 실행은 `research_version`, `catalog_version`, `scenario_version`, `eval_version`, seed·프롬프트·model/context 버전과 사용한 case ID를 남긴다. 버전이 바뀌면 영향받은 결과를 stale 처리한다.

사전 seed/가상 시계 설정은 테스트용 로컬 명령으로 가능하나 평가할 사용자 경로를 API 호출로 건너뛰지 않는다. 실제 화면을 보고 입력·선택·새로고침하며, DB/event 관측은 화면 결과 검증을 보강한다. [조사 기반 시나리오](24-market-research-and-scenario-design.md)의 대표 정상·모호·미식별·재고/공급 제한 family를 기능 통합부터 두 역할 QA까지 이어서 쓰되, 보호 holdout의 정확한 발화를 사전 QA에 노출하지 않는다. screenshot 한 장, HTTP 200, console 오류 없음만으로 성공하지 않는다.

## UX 판정과 증거

필수 여정 성공, 알림·금액·기한·현재 상태의 정합성, 상품 집계와 고객 상세의 수량/상태 일치, 오류 후 회복, 역할/세션 분리가 필수다. 막히는 버튼·잘못된 결제/수령 표시·필수 여정 불가·정보 누락으로 사용자가 다음 행동을 알 수 없는 문제는 릴리스 차단이다. 단순 장식 취향은 근거 있는 후속 과제로 둘 수 있다.

[QA 보고서](templates/ux-eval-report.md)에 URL/deployment/source SHA, 정책/seed/model/mode, viewport/browser/profile, persona 목적, 실제 입력·행동·관측, console/network·trace/screenshot·DB/event 증거, 재현 빈도·심각도·수정 PR·재검증을 기록한다. 브라우저 도구가 없으면 실제 UX 검증 완료라고 쓰지 않는다.

## 자연어 검증 범위 설계

모든 자연어 문장을 완전하게 커버한다는 보장은 하지 않는다. 평가셋의 범주·분모·실패·미검증 범위를 명시한다. 코드 커버리지, 한국어 발화 검증 범위, 업무 불변식, 도구 권한, 지연/비용을 별도로 본다.

초기 기본안은 고객 300개 이상, 경영주 120개 이상 고유 발화/대화 사례다. 정확한 규모·각 범주 최소 사례·합격선은 PLAN-READY에서 ADR로 조정할 수 있지만 기준선 실행 전에 고정하며 결과를 본 뒤 줄이지 않는다. 200개 이상 SKU 각각의 명확한 이름/ID 검색 가능성은 별도 결정적 상품 목록 검사로 보장하고, 자연어 eval을 쉬운 상품명 반복만으로 채우지 않는다. 이 표본은 정의한 범주에 대한 유한한 평가이며 모든 한국어 자연어 표현의 성공을 보장하지 않는다.

| 고객 축 | 경영주 축 |
|---|---|
| 정확명·브랜드/맛/용량·속성 조합 | 포함/제외·카테고리·수량·금액·예산 |
| 별칭·유행 표현·띄어쓰기·오타·자모·한영 혼용 | 이번만/앞으로·이전 변경 복원·문맥대명사 |
| 브랜드 생략·모호한 범주·후보 여러 개 | 저장 기준 없는 모호한 지시·상충 조건·우선순위 |
| 없는 상품·트렌드 미등록·후보 거절·후속 정정 | stale proposal·데이터/정책 변경 후 지시 |
| 수량/가격/점포가 섞인 문장 | 제한 초과·권한 밖 명령·실행과 제안 혼동 |
| 긴 입력·잡음·범위 밖 복수상품/이미지/링크 요구 | 긴/불완전 지시·연속 수정·중복 실행 |
| 프롬프트 주입·가짜 SKU 요구·도구 오용 | SQL/URL/역할 위조·정책 무시 요구 |

모든 축의 전 조합을 곱해 무한 테스트하지 않는다. 위험한 조합은 명시하고 나머지는 대표/쌍별 조합으로 설계한다. 각 범주에 명확 성공·확인 필요·미식별/거절·복구의 허용 행동을 지정한다. 실제 사용자 필요·검색/재고 어려움·시장/트렌드 조사 사례에서 일부 범주와 시나리오 묶음를 도출하고, 안전·권한·경계 사례로 보완한다. 연구에서 새로 확장한 문장은 `synthetic_expansion`으로 표시하며 실제 고객이나 경영주의 발언으로 제시하지 않는다.

## 데이터 분할·독립 정답

개발(dev), 후보 비교(validation), 최종 holdout을 구분한다. 시작안은 60/20/20이며 PLAN-READY ADR로 기준선 전에 조정할 수 있다. split은 문장 단위 무작위 추출이 아니라 `scenario_family_id`와 `paraphrase_family_id`를 포함한 `split_group_id` 단위다. 같은 사용자 필요·의도·상품/상태 조합에서 파생한 의미상 동등 문장, 번역/오타/말투 변형이 여러 split에 흩어지면 실패다. 각 핵심 범주의 표본 수와 분모를 평가자가 검사한다.

정답은 존재 SKU 집합·추가 질문 필요·미식별·구조화 명령·금지 도구/동작이다. 각 eval case는 별도 `eval_case_id`를 갖고 `research_case_id`와 `scenario_id` 출처·변경 이력, `utterance_origin`, 기대 행동, 금지 행동, 판정 근거를 기록한다. 조사 사례의 관찰, 실행 시나리오, 채점용 eval case를 같은 레코드나 같은 문장으로 취급하지 않는다.

상품 카탈로그 자체는 앱이 알아야 하는 공개 입력이며, holdout 발화와 정답을 프롬프트 예시·별칭에 복사하는 것은 금지한다. 평가자와 실험자를 분리한다. 최종 holdout은 실험자와 feature 구현자가 보지 않은 family를 nl-evaluator가 독립적으로 큐레이션해 접근·노출 이력을 보호한다. 최종 holdout을 보고 튜닝했다면 사용한 사례를 regression으로 옮기고 독립 새 holdout을 구성해 노출/교체 이력을 남긴다. 재검사를 위해 같은 문제를 무작정 다시 실행한 것은 새로운 holdout이 아니다.

## 지표와 최소 품질

- 확정 불변식: 허구 SKU 실행, 무권한 도구 실행, 동의 없는 접수/결제, 수량·금액 제한 위반 허용 0건. 로컬 서비스가 거래를 최종 차단했는지와 모델이 잘못 제안했는지를 별도 측정한다.
- 검색: 상품 목록 검증 범위, Recall@k, 명확한 요청의 최종 올바른 후보/선택 유도율, 잘못된 후보 확정 유도.
- 대화: 모호함 확인·미식별 판정·후속 정정·불필요 질문/과도한 거절 비율.
- 경영주: intent/scope/조건 필드 정확도, 이번만/지속 구분, 실행 전 검증 결과.
- 운영: 모델/프롬프트/context/검색과 research/catalog/scenario/eval 데이터 버전, 재시도·스키마 실패·P50/P95 지연·호출/토큰 사용량.

품질 문턱의 시작안: 명확 사례와 경영주 핵심 명령 95% 수준, 모호/미식별 허용 행동 90% 수준을 검토하되 실제 평가 전 데이터 난이도·서비스 흐름에 맞춰 채택한다. 이 숫자는 실행 결과나 사용자 직접 확정값이 아니다. 전체 평균 외 범주별·최악 범주와 표본 수/분모를 보고한다. 한두 사례 차이를 통계적 개선으로 과장하지 않는다.

별도 두 수준을 정한다: 필수 정상 기능/보수적 실패를 보장하는 출시 최소 기준과 더 나은 해석/검색을 위한 개선 목표. 둘 다 기준선 전 고정한다. 개선 목표에 못 미쳐도 최소 기준이 충족되면 23번의 중단 정책으로 한계를 남기고 출시 가능하다. 최소 기준·불변식 실패는 실험 포기 사유로 면제하지 않는다.

## 구현 방식과 참고

거래/권한은 결정적 코드·DB 검사로 채점하고 대화 적절성은 정답 집합과 독립 검토를 함께 사용한다. LLM judge 단독 찬성으로 필수 기능을 통과시키지 않는다. 실험·후보 비교·최선 버전 유지·중단은 [23번](23-nl-experiment-loop.md)을 따른다.

[Playwright Best Practices](https://playwright.dev/docs/best-practices)와 [Assertions](https://playwright.dev/docs/test-assertions)는 사용자에게 보이는 동작, 격리, 안정된 locator와 재시도 가능한 assertion을 설계할 참고다(2026-09-20). 구현 시 현재 API를 확인한다. 외부 사이트 자체 품질을 반복 테스트하지 않고 앱의 경계/fallback을 검증한다. 자연어 평가는 [OpenAI evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices)를 참고하되 별도 유료 평가 서비스를 필수로 추가하지 않는다.

## 디자인·발음·카피 검증

[26번](26-design-and-brand-guide.md)의 UX-B01~10을 AC-30으로 검사한다. 첫 진입과 직접 링크 진입의 브랜드/발음, 고객과 경영주 역할 구분, 좁은 화면·글자 확대·키보드·대비·화면 읽기, 실제 상태에 맞는 제목/설명/행동을 확인한다. ‘원하지쓰’ 안내는 눈에 보이는 텍스트여야 한다. 모의 결제 실패나 발주 승인만 된 상태에서 예약/픽업 성공 카피를 보여주면 실패다.

초기 shell에서는 가능한 브랜드·기본 레이아웃 검사만 적용하고 아직 없는 제품 흐름을 요구하지 않는다. 최종 QA는 상태별 실제 데이터와 화면을 대조한다. 독립 에이전트의 읽기 검토를 실제 인간 사용자 발음·이해도 실험으로 보고하지 않는다. 이번 문서 작성에서 실제 앱의 AC-30은 아직 실행하지 않았다.

## 서비스 가치와 편의성 회귀

D-37/43·CORE-25/26·AC-31/32와 [27번 VAL-01~08](27-service-values-and-guardrails.md)을 적용한다. 정확 검색·대체 후보·미충족 분류를 각각 평가하고 상품 추천 개선으로 기존 정상 경로 실패를 상쇄하지 않는다. 고객의 질문/필수 조작/완료 시간과 경영주의 상품→고객 상세 확인·승인/화면 이동/중복 알림·자동발주 정상 성공을 같은 업무량에서 비교한다. 기준선 전에 수치 문턱·허용폭을 ADR로 정하고 결과에 맞춰 낮추지 않는다.

동의 없는 대체·가짜 SKU·수요 오염·초과/중복 발주·권한 침해는 허용 0건이다. API 오류를 미식별 데이터로 넣거나 모든 요청을 보류하는 결과도 실패로 잡는다. 추가 최적화 종료는 필수 기준 면제가 아니며 보호 holdout의 공개 예시 오염을 검사한다.

## 공개 oracle 과소포함 오류의 버전 관리

[ADR008](decisions/ADR-008-public-oracle-equivalence.md)의 두 공개 oracle slot은 관측 가능한 같은 이름/브랜드/500ml에 맞는 두 상품 중 하나 또는 둘 모두의 고객 확인 후보를 허용하도록 정정한다. 후보 집합은 SKU 자동확정이나 거래 병합이 아니다. 원래 실패와 새 파생 점수를 구분하고 모든 비교 관측에 동일 규칙을 적용한다. 분모·합격선·확인/동의·다른 용량 오류·보호셋과 최종 QA는 유지하며, 이 예외 밖의 정답은 바꾸지 않는다.
