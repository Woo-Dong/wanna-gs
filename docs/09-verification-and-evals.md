# 검증과 평가 계획

상태: 계획. 아래 항목은 아직 실행하지 않았다. 완료 시 [PROGRESS.md](PROGRESS.md)에 실제 증거를 연결한다.

## 증거 구분

- `unit`: 순수 업무 함수 검증.
- `integration`: 격리된 실제 sql.js SQLite와 로컬 업무 서비스·snapshot 저장/복원 검증.
- `e2e-fixture`: 고정 모델 응답을 사용하는 브라우저 흐름.
- `e2e-live`: 실제 모델·DB·배포 URL을 사용하는 브라우저 흐름.
- `eval`: 정답/판정 기준이 있는 자연어 품질 평가.

고정 응답 결과를 live로 보고하지 않는다. 테스트 미실행, 실패, 차단을 통과와 구분한다. 구현 오류를 숨기려고 인수 기준을 약화하지 않는다.

부분 배정·취소·결제 실패 후 해제 등의 상세 정답은 미정 정책 결정 후 사례에 반영한다. 임시 구현의 동작을 정책 정답으로 삼지 않는다.

AC-01~AC-18과 AC-20~AC-31은 관련 기능이 존재하는 각 게이트에서 적용 범위를 정한다. AC-19만 G6 전용이다. G0~G5에서는 `pending_g6`로 기록하며 skip이나 실패를 PASS로 바꾸는 근거로 쓰지 않는다. G6에서는 제출할 정확한 Vercel deployment/source SHA에서 실제 DB와 실제 앱 LLM을 사용한 성공·예외 경로 증거가 없으면 AC-19는 통과하지 않는다.

AC-28의 실행 기본 한도는 [23번](23-nl-experiment-loop.md)과 같이 고객/경영주 각각 기준선 이후 후보 최대 6개, 전체 최대 12개이며 같은 역할에서 연속 3개 후보가 사전 개선 기준을 충족하지 못하면 추가 최적화를 멈춘다. PLAN-READY ADR에서 실제 잔량과 반복 계획에 맞게 기준선 전에 조정할 수 있다. 허구 SKU·동의·권한·수량 같은 필수 오류는 한도 도달로 면제하지 않는다.

## 단위 테스트

발주 가능 수량, 묶음 단위, 최소 수량, 가격·금액, 예산, 요청 상태별 집계, 동의 조건 비교, 48시간 경계, 상태 전이, 정책 범위. 낮은 영향의 표시 문구를 그대로 복제하는 테스트보다 거래 불변 조건에 집중한다.

## 통합 테스트

실제 테스트 SQLite에서 트랜잭션·고유 제약·재전송·순차 배정·예산 재검증 사용·stale proposal·세션 격리를 확인한다. 테스트 종료 후 해당 테스트 세션만 정리한다. 제출용 DB 전체를 지우지 않는다.

## 핵심 E2E 시나리오

1. 정확한 상품 요청 → 경영주 수동 묶음 승인 → 공급 확정 → 자동 모의 결제 → 입고 → 수령.
2. 활성 자동발주 정책 → 조건 충족 품목 자동 처리 → 예외 품목만 묶음 표시.
3. ‘샌드위치 빼고 5만 원 이내’ → 조건·정확한 합계 → 일괄 승인.
4. 상품 식별 실패 → 미식별 보존 → 경영주 조회, 정형 수요에는 미포함.
5. 각 1개 요청한 3명, 공급 2개 → 순서대로 2명 예약, 나머지 대기.
6. 요청 5개, 최소 발주 6개 → 자동발주 없음.
7. 동의 후 가격 변경 → 자동 결제 중단.
8. 입고 전/후 구분 → 가상 시계로 48시간 경계 확인.
9. DB 상태를 유지한 채 새로고침·역할 전환·같은 브라우저의 새로고침 후 확인.

## LLM 평가

개발 사례와 최종 평가 사례를 분리한다. 평가 규모의 초기 기본안은 [21번](21-ux-and-natural-language-quality.md)의 고객 300개 이상·경영주 120개 이상이다. PLAN-READY에서 범주 난이도·호출 한도를 근거로 ADR 조정할 수 있으나 기준선 전에 고정하며 결과를 보고 축소하지 않는다. 이 유한 표본은 모든 자연어 표현의 성공을 보장하지 않는다.

상품 식별: 정확한 이름, 띄어쓰기/오타, 별칭, 모호한 종류, 맛·용량 차이, 후보 없음, 후보 거절 후 정정. 실제 필요·탐색/재고 어려움·시점이 있는 시장/트렌드 조사 사례에서 시나리오 묶음를 파생하고, 새 문장은 `synthetic_expansion`으로 표시한다.

경영주: 제외 상품군, 예산 제한, 수요만큼, 직전 변경 복원, 이번만/앞으로, 저장된 기준 없는 모호한 지시, 서로 모순되는 제약.

측정: 후보 Recall@k, 잘못된 확정/가짜 상품 ID 수, 미식별 처리, 질문 적절성, 구조화 조건 정확도, 제약 위반 실행 수, 응답 시간, 호출 수·토큰·비용. 같은 의미/패러프레이즈 family는 한 split에만 두고 최종 holdout은 독립 평가자가 보호한다. 실제 측정 전에 수치 성능을 주장하지 않는다. 전체 점수 목표는 eval 세트 확정 시 기록한다. 가짜 상품·무권한 실행·초과 배정 등 핵심 불변 조건 위반은 제출 차단 사유다.

## Vector RAG 채택 판단

동일한 평가 세트에서 기본 검색과 하이브리드 검색을 비교한다. 후보 회수·정확성·미식별 판단이 개선되는지, 추가 API·시간·운영 비용이 허용되는지 기록한다. 벡터 기능의 존재만으로 검색 성공이라고 평가하지 않는다.

## 실패 주입과 관측

OpenAI 429/타임아웃/잘못된 JSON, 존재하지 않는 상품 ID, SQLite/snapshot 저장 실패, 공급 조건 변경, 중복 이벤트를 재현한다. 오류 메시지는 원인과 재시도 가능 여부를 구분하며 성공 메시지로 덮지 않는다.

증거는 예를 들어 `artifacts/verification/<run-id>/`에 명령 결과·평가 JSON·스크린샷·요약으로 남길 수 있다. 비밀값은 제거한다. 스크린샷만으로 DB·LLM의 정확성을 입증하지 않는다.

## 계층적 검증과 독립 판정

영역 구현자가 자체 단위 검증을 수행한 뒤 별도 검증자가 요구·반례·실행 결과를 확인한다. G0 계약 → G1 단위 → G2 실제 의존성 영역 통합 → G3 인접 영역 통합 → G4 수직 브라우저 흐름 → G5 전체 시스템/eval → G6 제출 URL의 순서와 증거 규칙은 [14번](14-agent-development-loop.md)을 따른다. 해당 작업에 의미 없는 레벨은 근거를 기록하며 필수 AC를 생략하는 용도로 쓰지 않는다.

### 조사·시나리오 자료의 게이트별 사용

초기 조사에서 공통 상품 목록와 시나리오 묶음를 만들고, 각 기능의 G0에서 그 기능에 필요한 최신 사용자/시장/공식 기술 근거를 확인한다. 낮은 근거는 가설로 표시해 독립 검토하며 사람·인용·재고 사실을 발명하지 않는다. 실패가 오래된 상품/트렌드/기술 가정에서 비롯됐다는 증거가 있을 때 해당 조사 사례만 갱신한다. 무제한 최신 자료 탐색은 게이트 통과 조건이 아니다.

| 게이트 | 조사·데이터 사용과 증거 |
|---|---|
| G0 | 기능별 조사 요약, source/date/evidence→설계·데이터·테스트 매핑, 적용 research/catalog/scenario/eval 버전과 case ID |
| G1 | dev split의 feature unit 사례와 결정적 catalog/lineage 검사. holdout 발화 사용 금지 |
| G2 | 같은 버전의 seed·희소 availability·정상/예외 시나리오로 실제 DB/서비스 통합 검사 |
| G3 | 고객↔경영주↔DB/NL 경계에서 공유 시나리오 상태·오류·권한·수량 정합성 검사 |
| G4 | 조사 기반 시나리오 묶음의 대표 합성 발화로 실제 브라우저 수직 흐름 검사. 보호 holdout 내용 비노출 |
| G5 | 선정 최선 버전에 전체 regression/validation, 독립 holdout, customer-qa·merchant-qa, 운영 감사 수행 |
| G6 | 동일 선정 버전이 제출 deployment에 반영됐는지 확인하고 대표 live 사례와 AC-19를 검증 |

각 보고서에는 `research_version`, `catalog_version`, `scenario_version`, `eval_version`, seed·policy·프롬프트·model/context 버전과 split hash를 기록한다. final holdout은 같은 research taxonomy와 출처·변경 이력을 공유할 수 있지만 개발/UX에 사용한 정확한 문장을 재사용하지 않는다.

### 테스트 정답과 품질

- 기대값은 확정 정책에서 도출한다. O/R 미정 결과는 17번의 위임 결정·두 검토·ADR 채택 후 기대값으로 고정한다. 단독 추측이나 사람 답변 대기로 대체하지 않는다.
- 수량 보존·가짜 ID 금지·권한·동의·기한은 코드/DB로 검증한다. LLM judge만으로 통과하지 않는다.
- 모호한 자연어는 단일 정답 대신 허용 후보/질문/미식별의 행동 집합을 정의한다.
- seed 생성과 정답/holdout 검토 역할을 분리한다. 개발 예시를 최종 평가로 재포장하지 않는다.
- 조사 사례의 관찰, 실행 시나리오, eval case를 별도 ID로 유지한다. source 문장을 synthetic 발화로 바꾸었으면 실제 인용이 아니라는 origin을 남긴다.
- 모델/프롬프트/샘플 수/반복 수/품질·지연 문턱을 사전에 기록한다(R-33). 합격 수치는 목표 실행에서 사전 자율 채택한다. 평가 결과를 보고 통과시키려고 낮추지 않는다.
- D-43에 따라 다중 사용자 동시성 시험은 제외한다. 단일 탭 반복 명령·snapshot 실패·reset 뒤 늦은 모델 응답을 검사하며 동시성 검증을 했다고 보고하지 않는다.
- 48시간을 실제로 기다리지 않는다. 공통 데모 clock을 주입해 직전/정각/직후를 검사한다.
- 커버리지 비율만으로 충분하지 않다. 무검증 성공·테스트 0개·필수 skip·전부 mock·flaky 재시도 성공을 별도로 점검한다.

## API 사용량 한도와 검증 예산

[18번](18-environment-preflight.md)의 split·반복·후보·도구 호출 수·재시도 기준으로 예산을 계산하고 final holdout/G6 호출분을 먼저 예약한다. 429는 제한된 backoff와 저장된 진행 위치로 재개한다. provider 일/월 한도 소진을 테스트 실패나 정확도 향상으로 혼동하지 않는다. 한도 때문에 사전 합격선을 낮추거나 미실행을 PASS로 표시하지 않는다. 미실행/transport failure 분모와 모델 응답이 있는 정확도 분모를 함께 보고해 실패를 숨기지 않는다.

## D-43 검증 범위 전환

29번의 P06/P07·G1~G6 표를 적용한다. 기존 DB란 실제 sql.js SQLite이며 거래 검증은 로컬 서비스다. 클라우드 PostgreSQL·다중 사용자 경합·서버 거래 인증·다른 기기의 상태 공유는 요구하지 않는다. QA 담당자는 서로 다르되 각자 한 탭에서 고객→경영주→고객을 전환해 동일 seed 시나리오를 검사한다.

추가 필수 사례: WASM/seed 로딩 실패, SQLite FK/rollback, export/import, IndexedDB 저장 실패 시 성공 미표시와 마지막 사본 복구, 새로고침 보존, schema/seed 불일치 안내·초기화, Preview/Production origin별 독립 초기화, reset 후 늦은 LLM 응답 거절. DB 자산에 비밀값/holdout 정답이 없어야 한다. 전체 200개 이상 상품과 서버 카탈로그의 SKU/hash 일치를 검사한다. 실제 SQL·브라우저 snapshot·live 모델의 증거를 각각 남긴다.
