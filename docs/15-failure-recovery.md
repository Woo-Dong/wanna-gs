# 실패 분류와 복구 절차

상태: 구현 시 적용할 복구 설계. 현재 실행 중인 자동 복구 서비스는 없다. 앱의 오류 처리와 개발 에이전트의 오류 수정은 서로 다르다.

## 두 종류의 루프

- 앱 실행 오류: 서버가 사용자에게 안정된 오류·다음 행동을 반환하고 저장된 실행 상태를 보존한다. LLM이 실패했다고 자동으로 코드를 수정·배포하지 않는다.
- 개발/검증 오류: 복구 에이전트가 테스트 실패를 재현·진단하고 허용된 파일을 수정한 후 독립 검증과 상위 통합 검증으로 돌아간다.

## 오류 분류와 책임

| 분류 | 대표 상황 | 자동으로 가능한 처리 | 멈추거나 결정할 지점 |
|---|---|---|---|
| 요구사항 | 부분 배정·취소 정답 미정, 서로 다른 명세 | 충돌 위치·영향·선택지 정리 | 위임 범위는 17번으로 자율 해결. 확정 불변식 충돌·외부 권한만 별도 차단 |
| 환경/접근 | 로그인·권한·네트워크·유료 크레딧 없음 | 환경 진단, 독립 테스트/fixture 개발 계속 | 권한·요금 필요 시 관련 호출 차단, live 성공 주장 금지 |
| 빌드/코드 | 타입 오류, 불법 상태, 잘못된 화면 | 재현 테스트·최소 수정 | 관련 게이트 통과 전 통합 금지 |
| 계약/통합 | 필드·단위·enum·오류 의미 불일치 | 원본 계약 대조, 양쪽 영향 분석 | 계약 소유자가 버전과 소비자를 함께 수정 |
| 데이터/마이그레이션 | seed FK 오류, 마이그레이션 실패 | 격리 DB 재현·전방 수정안 | 제출 DB reset/파괴적 복구를 자동 해결책으로 사용하지 않음 |
| 동시성/재전송 | 중복 발주·배정·예산 초과 | 동시 요청 재현, DB 제약/트랜잭션 수정 | 단일 요청 성공만으로 해결 판정 금지 |
| LLM | timeout, 429, 스키마 위반, 없는 상품, 지시 주입 | 제한 재시도·출력 거절·안내·평가 | 수량/권한/동의 불변식은 완화하지 않음 |
| UI | 로딩 고착, 화면만 성공, stale 상태 | 서버 상태 재조회, 오류·다음 행동 표시 | 화면 캡처만으로 DB 성공 판정 금지 |
| 배포 | 환경변수/region/스키마 불일치 | 로그·revision 비교, 호환되는 앱 버전 복구 | 앱 복구와 DB 복구는 별개, 호환성 검증 |
| 에이전트 협업 | 중복 작업, 파일 충돌, 죽은 작업 소유권 | 실행 상태 확인·인계·재배정 | 이전 실행/변경 확인 전 같은 변경 동시 실행 금지 |
| 검증 자체 | flaky, fixture 누수, 기대값 오류 | 격리·정답 근거 재검토·실행기 수정 | 테스트 삭제/skip/기준 완화로 성공 처리 금지 |

## 개발 실패 처리 순서

1. 기록: 실패한 task/gate/AC, 코드·환경 fingerprint, 입력, 기대/실제, 로그 위치를 [실패 보고서](templates/failure-report.md)에 남긴다. 비밀값·불필요한 원문 개인정보를 제외한다.
2. 영향 격리: 마지막 유효 게이트까지 보존하고 실패한 부모와 영향받은 후속 작업을 중단한다. 무관한 하위 작업은 계속한다. 공유 파일의 작성자 잠금을 확인한다.
3. 재현: 가장 작은 입력과 실제 필요한 의존성으로 재현한다. 공급 경쟁 문제는 실제 DB에서 경합을 만들고, LLM 품질은 모델/프롬프트/사례를 고정한다.
4. 정답 확인: 독립 검증자가 명세에서 기대 결과를 도출한다. 요구사항 공백이면 버그로 단정하지 않고 17번에서 ADR 초안·두 검토·채택 후 기대값을 확정한다. 사람 답변 대기를 기본 경로로 두지 않는다.
5. 회귀 사례와 가설: 재현 테스트가 수정 전 실패하는지 확인한다. 환경 문제라면 무의미한 앱 테스트를 만들지 않고 연결 진단을 남긴다. 한 번에 검증할 원인과 최소 변경 범위를 정한다.
6. 수정: 영역 소유자가 수정하거나 조정자가 복구 담당에게 소유권을 이전한다. 같은 파일을 두 에이전트가 동시에 고치지 않는다.
7. 재검증: 재현 사례 → 해당 단위/영역 통합 → 영향받은 영역 간 통합 → 필요한 E2E/eval/배포 확인. 독립 검증자가 다시 판정한다.
8. 종결/인계: 원인, 변경, 통과 증거, 무효화/재생성한 게이트, 잔여 문제를 기록한다. 재현되지 않는 실패는 원인 불명으로 남기고 통과 횟수만으로 닫지 않는다.

## 재시도와 회로 차단

아래 숫자는 개발용 운영 기본안이며 사용자가 정한 토큰/시간/비용 예산을 대신하지 않는다. 구현 시작 시 설정 파일에 기록한다.

- 일시적 읽기/LLM timeout·429·5xx: 최초 포함 최대 3회, provider의 Retry-After·잔여 실행시간·사용량을 확인한 제한적 backoff/jitter. 401/403·크레딧 소진·입력 오류·모델 미지원은 같은 요청을 반복하지 않는다.
- 모델 출력 형식 오류: 허용할 경우 수정 요청 1회. 다시 실패하면 안정된 오류로 반환한다. 존재하지 않는 상품/권한 초과 도구는 실행하지 않는다.
- 거래 변경 timeout: 성공 여부 불명확이면 먼저 실행 ID/멱등 키로 조회한다. 같은 키로 결과를 재사용하거나 안전하게 이어가며 새로운 키로 무작정 재발주·재결제하지 않는다. DB deadlock/serialization 재시도는 전체 트랜잭션이 롤백됐는지 확인한 후 제한한다.
- 개발 실패: 같은 실패 fingerprint에 새 증거 없이 같은 수정을 반복하지 않는다. 기본 2회 수정-검증 실패 후 진단 담당/독립 검증자가 가설을 재검토한다. 세 번째도 동일 실패가 계속되고 새 원인 증거가 없으면 해당 작업을 내부적으로 차단하고 원인·필요 조건·독립 작업을 기록한다. 이 횟수로 goal 도구의 blocked/paused 상태를 자동 변경하지 않는다. 실제 도구 계약과 사용자 지시를 따른다.
- 오류가 사라질 때까지 무한 호출, 범용 예외 삼키기, timeout 늘리기만 하기, 테스트 skip, fixture로 조용히 전환은 복구가 아니다.

## 부분 성공과 복구 불변식

| 실패 지점 | 복구가 보장해야 할 것 |
|---|---|
| 발주 저장 후 HTTP 응답 유실 | 실행 ID로 기존 발주 반환, 수요/예산 중복 차감 없음 |
| 공급 확정 후 배정 중단 | 공급 버전·배정 합계를 조회해 이어가기, 공급량 초과 금지 |
| 모의 결제 성공 후 예약 처리 중단 | 성공 결제 ID와 예약 생성 연결 복구, 같은 결제 재생성 금지 |
| 예약 확정 후 알림 생성 중단 | DB 트랜잭션 또는 내구성 실행 상태로 알림 보완, 성공 알림 중복 없음 |
| 입고/픽업 알림 재전송 | 최초 pickup_available_at 및 deadline 유지, 48시간 연장 금지 |
| 실행 중 세션 reset | 세대 번호/실행 상태 재검사로 오래된 요청이 새 세션 데이터에 쓰지 못함 |
| 마이그레이션 후 이전 앱 복구 | 스키마 호환성 확인, 불가능하면 전방 수정 또는 검증된 복구 경로 |

모의 결제는 외부 결제사가 없으므로 한 트랜잭션으로 묶을 수 있는 범위를 우선 검토한다. 여러 단계가 꼭 필요하면 단계별 실행 상태를 DB에 기록한다. durable queue를 새 필수 인프라로 추가하지 않는다. 이 문서만으로 분산 원자성이 보장된다고 주장하지 않는다.

## 장애 주입 검증

fixture/live 경계를 표시하고, 반복 가능한 seed와 모의 시계를 사용한다. 아래는 구현 단계의 필수 위험 검증 후보다. 실제 제품 결정에 맞춘 기대값을 G0에서 고정한다.

1. 동일 요청/승인/공급 이벤트를 두 번 및 동시에 전송.
2. 같은 예산·물량을 두 트랜잭션이 경쟁.
3. 저장 직후 응답 유실, 여러 단계 사이 강제 실패 후 재조회·재개.
4. 모델 timeout/429/invalid JSON/가짜 ID/권한 초과 도구 요청.
5. 고객 취소·가격 변경·정책 변경이 진행 중 승인과 경합.
6. 입고 중복, 기한 직전/정각/직후 수령 및 중복 수령.
7. 다른 세션 ID/역할 위조, reset 중 in-flight 실행, 다른 세션 정상 유지.
8. Preview가 제출 DB reset을 시도하는 잘못된 환경 연결 차단.

## 스킬과 서브 에이전트 연결

- [wanna-gs-verify](../.agents/skills/wanna-gs-verify/SKILL.md): 관련 게이트와 증거를 확인하고 독립 검증을 배정한다.
- [wanna-gs-recovery](../.agents/skills/wanna-gs-recovery/SKILL.md): 실패 기록·재현·분류·제한된 수정·회귀 경로를 관리한다.

스킬은 작업 지침이며 스스로 실행되는 서버나 테스트 도구가 아니다. 지원되는 프로젝트 환경에서 발견되는지 확인하고, 자동 발견되지 않으면 해당 SKILL.md를 명시적으로 읽는다. 복구 스킬을 생성했다는 이유로 배포·유료 구매·파괴적 DB 복구 권한이 추가되지 않는다.

## 위임 정책·Git 복구

[wanna-gs-decide](../.agents/skills/wanna-gs-decide/SKILL.md)로 정책 공백을 해결한다. 버그에 맞춰 요구를 낮추지 않는다. 필요한 정책 변경은 ADR·반례·두 검토·영향 테스트를 남긴다. push/PR/merge/배포 응답 유실은 원격 SHA·기존 PR·deployment부터 조회하고 16번 복구 절차를 적용한다.

## 무인 환경과 개선 실험

승인 질문을 생략하는 실행 정책에서도 권한은 자동 생기지 않는다. 파일/네트워크/조직 정책 실패는 환경 차단으로 기록하고 동일 금지 명령을 반복하거나 보호 장치를 해제하지 않는다. 필요한 외부 조치와 재개 지점을 남기고 수행 가능한 독립 작업을 계속한다. 실제 goal의 blocked/usage/budget 상태 전환은 현재 도구 계약을 따르며 첫 실패만으로 강제 종료하지 않는다.

자연어 성능 정체는 23번 실험 중단을 적용하고 기능 결함과 구분한다. 기준선·최선 버전·후보·데이터/split hash·정체 원인을 남긴다. 필수 오류를 ‘최적화 포기’로 면제하지 않는다. 평가 중 429는 제한 재시도, 한도 소진은 외부 차단이며 실패 사례를 분모에서 숨기지 않는다.

## 수정 전후 목적 보존

[card.md](../card.md)와 관련 CORE/유효 ADR을 확인한 뒤 실패 보고서에 원래 사용자 결과·유지할 정상 사례·인접 기능 영향을 적는다. 재현 실패를 고친 뒤 원래 정상 사례와 수정한 실패 사례를 독립 검증한다. 자연어 오류를 모든 요청 거절로 바꾸거나, 중복 처리 오류를 발주 기능 비활성화로 숨기는 변경은 복구 완료가 아니다. 정책 변경은 17번 절차를 따르고 구현·테스트 기대값을 함께 대조한다.
