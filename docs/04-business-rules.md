# 업무 규칙과 불변 조건

아래는 확정 요구를 구현 규칙으로 표현한 초안이다. 미정 정책을 우회해 확정하지 않는다.

## 요청과 수요

- BR-01: 상품 후보는 DB에 존재하는 상품 ID로 제한한다. 고객 확인 전 구매 요청을 만들지 않는다.
- BR-02: 요청은 한 점포·한 상품에 연결한다. 여러 상품 묶음은 제외한다.
- BR-03: 수량은 양의 정수, 금액은 정수 원 단위로 저장·계산한다. 개별 요청의 수량 유효 범위는 설정값으로 정하되 모집 목표/MOQ를 점포 전체 신청 상한으로 삼지 않는다(D-41).
- BR-04: 자동 구매 동의에는 상품·수량·점포·가격·동의 시각·조건 버전을 저장한다.
- BR-05: 미식별·취소·이미 예약된 수량은 신규 발주 대상 미확보 수요에 합산하지 않는다.
- BR-06: 접수 시각은 서버에서 기록한다. 동시 요청 순서는 DB가 부여한 일관된 순번을 사용한다.
- BR-07: 동일 요청의 재전송은 중복으로 세지 않는다. 의도적인 재요청 병합 정책은 O-02와 별개다.

## 발주와 공급

- BR-08: 발주 승인과 공급 확보는 다르다. `submitted`만으로 고객 예약을 확정하지 않는다.
- BR-09: 제안 생성 당시 데이터가 아니라 실행 직전 최신 수요·공급 조건·가격·예산을 재검증한다.
- BR-10: 유효 요청 중 이미 진행 중인 발주에 묶인 수량을 다시 발주하지 않는다. 발주 실패·취소 시 연결 해제 규칙을 명시한다.
- BR-11: 자동발주는 승인된 정책이 활성화된 상품·점포에만 허용한다.
- BR-12: 자동발주 수량은 아직 발주에 연결되지 않은 유효 요청 수량 이하여야 한다.
- BR-13: 최소 수량·묶음 단위를 맞추려면 요청 초과가 필요한 경우 자동발주하지 않는다.
- BR-14: 설정 예산과 발주 조건을 넘는 상품은 예외 묶음으로 분리한다. 여러 동시 실행에도 예산을 초과하지 않도록 예산 사용을 원자적으로 반영한다.
- BR-15: 수동 초과 발주 허용 여부는 O-12다. 자동발주 규칙을 수동 승인으로 몰래 우회하지 않는다.
- BR-16: 발주 제한·공급 종료·예정일은 모의 공급 데이터에 근거한다. LLM이 추정한 값은 실행 조건으로 사용하지 않는다.

## 배정과 모의 결제

- BR-17: 같은 점포·상품 안에서 접수 순서를 유지한다. 정확한 다수 수량/부분 배정은 O-01 결정 후 구현한다.
- BR-18: 배정 합계는 공급 확정 수량을 넘지 않는다. 실제 입고 수량과도 별도로 대조할 수 있어야 한다.
- BR-19: 배정과 물량 차감은 DB 트랜잭션·잠금 또는 조건부 갱신으로 동시성에 안전하게 처리한다.
- BR-20: 상품·점포·수량·가격이 고객 동의 조건과 다르거나 결제 실행 시 동의가 유효하지 않으면 자동 결제를 진행하지 않는다. 동의 유효기간의 구체 값은 O-03에서 정한다.
- BR-21: 모의 결제는 외부 결제사를 호출하지 않는다. 성공·실패는 명시적인 시뮬레이터 결과다.
- BR-22: 결제 성공을 DB에 기록한 뒤 예약 확정 알림을 생성한다. 반복 호출 시 같은 결제를 재생성하지 않는다.
- BR-23: 결제 실패 시 확정 예약 알림을 보내지 않는다. 물량 재배정은 O-06의 정책을 따른다.

## 입고·픽업

- BR-24: 입고가 확인되기 전 ‘지금 수령 가능’이라고 표시하지 않는다.
- BR-25: 픽업 가능 알림 생성과 시작·마감 시각 저장은 일관된 작업으로 처리한다.
- BR-26: 시작 시각 + 48시간이 마감이다. 사용자의 기기 시계나 브라우저 타이머는 권한 판단 근거가 아니다.
- BR-27: 만료 정리 Cron이 지연돼도 API는 마감 경계를 검사한다.
- BR-28: 기한 초과만으로 실제 환불·폐기·재판매가 완료됐다고 표시하지 않는다.

## 경영주 자연어와 권한

- BR-29: 자연어를 허용된 필드·연산으로 변환한다. LLM이 SQL·셸·임의 URL을 실행하지 않는다.
- BR-30: 금액·수량 계산은 서버가 한다. 모델 계산을 그대로 사용하지 않는다.
- BR-31: 이번 제안 수정과 지속 정책 변경은 구분한다. 모호하면 결과가 달라지는 부분만 묻는다.
- BR-32: 승인에는 제안 버전을 포함한다. 오래된 제안을 승인하면 최신 조건으로 재검토한다.
- BR-33: 고객은 경영주 발주·정책·초기화 API를 실행할 수 없다. 역할 확인은 서버에서 한다.

## 시뮬레이션 격리

- BR-34: 모든 거래 변경은 현재 데모 세션에만 적용한다. 다른 시연의 재고·요청·예약을 바꾸지 않는다.
- BR-35: 초기화·시간 이동은 데모 전용 동작이며 사용자가 보고 있는 세션을 명시한다.
- BR-36: 이벤트 ID/중복 방지 키를 갖고 재시도 결과를 재사용한다.
- BR-37: 에이전트 설명에는 사용한 상품·조건·정책 버전을 연결한다. 비밀 토큰이나 내부 추론 전문은 저장하지 않는다.

## 실행과 LLM의 경계

LLM 호출 전에 필요한 데이터 스냅샷을 읽고, 호출을 마친 후 짧은 DB 트랜잭션에서 최신 조건을 재확인한다. 모델을 기다리는 동안 DB 잠금을 유지하지 않는다. LLM 판단이 실패해도 수요·배정·예약 데이터가 부분적으로 손상되지 않도록 한다.

## 규칙을 테스트로 내리기 전

O-03의 대기 동의 기한, R-01의 FIFO/발주 연결 관계, R-03/R-04의 공급·입고 계약, R-07의 가격 기준, R-08의 묶음 원자성이 아직 결정되지 않았다. 해당 G0에서 합의한 뒤 이 문서와 상태/API/테스트를 함께 갱신한다. 확정된 ‘수량 초과 금지·권한 검사·48시간’ 자체를 실패 해결 목적으로 완화하지 않는다.

BR-34의 격리는 거래뿐 아니라 변경 가능한 공급 조건·가격·정책·예산·대화·제안에도 적용해야 한다. 구현 방식은 세션별 레코드 또는 overlay로 결정하고 다른 세션 변경 및 reset 중 오래된 실행을 실제 DB 통합으로 검증한다.

## 추천과 구매 확약의 분리

D-37과 [27번](27-service-values-and-guardrails.md)을 따른다. 추천 노출/선택·미식별 니즈·인근 점포 관심은 현재 점포의 유효 구매 확약 수량이 아니다. 대체 후보를 보여주거나 선택해도 기존 요청의 SKU·점포·동의·접수 순서를 수정하지 않는다. 새 요청에는 상품·수량·점포·가격 확인과 새 동의가 필요하고 기존 요청 전환/취소는 O-02/O-04/O-05에 따른다. 중복 활성 수요·동시 발주는 서버에서 방지한다.

묶음의 변화 없는 재조회는 승인/알림을 반복 생성하지 않는다. 의미 있는 변경은 최신 조건 재검증 대상이다. 활성 자동발주 정책 안에서는 매 건 승인을 추가하지 않고 정책 밖 예외만 요약한다. 편의성 개선을 이유로 권한·예산·수량 검사를 생략하지 않는다.

## 모집 목표와 기한의 분리

D-41: 최소 발주 기준을 달성해도 추가 요청을 받는다. 요청량을 목표값에 맞춰 잘라 저장하지 않는다. 추가 수요를 받았다는 사실은 발주·공급 확보·예약 확정을 뜻하지 않는다. 발주할 때에는 이미 연결된 수량을 제외하고 MOQ·주문 배수·예산·공급 조건을 다시 검사한다. 미발주 잔여 수요는 각 요청의 유효성에 따라 보존한다.

D-42: 모집/발주 가능 시간, 미결제 고객의 구매 동의 유효기간, 입고 후 픽업 48시간은 같은 만료 처리로 연결하지 않는다. 발주 가능 기한 종료만으로 요청·예약을 일괄 만료시키지 않는다. 공급 확보 후 모의 결제 실행 시에도 동의 유효성을 다시 검사한다. 결제 완료·입고 대기 예약에 구매 동의 만료를 소급 적용해 수령 만료로 바꾸지 않는다. 입고 전에는 픽업 시간이 흐르지 않으며, 입고 후 BR-25/26의 시점부터 시작한다. 모집 회차나 새 모집 마감 기능 자체를 추가하는 결정은 아니다.
