# 제품 정의와 범위

기준일: 2026-09-20 · 제품 범위: 확정 / 요구사항 표현: 명세화 초안

## 이름과 목적

- 국문: 원하GS
- 영문: WANNA GS
- 확정 발음: 원하지쓰 (D-35). 첫 화면에 ‘원하지쓰라고 읽어요’를 보이는 글자로 안내한다.
- 의미: ‘살게요’ 이전의 ‘원해요’를 표현하고 기록하는 서비스.

고객이 원하는 상품을 자연어로 요청하면 상품을 식별하고 한 점포에 수요를 모은다. 경영주에게 발주 근거와 다음 행동을 제공하고, 확보된 물량은 접수 순서에 따라 모의 자동 결제·픽업 예약으로 연결한다.

## 문제 가설: 외부 검증 필요

원안은 고객이 원하는 상품을 찾기 위해 점포별 재고를 반복 확인하거나 입고를 추측해야 하고, 경영주는 판매로 이어지지 않은 수요를 충분히 관찰하기 어렵다는 문제에서 출발했다. 잘못된 발주는 재고·폐기 부담으로, 미발주는 기회 손실로 이어질 수 있다는 가설이다.

‘현재 우리동네GS의 예약은 기존 점포 재고에만 가능하다’, ‘POS·발주 시스템에는 판매 기록 외 수요가 없다’ 등의 표현은 실제 서비스·내부 업무 검증을 완료하지 않았다. 발표에서는 확정 사실처럼 단정하지 말고 가설 또는 관찰이 필요한 문제로 설명한다. 실제 GS 발주 정책을 모사했다는 주장도 하지 않는다.

## 이번 구현에서 제외

- 본부 전용 화면, 통계, 다운로드, 수요 지도, 신규 상품 검토 업무 기능.
- 사진·링크 입력, 여러 상품 묶음, 레시피 단위 요청.
- 실행 중 웹에서 신상품을 자동 발굴·등록하는 기능. 자료 준비 단계의 웹 검색은 가능.
- 실제 GS 상품·재고·발주·예약 시스템 연동.
- 실제 결제수단 입력·결제사·금전 거래·실제 환불.
- 인근 점포 수요 합산, 자동 점포 이동, 임박 재고 역매칭.
- SNS 트렌드, 요청 발굴자 배지·크레딧.
- 화면을 닫은 고객에게 전달하는 실제 SMS·이메일·모바일 푸시.
- 판매 성과에 따라 추천을 자동 학습하는 모델. 수령 결과는 남길 수 있지만 학습 루프는 향후 확장.

## 선택 기술 실험

Vector RAG는 pgvector와 임베딩 접근이 가능할 때 기본 검색과 비교하는 실험이다. 사용 여부는 품질·속도·비용 증거로 결정한다. 벡터 검색을 넣지 않았다는 이유로 필수 제품 흐름을 미완료로 처리하지 않는다.

## 성공의 정의

실제 배포 URL에서 고객 요청 한 건을 접수부터 수령까지 처리할 수 있어야 한다. 고객·경영주 화면의 수량·금액·상태가 일치하고 예외가 생기면 원인과 다음 행동을 안내해야 한다. 검증은 [09-verification-and-evals.md](09-verification-and-evals.md)를 따른다.

## 개발 목표 보강

[핵심 요구 요약](CORE_REQUIREMENTS.md)을 모든 작업의 기준으로 쓴다. 초기 사용자 니즈·시장/트렌드 조사에서 약 200개 상품·실제 점포 위치·합성 사용자·자연어 평가 시나리오를 함께 만든다(19/24번). 제품 정상 동작에 더해 자연어 이해·매핑 품질을 기준선 대비 개선하는 목표를 포함한다(21/23번). 정해진 시도 끝에 추가 개선을 중단할 수 있으나 필수 동작·거래 불변식·출시 최소 기준을 면제하지 않는다. 실제 사용자 조사 자료와 합성 발화의 차이를 보고한다.

## 서비스 가치의 구현 범위

D-37·CORE-25에 따라 [27번](27-service-values-and-guardrails.md)을 적용한다. 고객의 말은 seed DB의 존재 SKU와 연결하고, 식별 실패·확인된 미취급 니즈를 정제해 남긴다. 유사 상품은 원상품과 다른 후보로 명시하며 고객 확인·새 동의 없이 요청을 바꾸지 않는다. 품절·공급 제한·시스템 오류를 미식별로 섞지 않는다.

경영주에게는 묶음 요약·예외 검토·승인한 정책 안의 자동발주로 일을 줄인다. 인근 점포 관심이나 다른 상품의 발주 제안은 선택 부가 기능으로 두며 합산 발주·자동 점포 이동은 계속 제외한다. 본부 가치는 데이터 활용 가능성으로만 설명한다. 필수 여정과 편의성 회귀는 AC-31로 검증한다.
