# 역할·공유 맥락·모델 선택

최초 구현 기준. 개발용 서브 에이전트의 책임을 아래 역할로 나눈다. 가용 슬롯과 작업 의존성에 따라 순차 또는 병렬로 배정한다. 앱에서 실행하는 고객·경영주 LLM은 이 개발 역할과 별도로 관리한다.

## 책임과 협업 계약

| 역할 | 책임·주요 산출물 | 협업/경계 |
|---|---|---|
| coordinator | 요구·우선순위·DAG·소유권·결정 원장·종료 판단 | 통합/배포를 직렬화, 자기 증거만으로 통과 금지 |
| customer-ux | 고객 여정·모바일 화면 구조·상품 확인·점포/지도·동의·오류 안내 | customer-fe/be와 화면 상태 계약 |
| customer-fe | 고객 UI·입력/로딩/오류/키보드·API 소비 | 거래 검증은 로컬 domain/service, 서버는 모델 입력 검증 |
| customer-be | 고객 요청/동의·조회/취소의 로컬 서비스와 서버 모델 API | 공유 domain 서비스를 재사용, 정책 복제 금지 |
| merchant-ux | 묶음 수요·예외·일괄 승인·자연어 수정의 업무 흐름 | 불필요한 건별 검토를 줄이는 기준 |
| merchant-fe | 경영주 대시보드·그룹 조작·정책/결과 표시 | merchant-be 및 공통 계약 |
| merchant-be | 제안/정책/발주/입고/수령의 로컬 서비스와 서버 모델 API | 순차 명령·중복·역할·버전 검사 |
| domain-owner | 발주·배정·모의 결제·예약·시간/수량 불변식 | 고객/경영주 BE 공통, 중복 구현 금지 |
| dba | 스키마·마이그레이션·제약·인덱스·seed·SQLite 저장/복구 | 공통 DB 변경 단일 작성자, 정책은 ADR 근거 |
| data-research | 200 SKU·공개 점포·출처 이력·합성 actor·분포 | DBA import, 독립 data reviewer |
| nl-implementation | 상품 검색·속성/별칭·structured output·도구 경계 | 앱 모델/provider·프롬프트 버전 |
| nl-experiment | 실패 분석·가설·후보 프롬프트/검색/데이터 실험 | 23번 적용, holdout 정답 관리 금지 |
| nl-evaluator | 검증 범위·정답·holdout·독립 채점·품질 판정 | 실험자와 같은 후보를 자기 승인하지 않음 |
| customer-qa | 고객 관점 브라우저 E2E·탐색적 UX 검사 | 해당 기능 구현자와 별도 agent |
| merchant-qa | 경영주 관점 브라우저 E2E·업무 부담 검사 | customer-qa와도 별도 agent, 순차 가능 |
| code-reviewer/integrator | 계약·반례·테스트 증거·PR 통합·회귀 | 자기 구현 리뷰 불인정, 공유 merge 단일 담당 |
| method-auditor | 역할·맥락·게이트·실험·종료 규칙 자체의 모호함 감사 | 22번의 한 단계 관리, 읽기/제안 중심 |

작은 작업에서는 UX+FE 등 역할을 한 구현자에게 순차 맡길 수 있다. 그러나 자기 구현의 독립 코드 리뷰·QA·후보 품질 승인은 겸임하지 않는다. DBA가 모든 카피 변경을 승인하거나 모든 문장마다 위원회를 여는 방식으로 운영하지 않는다.

## 공통 Context Manifest

각 작업은 [맥락 양식](templates/context-manifest.md)을 받는다. 전체 대화 복사 대신 현재 유효한 근거와 담당 영역을 전달한다.

필수: manifest ID/hash, CORE/사용자 결정 버전, 적용 ADR 및 폐기/금지 동작, API/schema/state/config·seed/clock·prompt/model/eval 버전, task/branch/base SHA, 의존 담당·파일 소유권, 적용 AC/게이트, 제외 범위.

시작 시 에이전트는 적용 버전을 확인하고 결과에 `consumed_context_hash`를 반환한다. 검증자는 동일한 요구와 버전을 읽고, 구현자와 독립적으로 반례와 기대값을 도출한다.

현재 정책·계약 변경은 조정자가 관련 작업에 통지한다. 영향받은 작업은 새 manifest를 읽고 ACK하며 기존 결과는 stale 처리한다. 영향이 없는 부분까지 자동 재실행하지 않는다. 같은 이름의 오래된 ADR/seed를 받았으면 파일을 확인하고 작업한다.

## 긴밀한 협업 방식

- 직접 메시지/인계는 task ID·입력 버전·관측·결정 필요사항·수정 제안·영향 파일을 포함한다.
- 토론으로 정한 결론은 ADR 또는 task decision log에 남긴다. 채팅만 있는 합의는 통합 계약이 아니다.
- 다른 담당의 파일은 요청으로 변경하고 소유권 이전을 기록한다. 공유 checkout의 branch 전환을 동시에 하지 않는다.
- stalled 작업은 실행/파일 상태를 확인한 뒤 재배정한다. 죽은 작업을 새 이름으로 중복 실행하지 않는다.
- customer UX↔FE↔BE↔DB↔merchant↔NL의 상태/오류/수량·기한 표시를 교차 점검한다. 각 화면이 따로 성공해도 연결 경험이 다르면 G3/G4 실패다.

## 모델 선택: 품질 우선

사용자가 작업별 모델 선택을 허용했다. 실제 tool/catalog에서 사용 가능 모델·reasoning 옵션·모델 override가 가능한지 확인한 후 선택한다. API 가격이나 Enterprise 사용량 차이를 이름만으로 확정하지 않는다. 개발용 Codex 모델과 앱 런타임 API 모델의 인증/사용량은 별개다.

| 작업 | 선호 역량 등급 | 이 환경에서 검토할 예시 |
|---|---|---|
| 고정 형식 정리·단순 검색·검증 가능한 반복 변환 | economy | gpt-5.6-luna, 사용 가능 시 |
| 계약 명확한 일반 FE/BE·자료 검토·테스트 보강 | capable | gpt-5.6-terra 또는 gpt-5.6-sol |
| 핵심 요구 해석·아키텍처·거래/DB/권한·정책 채택·중요 독립 검증·릴리스·운영 감사 | highest suitable available | gpt-6-astra, 작업에 맞는 high 이상 reasoning 검토 |
| 자연어 실험 후보의 단순 생성 | capable | 결과를 별도 평가자가 검사 |
| 평가셋 설계·실패 원인·후보 채택/중단 판정 | high capability | 중요한 판단을 위해 가용 강한 모델 우선 |

이름은 현재 환경 예시다. 특정 모델 부재만으로 모든 개발을 멈추지 말고 동등하게 적합한 가용 모델/상위 모델로 대체해 이유를 남긴다. 적절한 판단 역량 자체가 없으면 중요한 결정을 통과했다고 꾸미지 않는다.

실패 반복·요구 오해·상충 계약·검증 불충분이 보이면 담당 모델/추론 깊이를 승격하거나 작업을 더 작게 나눈다. 단순 비용 절감 때문에 품질 게이트를 낮추지 않는다. `risk_class`, `selected_model`, `reasoning`, `selection_reason`, `escalation`을 작업 계약에 기록한다. 명시적 override를 지원하지 않는 실행 경로에서는 실제 상속 모델을 기록하고 모델을 바꿨다고 주장하지 않는다.

시간/토큰을 충분히 쓰라는 지시는 계획·검증에 투자하라는 뜻이다. 임의의 goal token_budget을 만들거나 유료 API 자동 구매·무료 한도 초과를 승인한 것은 아니다. 불필요한 전체 재검사/무한 토론보다 추가 반례·실제 관측에 사용한다.

## 근거

[OpenAI Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)는 역할별 모델/추론 선택과 상속을 설명한다(2026-09-20 확인). 실제 도구 가용 목록을 우선한다. 역할 배치·품질 승격 기준은 이 프로젝트의 운영 설계다.

## 실행 시점의 기능별 조사

`research-lead`는 [24번](24-market-research-and-scenario-design.md)의 연구 질문과 근거 지도를 관리하고 필요한 영역에 조사 작업을 배정한다. 상품/data-research 외 고객/경영주 UX·BE·DBA·QA도 자기 계약을 결정하기 전 최신 자료를 확인한다. 조사 담당은 질문·출처·확인일·불확실성·권장 설계·case 연결을 넘기고 해당 기능 소유자가 채택을 책임진다. 연구 인원도 실제 슬롯 안에서 순차/병렬 배정하며 영구 상주 에이전트를 늘리는 것이 목적은 아니다. wanna-gs-research 스킬을 사용한다.

## 작업 목적 전달

새 담당자와 재개 담당자는 [card.md](../card.md)와 관련 CORE·유효 ADR을 직접 확인한다. Context Manifest에는 사용자에게 남아야 할 결과, 유지할 정상 사례, 금지할 변화와 읽은 문서 hash를 넣는다. ACK는 문서 이름을 받았다는 응답만으로 충분하지 않으며 자신의 작업 범위·기대 결과를 확인해야 한다. 변경이 없는 긴 문서 전체를 매번 복제하지 않고 관련 기준과 현재 진행 포인터를 전달한다.

## 디자인 전달

UX/FE·고객/경영주 QA는 26번 디자인 기준, 12번 카피, D-35·CORE-24·AC-30을 공통 입력으로 사용한다. 화면별 상태·주요 행동·발음 안내 위치를 인계하며 구현자는 상태별 화면을 만들고 독립 QA는 첫 방문 관점에서 확인한다. 디자인 토큰은 프로젝트 시작값과 공식 자료에서 관찰한 요소를 구분한다.

D-37에 따라 DBA는 27번의 니즈/거래 분리 계약, 고객 담당은 정확/대체 확인, 경영주 담당은 묶음·예외·정책 실행을 책임진다. 독립 QA는 CORE-25·AC-31·VAL-01~08과 편의성 회귀를 검증한다. 원장의 상태 구별과 새 동의 규칙을 context manifest에 연결한다.
