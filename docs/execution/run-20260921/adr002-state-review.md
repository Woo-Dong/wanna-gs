## 판정

**현재 초안 그대로의 채택은 보류한다. 아래 1~5의 계약을 보완한 뒤 2차 검토하면 된다.** 7일 동의, 전량 FIFO, 총 2회 모의 결제, 실패 점유 10분, 사전 승인 자동발주라는 선택 자체를 기각하는 것은 아니다. 정상 복귀를 막거나 같은 물량을 두 번 셀 수 있는 경계가 아직 명확하지 않다. 외부 사용자 판단이 필요한 충돌은 발견하지 않았으므로 조정자가 위임 범위에서 보완할 수 있다.

## 1. [높음] 복수 공급 line 배정과 늦은 결제의 픽업 알림 트리거

초안은 회차 간 공급 잔량을 합산하지만 “입고와 알림 동일 transaction” 및 “입고 line 1회”만 명시한다. 예약이 여러 공급 line을 소비하거나 입고 후 생성될 때 알림 기산점을 결정할 수 없다.

- 반례 A: 요청 A=3. L1에서 2 확보·입고 완료, L2에서 1 확보 후 A 전량 배정·결제. L2가 아직 미입고라면 A는 confirmed이며 pickup_deadline이 없어야 한다. L2의 마지막 1개 입고 때 한 번만 pickup_ready/알림/48시간을 생성해야 한다.
- 반례 B: L1의 잔량 1은 이미 입고됐다. 새 요청 B=1이 명시 동의하고 잔량으로 배정·결제된다. 이후 새 입고 event가 없으므로 입고 event에서만 알림을 만들면 B가 영원히 수령 불가다.
- 반례 C: 결제 실패 점유 중 해당 line의 입고가 완료됐다. 고객 명시 재시도가 성공하면 이미 입고된 전량을 근거로 그 성공 transaction에서 알림을 만들 수 있어야 한다.

보완할 최소 계약: allocation의 source line별 수량·입고 상태를 추적한다. “결제 성공 AND 배정된 모든 수량 입고” 조건이 처음 충족되는 transaction이 pickup_ready·고유 알림·deadline을 함께 생성한다. 트리거는 입고와 결제/배정 성공 양쪽이다. 이미 생성된 알림/deadline은 재실행으로 바뀌지 않는다. 입고 전에 알림을 만들거나 수령 가능으로 표시하면 실패다.

회귀: 위 A/B/C, source line 입고 역순, 새 event ID의 재입고, snapshot 복원 후 재평가. 각 경우 알림 1개·정확한 첫 생성 시각·48시간 직전/정각/직후를 대조한다.

## 2. [높음] 공급 보존식과 진행 중 연결의 해제·재배정 단위

“미확보 연결 해제”, “pool 잔량”, “allocation/reservation 없는 수량”은 방향은 맞지만 서로 다른 상태의 수량을 어떤 축으로 한 번씩 집계하는지가 없다. 요청=3에 공급=2처럼 전량 배정 전에도 일부 공급은 존재한다. 발주 연결과 확보 수량, allocation과 reservation을 동시에 빼면 수요나 공급이 사라지거나 중복된다.

- 반례 A: A=3, 발주 L1=3 최종 확보 2. 아직 allocation은 0, pool은 2, L1의 미확보 1은 최종 해제돼야 한다. 신규 발주 필요량은 1이어야 하며 0 또는 3이면 실패다.
- 반례 B: 위 상태에서 L2=1이 진행 중이면 신규 발주 필요량은 0이다. L2 확보 1 뒤 A 전량3 배정 시 pool은 0이어야 한다. reservation도 3이라고 물리 공급을 6으로 세면 실패다.
- 반례 C: A 취소/동의 만료가 L2 최종 공급 전에 발생한다. 제출 발주 자체는 남지만 active demand link는 해제돼야 한다. L2가 도착하면 취소된 A로 재연결하지 않고 source가 있는 pool로 전환한다. 그 사이 신규 고객 B를 위한 발주에서 이미 확보한 pool을 두 번 할당하거나 진행 중 공급을 미리 확보로 세면 실패다.
- 반례 D: 결제 성공 후 수령 만료된 1개는 자동 재판매가 제외됐으므로 pool에 재투입하면 안 된다.

보완할 최소 계약: source line별 확정 확보량은 `미배정 pool + 유효 결제실패 점유 + 결제 성공에 귀속된 물량`으로 한 번만 분해한다. 결제 성공 물량 안의 입고대기/픽업가능/수령완료/수령만료는 상호 배타 상태다. allocation/reservation/event는 동일 물량의 관계 기록이며 별도 추가 재고가 아니다. 진행 중 발주 link는 미확정 약정 수량으로 별도 보존하고 공급 최종 확정·취소·동의 부적합 때 각각 어떤 link가 비활성화되는지 지정한다. 신규 발주 산식은 동일 session/store/SKU/호환조건 그룹에서 pool과 active link를 한 번씩만 차감하고 음수는 0으로 고정한다. 요청별 상세와 그룹 합계도 이 투영을 사용한다.

정확한 테이블 이름은 구현자가 정할 수 있다. 그러나 이 보존식·전이 기대값은 schema/테스트 전 확정해야 한다. MOQ/배수 때문에 1개 보충 발주가 불가능한 사례는 보류가 정답이며 보존식을 깨서 MOQ만큼 초과 발주하지 않는다.

## 3. [높음] 결제실패 점유 중 동의 만료·조건 변경·취소와 재동의 복귀

10분 점유/2회 실패 해제는 정했지만 7일 동의 만료나 가격 변경이 그보다 먼저 발생할 때 점유·발주 link 처리 순서가 미정이다. 명시 재시도도 원래 동의와 모든 조건을 다시 검사해야 한다.

- 반례 A: 동의 만료 1분 전에 최초 결제가 실패했다. 2분 뒤 고객이 재시도한다. 점유 10분 이내여도 동의가 만료됐으므로 결제하면 안 된다.
- 반례 B: 최초 실패 뒤 판매가가 2,000원→1,800원으로 내려갔다. 금액이 적어도 초안 O-05에 따라 자동/수동 retry 결제를 막고 조건 확인으로 가야 한다.
- 반례 C: 실패 점유 중 취소와 retry가 큐에 연속 들어온다. 취소가 먼저 확정되면 물량 1회 해제·retry 거절이고, 결제가 먼저 성공하면 취소 거절이다.
- 반례 D: 실패 2회 뒤 review_required에서 새 동의한다. 시도 횟수를 lifetime 총 2회로 유지하면 정상 복귀가 영구 차단된다. 반대로 동일 consent/배정에 대해 새 command_id만 바꾸어 2회 한도를 우회하면 실패다.

보완할 최소 계약: 큐의 각 command에서 deadline/동의/현재 조건/취소 상태를 먼저 재검사한다. 동의 만료·조건 불일치·취소·10분 만료·2회 실패 중 먼저 확정된 사건이 점유를 정확히 한 번 해제한다. 해제 시각을 알림 48시간과 섞지 않는다. 실패 보유분의 만료는 `now >= hold_deadline`에서 retry 불가로 고정한다. 새 동의는 이전 allocation/실패 cycle을 닫고 새 순번·새 consent_version·새 payment cycle로 진입해 최초 자동 시도 1회+명시 retry 1회를 가질 수 있도록 한다. 이전 cycle의 지연 command는 새 물량을 소비하지 않는다. 결과 미확인은 durable 결과 조회가 우선이며 알려진 failure만 retry 횟수에 따라 처리한다.

회귀: 7일 및 10분의 직전/정각/직후와 동시 경계, price up/down, 취소/재시도 양 순서, 새 동의 뒤 성공, 이전 command 재전송. 전체 실패에서 성공 예약 알림 0, 해제 후 다음 유효 FIFO 정상 성공을 확인한다.

## 4. [높음] KST 일예산의 발생일 귀속과 비용 snapshot

승인 시 점유하고 공급 최종 확정 때 미확보 매입액을 해제한다는 규칙은 자정을 넘는 발주에서 어느 날짜 장부를 수정하는지 미정이다. 현재일 used를 줄이면 새 날짜 예산이 잘못 증가한다.

- 반례: 9월21일 23:59에 단가1,000원·수량10을 승인해 그날 10,000원을 점유한다. 9월22일 00:01에 확보6으로 확정한다. 해제4,000원은 21일 장부에만 반영돼야 하며 22일 사용액을 음수로 만들거나 22일 신규 발주 한도를 늘리면 실패다.
- 추가 반례: 발주 이후 카탈로그 매입가가 1,200원으로 바뀐 상태에서 4개 미확보를 해제한다. 현재 단가로 4,800원을 환원하면 원 승인과 보존식이 어긋난다.

보완할 최소 계약: 발주 승인 시 budget_day(KST), 정수 매입단가·총 점유액을 immutable snapshot으로 저장한다. 공급 결과의 확보/해제는 그 장부와 단가를 사용한다. 하루 사용액은 당일 승인 건의 진행 중 점유+최종 확보 원가이며 취소된 고객 요청만으로 되돌리지 않는다. 공통 clock jump도 기존 날짜 귀속을 이동시키지 않는다. 정책 예산 수정이 적용되는 날짜/향후 정책 범위와 현재일 이미 사용액 미만 거절을 명시한다.

회귀: 자정 전후·0공급·부분/전량 공급·재확정·매입가 변경·day jump·그날 used와 다음 날 allowance를 대조한다.

## 5. [중간] 수량 감소와 동의 갱신의 순번 규칙 충돌

O-02는 “감소는 순번 유지”와 “동의 재작성은 새 순번”을 같이 명시한다. O-03은 동의 tuple에 수량을 포함한다. 따라서 A가 미연결 pending 수량5→3으로 줄일 때 동의 수량을5로 남기면 조건 불일치이고, 동의 tuple을3으로 쓰면 새 순번 규칙과 충돌한다.

보완할 최소 계약: 수량 감소도 고객이 변경된 수량·금액을 명시 확인하고 consent tuple을 갱신한다. 이 경우만 순번 유지인지, 또는 모든 재동의가 새 순번인지 하나를 정한다. 감소 시 동의기한이 갱신되는지도 명시한다. 이 검토자의 권고는 유효 동의 상태에서 고객 명시 감소만 순번을 유지하고, 이미 만료/조건불일치/review_required인 요청의 재동의는 새 순번으로 처리하는 것이다. 감소 확인을 동의 없이 자동으로 긍정 처리하지 않는다.

회귀: A5(선두)·B1에서 A3으로 감소, 이후 공급3의 대상·동의 tuple·시각·deadline 확인. 같은 감소라도 만료된 A는 새 동의·새 순번이고 B를 앞서면 실패다.

## 보완 없이 유지 가능한 선택 및 구현 시 명확히 할 사항

- 전량 FIFO가 선두를 건너뛰지 않으면서 이미 결제실패 점유된 요청 뒤의 남는 pool을 어떻게 처리할지는 점유량을 빼고 유효 pending에 적용하면 된다. 뒤 고객의 결제를 막기 위해 선두에 이미 점유된 수량을 두 번 요구하지 않는다.
- 동일 command_id에 다른 payload를 보낸 경우 원 결과를 그대로 신규 행동 성공처럼 표시하지 않도록 command payload fingerprint 불일치를 거절한다. 동일 payload 재전송은 기존 durable 결과다. 이는 중복 방지 구현 기대값으로 명시하면 된다.
- 세션 reset/generation과 snapshot 저장 실패의 복원은 방향이 적절하다. 서버 LLM 결과가 늦게 도착해도 reset 전 command를 새 세션에 쓰지 않도록 generation을 검증한다.
- 7일은 미결제 동의에만 적용하고 결제된 입고대기 예약에는 pickup_deadline이 없다는 문구는 적절하다. 기한을 하나로 합치는 대안은 기각해야 한다.
- 결제 완료 취소/자동 환불/폐기/재판매를 제외하는 것은 명시된 데모 단순화로 기록할 수 있다. 기록 보존과 경영주 상태 조회는 계속 필요하다.

## 다음 검토와 증거

조정자는 1~5를 정책 본문에 보완하고 새 ADR hash를 전달하면 된다. 보완이 위 반례를 닫고 필수 정상 흐름을 유지하면 새 논점을 늘리지 않고 2차로 닫는다. 이 보고서의 제안은 아직 채택 정책/테스트 성공이 아니다. 구현 후 정상 구매·7일 재동의·실패 해제·복수 source 입고·예산 날짜·수량 보존을 실제 SQLite와 두 역할 브라우저에서 별도 실행해야 한다.
