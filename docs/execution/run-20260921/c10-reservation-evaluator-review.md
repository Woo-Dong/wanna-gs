# C10 사전 예약 독립 평가 검토

상태: **조건부 적합 제안, 아직 새 설정 채택/모델 실행 없음.** 읽기 전용 계약·실행기 검토와 임시 장부 실험만 수행했다. C9의83/84 최소PASS·C5핵심범주 회귀에 따른 채택FAIL, val02/holdout STOP을 유지한다. 목표/정답/필수 평가 분모/95·90/정상 회귀0/$20·2400을 변경하지 않는다.

## 계약과 실행기의 차이

ADR003 오류처리의 '최초포함최대3회'는 일시429/timeout에 대한 상한이다. 모든 미래 turn을 반드시 세 번 실행하거나 처음부터 세 번분을 보장하라는 최소 호출 수는 아니다. 비용행과 채택보완은 실제 turns·retry 여유 및 필수 best/holdout/G5/G6를 먼저 예약하도록 한다. docs25도 실제 사용량을 대조해 선택 실험부터 줄이고 필수미완료를 숨기지 않도록 한다. 따라서 결과를 본 뒤 실패 분모를 줄이는 방식은 허용되지 않지만, 새 후보 실행 전에 미래 필수1회와 명시적인 추가 retry 여유를 고정하는 것은 가능한 운영 재산정이다.

현재 `scripts/run_nl_eval.py`의 Runner.run은 각 outbound 직전에 후속예약 합계에 `remaining*3-len(attempts)-1`을 더한다. Budget.reserve는 여기에 실제 다음1회를 더해2400 상한을 검사한다. 비용은 실제 장부 + 다음unknown$.05 + 후속cost reserve가20 이상이면 STOP한다. 따라서 현재 실행 단계의 최대3회 예약은 그대로 유지하며, 다음 단계로 진입할 때 실제 새 장부와 해당 단계의3회 예약을 다시 검사한다. 후속예약을 낮추어도 전체 장부 가드는 없어지지 않는다. 반면 후속의 모든 turn×3 완주 보장은 포기해야 하며, 다음 단계가 실제 필수1회분은 남아 있어도 보수적 진입 가드 때문에 STOP할 수 있다.

## 구체 제안: 미래 NL turn당 필수1회+retry여유1회

| 실행 단계 | 고정 후속 예약 | 합계 | 추정비용(.0105/attempt) |
|---|---|---:|---:|
| dev30/34 | validation92×2repeat×2attempt + holdout92×2 + UX84 + QA/G6 12 |648|$6.804|
| validation84/92 동일 두 반복 | 후속 validation92×2 + holdout92×2 + UX84 + QA/G6 12 |464|$4.872|
| 신규 holdout84/92 최초1회 | UX84 + QA/G6 12 |96|$1.008|

미래 필수 NL분모는 validation92×2와 holdout92 그대로이며 추가 미래 retry 여유276회를 초기 dev후속에 둔다. 현재 단계의 일시 장애는 원래 최대3회와 현재stage×3 예약을 적용한다. '미래2attempt 예약'을 실제 모든 호출의 retry 상한2 또는 두 번째 시도 의무로 해석하지 않는다. 별도 성공선별 재실행 권한은 생기지 않는다. UX84는 ADR007의 고정 두 arm 전체 workload이고, QA/G6는 필수8+복구여유4다. 해당 실측 계획이 바뀌면 호출 전 예약도 다시 검토해야 한다.

현재 upper1476/$9.2915701에서 dev최대102+후속648=2226, 비용 계획$9.2915701+750×.0105+.05=$17.2165701이다. .0105는 운영 추정치이며 공급자 최악 비용 보장이나 실제 청구액이 아니다. 실제 token usage/unknown에 의한 비용STOP은 유지한다.

## 임시 장부로 실제 Budget.reserve 재현

실장부를 메모리에서 읽고 임시파일에 복사했다. 추가된 성공 호출과 비용은 합성 경계 조건이며 실측으로 주장하지 않는다. 실제 HTTP/모델0·실장부 쓰기0·보호 raw 접근0이다.

| 조건 | 호출 가드 합계 | 결과 |
|---|---:|---|
| 기존 dev후속924 |1476+102+924=2502|CALL_RESERVE_STOP|
| 제안 dev후속648 |1476+102+648=2226|ALLOWED|
| 정상dev34 뒤 val01 |1510+276+464=2250|ALLOWED|

따라서 정상 성공 경로는 진입 가능하고 실제 초과 경계는 차단된다. 두 validation config의 보수적 중복예약도 그대로 남긴다. 모든 단계 최대retry를 끝낼 수 있다는 주장은 하지 않는다. Budget의 후속예약 숫자만으로 각 업무 분모가 의미적으로 검증되는 것은 아니므로, 독립 계획 검토·실제 고정 dataset turns/UX/QA 계획·불변 config 결속을 함께 유지해야 한다.

## 채택 경계와 증거

이 제안은 기존 상한 내 미래 선택 retry 여유의 재산정이며, runner/SDK/정답/사례/채점/필수 평가를 바꾸지 않는다. root의 D48 위임 판단과 별도 두 번째 관점의 분모·운영 검토 후 새 config에 고정할 수 있다. 이미 실행된 설정·실패를 덮지 않는다. 정확 source/CI/Production proof/모델 결속·GO 전에는 호출하지 않는다. 두 validation 반복 각각의 최소/정상·핵심 회귀 조건 통과 전 freeze/holdout은 금지다. 새 보호셋은 별도 GO와 최초1회만 허용하며 실패를 재시도 성공으로 대체하지 않는다.
