## 반례·인접 정상 흐름 확인

| 사례 | 판단 |
|---|---|
| 수요8/capacity10 승인 뒤 공급3 | 접수 capacity2를 유지하고 부족5를 pending에 남긴다. 공급 부족을 고객 취소/기한 만료로 치환하지 않고, 원래8개 접수 한도를 자동 복원하지 않아 같은 부족5의 무한 자동발주를 막는다. |
| 잔여 capacity2와 부족5 | 기존 ADR-002대로 pool/진행coverage를 먼저 차감하고 MOQ/예산/조건을 만족하는 최대2만 새로 발주할 수 있다. 최초 실패를 이유로 잔여의 모든 정상발주를 막는 정책은 아니다. 2 추가승인 뒤 capacity0이면 보류하되 수요는 보존한다. |
| capacity10 명시 재설정 | 새 절대값·revision과 최신 수요 재계산을 요구하므로 실제로 추가 공급 가능 조건을 시연할 정상 복귀 경로가 있다. 예전 요청8을 무조건 다시 주문하지 않고 유효 미확보량만 대상으로 한다. 자동정책off이면 조건 변경만으로 수동 발주하지 않는다. |
| 승인이 stale/예산부족/저장실패 | 같은 transaction 재검사·rollback으로 capacity/예산만 소모되고 발주가 없는 상태를 방지한다. 실패 뒤 정상 조건 재시도 가능성을 유지한다. |
| 요청 취소·중복 클릭 | ADR-002가 제출 발주를 소급 취소하지 않으므로 capacity 자동복원 없음과 일관된다. 동일 command/payload replay는 이전 결과이며 capacity 재차감하지 않는다. 명시적 조건 재설정도 기존 command/generation/역할·점포 검사 적용 대상으로 구현한다. |
| 고객/경영주 이해 | 재고·추가 접수량·진행 발주·확보/미확보를 분리 표시하고 0의 보류사유를 알리는 계약이어서 공급cap을 소매 재고/확보 보증으로 오인하지 않는다. 고객이 정상 요청을 남기는 경로와 경영주 묶음/상세는 유지된다. |

‘같은 capacity 최대치를 매번 재사용’ 또는 ‘부족 확정 때 자동 환원’은 자동재검토 이벤트와 결합해 반복 발주를 유발할 수 있어 기각에 동의한다. capacity를 소모하는 방식은 승인 가능한 공급 범위를 제한하는 모의 정책이며 실제 공급자 계약이나 발주 성공 보장이 아니다.

비차단 문서 정리: 본문 CORE-6/7/8 표기를 원장 형식 CORE-06/07/08로 맞추고 채택 시 DECISION_INDEX·policy key·영향 task/context를 갱신한다. 새 요구나 재검토 차단 조건은 아니다.

필수 실행 증거는 초안에 제시된 숫자 사례 그대로 단위/실제 SQLite/중복 명령·snapshot 실패와 정상 복귀에 연결한다. 정책 논리 찬성을 앱 테스트 PASS로 표시하지 않는다.
