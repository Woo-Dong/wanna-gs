## 기존 문서가 허용하는 범위

ADR003은 UX8종 각각3회, baseline/best 동일 workload·seed·viewport·clock, 최대 조작·화면이동 증가0, 비모델 완료시간 중앙값10% 초과악화 금지, 정상 필수 시나리오100%, 실패 분모 공개를 정했다. 현재 원본은 이를 비교할 만큼 완주하지 못했다. clear-1 성공2개의 중앙값을 세 반복 완료 기준선으로 사용하거나 나머지 업무에 확장할 수 없다.

ADR003의 ‘baseline336 case만1회’는 NL 기준선에 대한 조항이다. 이것을 UX 재측정 금지로 확장할 근거는 없지만, 반대로 UX 실패 후 무제한 새 run을 허용하는 조항도 아니다. docs15는 모델/프롬프트/사례를 고정한 재현, 원인 가설·제한적 재검증을 허용한다. 그러나 ‘재현되지 않는 실패는 원인 불명으로 남기고 통과 횟수만으로 닫지 않는다’고 명시한다. 즉 같은 B0가 다음에 통과해도 최초 모델 오류가 해결됐다고 주장할 수 없다.

docs23은 기준선/후보/최선 버전과 실패 결과를 보존하며 무작위 모델 변동을 개선으로 단정하지 않도록 한다. 비교 가능한 기준선 없이 개선 완료를 선언하지 못한다. 따라서 새 실행 중 좋은 것만 고르거나 성공 사례를 모아3회를 만드는 것은 금지된다. 문서의 일시 5xx/timeout 재시도 일반안은 이미 고정된 UX 도구의 no-retry/stop 계약을 조용히 바꾸는 근거가 아니다.

**공백:** 실패한 전체 UX run 이후 한 번의 재측정을 허용할지, 어느 run을 비교의 참조선으로 사전 지정할지, 두 run의 누적 실패·미실행을 어떻게 연결할지에 대한 절차가 없다. 이는 제품 최소기준을 바꾸는 문제가 아니라 측정 복구의 참조선·출처 관리 문제이므로 docs17의 최소 위임 ADR로 한정해 해결할 수 있다.

## 최소 ADR 초안 권고

다음 내용만 정하고 다른 모델/질문/상품/합격선은 바꾸지 않는다.

1. 최초 B0 NL 기준선 및 최초 UX run은 영구 보존한다. 원본 결과에 재개하거나 행을 덮어쓰지 않고, 이번 중단은 resolved/PASS로 승격하지 않는다.
2. **같은 B0 전체8×3의 새 재측정 한 번**만 사전에 지정한다. 실패한 clear-1만 재시도하거나 최초 성공2개와 새 성공1개를 합치지 않는다. 새 run ID·독립 context/DB를 쓰고 고정 순서·workload/harness/모델·프롬프트·검색·schema/catalog·seed·clock·viewport를 그대로 유지한다. 실제 build/source 일치를 먼저 확인한다.
3. 원래 no-retry/중단 조건을 유지한다. 새 run도 오류가 나면 해당24분모와 미실행을 남기고 비교 NOT_READY다. 결과를 보고 세 번째 재측정을 추가하거나 다른 실행으로 참조선을 교체하지 않는다. 추가 정책 변경이 필요하다면 새 증거·원인·독립 검토가 필요하며 이 ADR이 자동 권한을 주지 않는다.
4. 새 실행을 시작하기 **전에** 공식 비교용 재측정 ID를 지정한다. 완주24/24 correctness가 확보될 때만 그 단일 run의 workload별 최대 조작·이동 및 세 반복 중앙값을 best와 비교한다. 첫 run 실패가 사라졌거나 B0의 정상 성공률이100%가 되었다고 표현하지 않는다. 첫 run과 재측정의 성공시간을 섞거나 느린 기준선을 택하지 않는다.
5. 실제 best는 기존 정상 필수100%, 최소 정확도·불변식, UX24회 전부 정상, 두 validation/holdout 및 역할 QA/G5/G6를 그대로 충족해야 한다. B0의 NL 실패나 최초 UX 실패는 새 best의 성공 증거로 바뀌지 않는다. 동일 workload/seed/clock과 최대조작·화면이동 증가0·중앙값10% 규칙을 유지한다.
6. 새 호출 전 동일 goal Budget/prior50 장부에 명시 호출상한 및 남은 validation/holdout/best UX/G5/G6 예비량을 예약한다. 전체2400회/$15를 늘리거나 초기3회를 비용/호출에서 제거하지 않는다. 새 승인 config는 실제 시행 결정을 내린 조정자가 발급한다.
7. release 증거에는 최초 실패 run과 재측정 run의 해시·관계·사전지정 참조ID 및 두 분모를 함께 연결한다. gate에는 단순히 성공한 두 번째 결과만 넣고 이력을 숨기지 않는다. 필요하다면 recovery provenance 검사만 보완하고 제품/성능 기준은 완화하지 않는다. 원본의 blocked/complete flags를 수정하지 않는다.

## 반례와 목적 보존

- 계속 새 run을 돌려 우연한24PASS를 얻으면 취약한 B0의 실제 실패가 숨는다. 1회 사전지정·자동추가금지와 실패원본 병기가 이를 제한한다.
- 마지막21건만 실행하면 workload/반복의 순차적 노출과 실행 경계가 달라지고 성공 조각을 합치게 된다. 전체 동일24 재측정으로 한정한다.
- B0에 C1 검색/enum을 넣고 baseline이라고 부르면 개선전후 비교가 사라진다. B0 source 그대로, 개선은 별도후보로 유지한다.
- 전부 거절·fixture 대체·추가질문 삭제로 오류를 없애면 고객의 정상 상품요청 목적을 훼손한다. 실제 best 정상성공/동의·대체·미식별/경영주 업무량 기준을 모두 유지한다.
- 실패시간을 성공완료 중앙값에 넣어 기준선을 느리게 만들면 best의10% 기준이 느슨해진다. 실패는 실패 분모로 공개하고 성공 완료시간과 섞지 않는다.

채택 전에는 ②가 현재 판정이며 원래 기준 아래 제품개선·독립 작업은 계속할 수 있다. 최소 ADR 채택 여부는 조정자가 두 독립 검토를 대조해 결정한다. 본 검토로 새 모델 호출이나 기준선 대체는 실행하지 않았다.

## G5 checker 최소 변경 계약 제안 — 구현하지 않음

기존 `ux.baseline`에는 사전지정 재측정의 실제 live24 결과를 넣고, 기존 `ux()`의 baseline24/24 정상 및 best 성능 비교는 그대로 둔다. 최초 실패 원본을 그 함수에 넣어 성공조건을 우회하거나 완화하지 않는다. 대신 `ux.baseline_recovery`라는 provenance 연결만 추가하는 범위가 적절하다.

1. **필수 연결:** ADR006을 적용한 release에서는 recovery 블록이 필수다. 블록에는 채택된 ADR reference, 최초 실행의 공개 정제 증거 reference, 승인/사전지정 실행 reference를 기존 `{path,sha256}` 형식으로 연결한다. 키를 누락하면 일반 성공 baseline으로 돌아가 원본 실패를 숨길 수 없도록 한다. 일반적인 모든 미래복구를 위한 추상화는 필요 없다.
2. **고정 정체성:** original run ID=`ux-baseline-b0-v2-01`, private 원본 result SHA=`4989b1053468134ff8a3099b951493ba483687f57fb14de49db48ea4e87b4209`, 지정 recovery ID=`ux-baseline-b0-v2-recovery-01`. 실제 `ux.baseline.runId`가 recovery ID와 일치해야 한다. 원본·recovery·best ID는 달라야 한다. 원본 private 파일은 checker가 열지 않고, 원본해시와 공개 정제파일해시를 구별한다.
3. **실패 분모 재계산:** 최초 정제 증거는 고정 workload8종/반복1·2·3 예정집합과 실제3개 row의 workload/repetition/status만으로도 분모를 재계산할 수 있다. 중복·없는 업무·범위 밖 반복을 거절하고 결과가 expected24/executed3/passed2/failed1/missing21, complete=false 및 기존 stopCode와 일치해야 한다. cached summary만 믿지 않는다. 요청/대화/사용자상세/보호holdout 본문은 공개할 필요가 없다.
4. **동일 실행조건:** original 정제증거와 recovery의 B0 제품/서버 source hash 집합, 모델·prompt·catalog/schema, seed/clock/viewports/workload/harness를 대조한다. 원본에 없는 모델 설정은 실제 최초 승인 config/실행기록에서 정제한 연결증거를 사용한다. best 소스는 개선으로 달라질 수 있으므로 이 동일성은 **original↔recovery**이고, 기존 baseline↔best workload 비교는 별도로 유지한다. 원격 실행사실은 독립 보고 한계 안에서 판정한다.
