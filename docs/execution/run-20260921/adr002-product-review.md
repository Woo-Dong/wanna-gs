## 판정

**수정 후 채택 찬성. 현재 원문은 아래 세 공백을 해소하기 전 채택 보류 권고.** 한 탭에서 순차 처리하고 전량 FIFO·7일 미결제 동의·10분 결제 점유·2회 시도·엄격한 예산을 쓰는 단순화 자체는 위임 범위이며 사용자 고정 요구와 충돌하지 않는다. 실제 GS 정책으로 주장하지 않은 점도 적절하다. 아래는 새 기능 제안이 아니라 현재 계약의 정상 복귀·대체 의도·입고 의미를 보존하기 위한 명시화다.

## 필수 수정 요청

### PV-01 — 대체 ‘전환’과 별도 추가 구매를 구별

- 위치: O-05의 `SKU/점포 대안은 별도 새 요청+동의`.
- 구체 반례: 고객이 A 1개를 미확보 상태로 기다리다 B로 바꾸려 한다. B 확인·동의를 받고 별도 요청만 만들면 A와 B가 모두 유효 수요로 남아 각각 자동발주·결제된다. 새 동의만으로 고객의 ‘대신’ 의도를 보존한 것이 아니다.
- 기준: 27번은 추천 노출/선택으로 원요청을 바꾸지 않되 **새 요청 전환에서 이중 수요·중복 발주를 방지**하도록 O-02/O-04/O-05에 명시하라고 요구한다.
- 최소 보완: 추천과 거래 변경을 계속 분리한다. 전환 최종 확인에 원요청 처리 결과를 포함하고, 결제 전 원요청 취소+새 요청 생성/동의를 한 원자적 도메인 명령으로 처리하거나 원요청을 명시 취소한 뒤 새 요청으로 연결한다. 새 요청 실패 시 원요청 상태가 예측 가능해야 한다. 이미 결제 성공한 원요청은 취소 가능한 것으로 안내하지 않는다. 고객이 두 상품을 모두 원한다는 별도 의도를 확인했을 때만 추가 구매로 유지한다.
- 필수 회귀: 대체 노출/거절 시 A 불변; 전환 성공 후 A의 신규발주 수요0/B 1; 전환 실패 시 한쪽만 임의 소실/이중 생성 없음; 이미 결제된 A 전환 제한과 원래 픽업 유지; 원니즈→대체 요청 lineage 보존.

### PV-02 — 보류 가능한 예외와 실행 묶음의 무효화를 분리

- 위치: R-08/09의 `하나라도 stale/불법이면 전체 transaction 거절·새 제안`와 O-08/12의 MOQ/예산 보류.
- 구체 반례: 10품목 중 1품목이 정상적인 공급/MOQ 제한 예외다. 자동발주가 이를 실행 후보에 포함하고 전체를 ‘불법’으로 실패시키면 나머지 9품목도 영구 보류될 수 있다. 경영주는 같은 예외를 제거하고 매번 재승인하게 된다.
- 기준: CORE-05/25와 27번은 승인 정책 안 정상 자동발주, 정책 밖 항목만 보류, 성공/실패/보류 한 요약을 요구한다. 전부 보류로 성공 경로를 없애면 실패다.
- 최소 보완: 제안 단계에서 공급/MOQ/범위/예산 등 알려진 예외를 `deferred`로 명시하고 유효 실행 집합을 만든다고 고정한다. **그 실행 집합**의 revision/권한/동의 불변식이 달라진 경우 전체 거절은 허용한다. 자동 정책의 갱신 가능한 제안 재계산은 새 정책 동의를 요구하지 않는다. 수동 승인의 의미가 달라지는 경우에만 새 묶음을 한 번 확인한다.
- 필수 회귀: 유효9+보류1은 유효 품목 실행·보류 사유 표시; 실행 집합 중 stale1은 0실행 후 새 제안; 변화 없는 재조회는 재승인/알림0; 반복 실행 주문 중복0.

### PV-03 — 여러 공급 line을 합친 전량 예약의 픽업 시점 명시

- 위치: O-01 회차 간 확보 잔량 합산, R-02/03/04 line별 입고, O-07 입고와 알림 동일 transaction.
- 구체 반례: 선두 요청3개를 공급 line A의2개와 B의1개로 확보해 전량 예약한다. A만 입고됐는데 `입고와 알림 동일 transaction`을 요청 알림 생성으로 해석하면 아직 1개가 도착하지 않은 예약의 48시간이 시작된다. B가 늦게 오면 고객은 상품 전부를 받을 수 없는데 만료된다.
- 기준: D-42, CORE-07/10, 전량 수령 정책. 확보와 입고는 다른 상태다.
- 최소 보완: line 입고는 그 line의 확보량을 입고 처리하되 **예약에 배정된 전체 수량의 모든 출처가 입고된 경우에만** 해당 예약의 첫 픽업 알림/48시간을 원자적으로 생성한다고 명시한다. 이미 입고된 pool에서 나중에 예약을 만들 때는 모의결제 성공 및 전량 입고를 확인한 예약 준비 시점에 알림을 생성한다.
- 필수 회귀: A2 입고/B1 미입고는 예약 입고대기·deadline 없음; B1 입고 순간 첫 알림+48시간; 중복 입고/알림 재생성은 기한 불변; 이미 입고된 pool로 정상 예약 즉시 픽업 가능.

## 찬성 및 비차단 확인 사항

| 항목 | 판단·필수 구현 확인 |
|---|---|
| 정상 성공 | 정확 상품은 추가 질문 없이 확인 카드, 유효 정책 안 자동발주 정상 실행, 공급→결제→예약→입고·48시간 흐름 유지. 안전을 이유로 모든 요청을 거절하지 않는 계약에 찬성. |
| FIFO | 전량 FIFO에서 선두3/공급2 대기는 명확한 선택이고 근거 있는 예측 가능성을 준다. 고객/경영주에는 ‘앞 요청의 전량 확보 대기’와 확보 잔량을 설명해야 한다. 재동의·수량 증가 후 순번 이동은 확인 전 보여주고 감소는 기존 동의 범위/총액 처리도 명세에 연결한다. |
| D-40 | 팀원 M-01~13을 채택하거나 모집 회차/픽업 제외를 되살리지 않는다. 기존 독립 구현의 세부 정책으로 읽히므로 준수. |
| D-41 | 총 접수 상한 없음, 개별 수량1~20은 위임 가능한 유효 범위. MOQ를 넘는 13명/추가 요청이 잘리지 않는 회귀를 유지해야 함. |
| D-42 | 7일은 미결제 동의만, 결제 완료 예약 소급 만료 금지는 적합. PV-03의 입고 합산 경계까지 보완하면 의도가 명확해짐. |
| D-43 | 동일 snapshot 집계와 고객 상세 합계 불일치 시 승인 차단에 찬성. 실제 상세는 상품·수량·가격·동의 여부/시각·순번·발주 연결·확보/배정/결제/예약/픽업을 모두 표시하고 읽기 전용으로 유지해야 함. |
| 업무 부담 | 1회 묶음 승인·초기 자동off·승인 정책 on 이후 건별 승인 없음은 적합. PV-02를 보완하고 mixed 결과 요약·정책 해제·같은 묶음 반복 조회를 편의성 QA에 넣을 것. |
| 한 탭/보존 | 단일 Worker·commit/export/내구 저장 완료 뒤 성공·generation 늦은 응답 차단은 요청 성공 후 새로고침 손실 위험을 줄인다. 실패 시 UI가 성공으로 남지 않는 브라우저 확인이 필요. |

## 재검토 조건과 한계
